はじめに

Claude Code のインストールから最初のワークフロー、パーミッションモデルまでの基礎知識

1.1 Claude Code とは

▼

◆ 概要

Claude Code は Anthropic が提供する公式 CLI ツールです。ターミナルから直接 Claude を呼び出し、コードベース全体を理解・編集・実行できるエージェント型の開発支援ツールです。

  • オーケストレーション層: Claude Code はモデルとファイルシステムの間に位置するオーケストレーション層として機能する
  • エージェントループ: 内部では while(tool_call) ループを実行し、モデルが自律的にツールを選択・実行する
  • ツール統合: Bash、ファイル読み書き、検索などのツールをモデルが自由に使用できる
  • IDE 統合: VS Code や JetBrains に拡張機能として組み込み可能

✓ 設計哲学

「スキャフォルディングを減らし、モデルを信頼する」 — Claude Code は複雑なパイプラインや分類器を使わず、モデル自身に判断を委ねるシンプルな設計を採用しています。DAG（有向非巡回グラフ）もクラシファイアも RAG も使わず、モデルが全てを決定します。

1.2 インストール

▼

Node.js 18 以上が必要です。以下のコマンドでグローバルインストールします。

# グローバルインストール
npm install -g @anthropic-ai/claude-code

# インストール確認
claude --version

# 初回起動（認証フロー開始）
claude

★ 認証方法

  • Anthropic アカウント: ブラウザ経由で OAuth 認証
  • API キー: ANTHROPIC_API_KEY 環境変数を設定
  • Amazon Bedrock: --provider bedrock フラグで接続
  • Google Vertex AI: --provider vertex フラグで接続

1.3 最初のワークフロー

▼

◆ 基本フロー

Claude Code の基本的な使用フローは以下の4ステップです:

  1. claude を起動 — ターミナルでプロジェクトディレクトリに移動し claude を実行
  2. プロンプトを入力 — やりたいことを自然言語で記述
  3. レビュー — Claude が提案するファイル変更やコマンドを確認
  4. 承認 — 問題なければ承認して実行
# プロジェクトディレクトリで起動
cd my-project
claude

# ワンショットモード（対話なし）
claude "src/api.ts のエラーハンドリングを改善して"

# パイプモード（CI/CD 用）
echo "テストを書いて" | claude -p

1.4 パーミッションモード

▼

Claude Code は安全性を確保するため、複数のパーミッションモードを提供しています。Shift+Tab でモードを切り替えられます。

モード説明用途
Default読み取りは自動許可、書き込み・実行は都度確認通常の開発作業
acceptEditsファイル編集を自動許可、Bash コマンドは都度確認信頼できるコード編集
Plan Mode読み取り専用。計画のみ立案し実行しない調査・設計フェーズ
dontAsk許可リストのツールを自動承認繰り返し作業
bypassPermissions全ツールを自動承認（Docker 推奨）CI/CD、サンドボックス環境

! 注意点

bypassPermissions はローカル開発では使用しないでください。必ず Docker 等のサンドボックス環境で使用すること。セキュリティリスクが非常に高いモードです。

コア概念

マスターループ、コアツール、コンテキスト管理 — Claude Code の内部動作を理解する

2.1 マスターループ

▼

◆ while(tool_call) ループ

Claude Code の中核は極めてシンプルな while(tool_call) ループです。DAG（有向非巡回グラフ）もクラシファイアも RAG も使用せず、モデルが全てを決定します。

  • モデルにプロンプトとツール定義を送信
  • stop_reason を検査: "tool_use" ならツール実行 → 結果を履歴に追加 → 再送信
  • stop_reason が "end_turn" なら完了
  • モデルがどのツールをいつ使うか自律的に判断する
# Claude Code の内部ループ（簡略化）
while True:
    response = call_model(messages, tools)
    if response.stop_reason == "end_turn":
        break  # 完了
    for block in response.content:
        if block.type == "tool_use":
            result = execute_tool(block)
            messages.append(response)
            messages.append(tool_result(result))

✓ stop_reason によるループ制御

stop_reason は2つの値を取ります:

  • end_turn — モデルがタスク完了と判断。ループを終了する。
  • tool_use — モデルがツール呼び出しを要求。ツールを実行し結果を返す。

重要: テキスト内容や自然言語で完了を判定してはいけない。stop_reason のみが信頼できる終了条件。

2.2 8つのコアツール

▼

Claude Code はモデルに以下の8つのコアツールを提供します。モデルはタスクに応じてこれらを自律的に選択します。

ツール機能用途
Bashシェルコマンド実行ビルド、テスト、git操作、任意のCLI
Readファイル読み取りソースコード閲覧、設定確認
Edit部分的なファイル編集既存ファイルの修正（差分ベース）
Writeファイル全体の書き込み新規ファイル作成、全面書き換え
Grep正規表現検索コード内のパターン検索
Globファイルパターンマッチファイル名でのファイル検索
Taskサブエージェント生成独立した調査・実行タスクの委譲
TodoWriteTODO リスト管理タスク進捗の追跡

★ Grep vs Glob の使い分け

  • Grep: ファイル内容を検索（「この関数を呼んでいる箇所は？」）
  • Glob: ファイル名を検索（「*.test.ts ファイルはどこに？」）

2.3 200K トークンバジェット

▼

◆ コンテキストウィンドウの構造

Claude Code は 200K トークンのコンテキストウィンドウを以下の要素で共有します:

  • システムプロンプト — ツール定義、CLAUDE.md の内容、パーミッション設定
  • 会話履歴 — ユーザーメッセージとアシスタントレスポンスの全履歴
  • ツール結果 — ファイル内容、コマンド出力、検索結果など
  • レスポンスバッファ — モデルが応答を生成するための余白

! コンテキスト管理の重要性

大きなファイルを読み込んだり、長い出力を持つコマンドを実行すると、コンテキストウィンドウが急速に消費されます。これが Claude Code の最大の制約であり、効果的な使用にはコンテキスト管理が不可欠です。

2.4 サブエージェント（Task ツール）

▼

◆ サブエージェント = 分離

Task ツールで生成されるサブエージェントは以下の特徴があります:

  • 独自のコンテキスト: メインエージェントのコンテキストを汚さずに作業できる
  • depth=1: サブエージェントはさらにサブエージェントを生成できない（1階層のみ）
  • 結果の要約: サブエージェントの出力は要約されてメインエージェントに返される
  • メモリ非共有: 親エージェントの会話履歴にはアクセスできない
# サブエージェントの使用例（内部的な動作）
# メインエージェントが Task ツールを呼び出すと:
# 1. 新しいコンテキストでサブエージェントが起動
# 2. 指定されたプロンプトに基づいて作業
# 3. 結果を要約してメインに返却
# 4. メインのコンテキストは要約分しか消費しない

✓ サブエージェントの活用場面

  • 大量のファイルを調査する必要がある場合（調査結果のみ受け取る）
  • 独立した小タスク（テスト作成、リファクタリングなど）
  • メインのコンテキストを節約したい場合

2.5 自動コンパクション

▼

◆ コンテキスト自動管理

コンテキストウィンドウの使用率が 75-92% に達すると、Claude Code は自動的にコンパクション（圧縮）を実行します。

  • 古い会話履歴を要約して圧縮
  • 重要な情報（ファイルパス、決定事項など）は保持
  • ツール結果の詳細は要約に置き換え

✓ 手動コンパクション

/compact コマンドで手動でもコンパクションを実行できます。コンテキストの使用率が高くなってきたら、重要な作業の前に手動で実行するとよいでしょう。

3.1 CLAUDE.md ヒエラルキー

▼

◆ 3レベルの CLAUDE.md

CLAUDE.md はプロジェクトの指示書として機能し、3つのレベルで階層的に読み込まれます。

レベルパス用途Git管理
企業/ユーザー~/.claude/CLAUDE.md個人のグローバル設定・スタイルいいえ
プロジェクト（共有）./CLAUDE.mdチーム共有のプロジェクトルールはい
プロジェクト（個人）./.claude/CLAUDE.local.md個人のプロジェクト固有設定いいえ

✓ CLAUDE.md のベストプラクティス

  • コーディング規約、テスト方針、アーキテクチャの決定事項を記載
  • 簡潔に書く（冗長な説明はコンテキストを浪費）
  • チーム共有の規約は ./CLAUDE.md に、個人の好みは .claude/CLAUDE.local.md に
# CLAUDE.md の例
# プロジェクトルール

## コーディング規約
- TypeScript を使用、any 型は禁止
- テストは vitest で書く
- コミットメッセージは Conventional Commits 形式

## アーキテクチャ
- src/api/ に API ルートを配置
- src/lib/ に共有ユーティリティ
- src/components/ に React コンポーネント

3.3 @import 構文とパスルール

▼

◆ @import で外部ファイルを参照

CLAUDE.md 内で @import を使うと、他のマークダウンファイルを読み込めます。

# CLAUDE.md 内での @import 使用例
@import docs/coding-standards.md
@import docs/api-conventions.md

◆ .claude/rules/ による glob パターンルール

.claude/rules/ ディレクトリにマークダウンファイルを配置し、フロントマターで glob パターンを指定すると、特定のファイルパスに対してのみルールを適用できます。

# .claude/rules/test-rules.md
---
globs: **/*.test.ts, **/*.spec.ts
---

テストファイルでは以下のルールに従うこと:
- describe/it 形式で記述
- モックは vi.mock() を使用
- アサーションは expect() を使用
# .claude/rules/api-rules.md
---
globs: src/api/**/*.ts
---

API ルートでは:
- Zod でリクエストバリデーション
- エラーは AppError クラスでラップ
- レスポンスは統一フォーマット

4.1 カスタムエージェント

▼

◆ .claude/agents/ ディレクトリ

カスタムエージェントは .claude/agents/ にマークダウンファイルとして定義します。フロントマターで名前、説明、モデル、使用可能ツールを指定します。

---
name: コードレビュアー
description: コードの品質、セキュリティ、パフォーマンスをレビュー

  - Read
  - Grep
  - Glob
---

あなたはコードレビューの専門家です。
以下の観点でレビューしてください:
1. コード品質とベストプラクティス
2. セキュリティの脆弱性
3. パフォーマンスの問題
4. テストカバレッジの不足

★ 主要エージェント例

エージェント用途推奨ツール
code-reviewerコードレビューRead, Grep, Glob
test-writerテスト自動生成Read, Write, Bash
security-auditorセキュリティ監査Read, Grep, Glob
refactoring-specialistリファクタリングRead, Edit, Grep, Bash

エージェントは @agent-name で呼び出せます:

# エージェントの呼び出し
@code-reviewer src/api/users.ts をレビューして

4.2 スキル

▼

◆ .claude/skills/ ディレクトリ

スキルは特定の手順やワークフローをカプセル化したものです。SKILL.md にフロントマター付きで定義します。

# .claude/skills/deploy/SKILL.md
---
context: fork
allowed-tools:
  - Bash
  - Read
argument-hint: "デプロイ先の環境名 (staging|production)"
---

# デプロイ手順

1. テストを実行: `npm test`
2. ビルド: `npm run build`
3. 環境変数を確認
4. デプロイコマンドを実行

✓ context: fork の意味

context: fork を指定すると、スキルの実行がサブエージェント内で行われ、冗長な出力がメインの会話コンテキストに流れ込むのを防ぎます。メインの会話がクリーンに保たれるため、出力が多いスキルには積極的に使用しましょう。

4.3 コマンド

▼

◆ カスタムコマンド（スラッシュコマンド）

コマンドは /command-name で呼び出せる再利用可能なプロンプトです。

スコープパス共有
プロジェクト.claude/commands/チームで共有（Git管理）
パーソナル~/.claude/commands/個人のみ
# .claude/commands/fix-lint.md
ESLint エラーを全て修正してください。
1. `npm run lint` でエラーを確認
2. 各エラーを適切に修正
3. `npm run lint` で修正を確認
4. 残りのエラーがあれば繰り返す

使用方法:

# コマンドの呼び出し
/fix-lint

4.4 フック

▼

◆ settings.json でのフック定義

フックはツール実行の前後に自動実行されるスクリプトです。セキュリティチェックや自動フォーマットに使用します。

// .claude/settings.json
{
  "hooks": {
    "PreToolUse": [
      {
        "tool": "Bash",
        "command": "bash .claude/hooks/validate-command.sh"
      }
    ],
    "PostToolUse": [
      {
        "tool": "Write",
        "command": "bash .claude/hooks/auto-format.sh"
      }
    ]
  }
}

★ フックのタイミング

  • PreToolUse: ツール実行前に実行。危険なコマンドのブロックに使用。
  • PostToolUse: ツール実行後に実行。フォーマット、バリデーションに使用。

4.5 判断ガイド: どれを使うべきか

▼
機能用途コンテキスト呼び出し方
エージェント特定の役割・ペルソナ独自のモデル・ツール設定@agent-name
スキル手順・ワークフローfork 可能（分離）/skill-name
コマンド再利用プロンプトメインコンテキスト内/command-name
フック自動チェック・変換ツール実行の前後自動（設定ベース）

✓ 選択の指針

  • 特定の専門家の視点が必要 → エージェント
  • 複数ステップの手順を標準化したい → スキル
  • よく使うプロンプトを保存したい → コマンド
  • 毎回自動で実行したいチェック → フック

MCP & ツール

Model Context Protocol による外部ツール統合、設定方法、コミュニティサーバー

5.1 MCP とは

▼

◆ Model Context Protocol

MCP（Model Context Protocol）は、LLM と外部ツール・データソースを接続するためのオープンプロトコルです。Claude Code はMCPクライアントとして機能し、外部の MCP サーバーが提供するツールを使用できます。

  • 統一インターフェース: 異なるサービスでも同じプロトコルで統合
  • 双方向通信: ツール呼び出しだけでなく、リソース（コンテンツカタログ）も提供
  • セキュリティ: ツールごとの許可制御が可能

5.2 MCP 設定

▼

◆ 設定ファイルの配置

ファイルスコープ用途
.mcp.jsonプロジェクトプロジェクト固有の MCP サーバー
~/.claude.jsonユーザー全プロジェクト共通の MCP サーバー
// .mcp.json の例
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": {
        "GITHUB_TOKEN": "${GITHUB_TOKEN}"
      }
    },
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/path/to/dir"]
    }
  }
}

✓ 環境変数の展開

${GITHUB_TOKEN} のような構文で環境変数を参照できます。シークレットをファイルに直接書かずに済むため、セキュリティが向上します。

5.3 コミュニティ MCP サーバー

▼
サーバー機能パッケージ
GitHubPR、Issue、リポジトリ操作@modelcontextprotocol/server-github
Slackメッセージ送受信、チャンネル管理@modelcontextprotocol/server-slack
Filesystemファイルシステムアクセス@modelcontextprotocol/server-filesystem
DatabaseSQL クエリ実行各DB用の MCP サーバー
Jiraチケット管理コミュニティ製サーバー

! Build vs Use の判断

  • 既存サーバーを使用: 一般的なサービス（GitHub, Slack等）にはコミュニティサーバーを使用
  • カスタムサーバーを構築: 社内システムや独自 API への接続が必要な場合

5.4 tool_choice とリソース

▼

◆ tool_choice オプション

値動作用途
autoモデルが自由にツール選択（デフォルト）通常のエージェントループ
anyモデルは必ず何かのツールを使用ツール使用を強制したい場合
forced（特定ツール名）指定したツールを必ず使用特定の操作を強制したい場合

★ MCP リソース

MCP サーバーはツールだけでなく「リソース」も提供できます。リソースはコンテンツカタログとして機能し、モデルが参照できるドキュメントやデータを提供します。ツールが「アクション」なら、リソースは「情報源」です。

ワークフロー

TDD、仕様駆動開発、Plan Mode、CI/CD 統合、デュアルインスタンスパターン

6.1 TDD with Claude Code

▼

◆ Red-Green-Refactor

Claude Code を使ったテスト駆動開発の流れ:

  1. Red: 「この関数のテストを書いて。まだ実装していないので失敗するはず」
  2. Green: 「テストが通る最小限の実装を書いて」
  3. Refactor: 「テストを維持しながらリファクタリングして」
# TDD ワークフロー例
# Step 1: テスト作成
> src/utils/validate.ts の email バリデーション関数の
  テストを書いて。関数はまだ未実装。

# Step 2: 実装
> テストが全て通る実装を書いて

# Step 3: リファクタリング
> テストを壊さずにリファクタリングして

6.2 仕様駆動開発 (Spec-First)

▼

✓ 設計 → 仕様 → 実装

  • Step 1: Plan Mode で設計を議論（ファイルは変更しない）
  • Step 2: 仕様をマークダウンまたはテストとして記述
  • Step 3: 仕様に基づいて実装

このアプローチにより、Claude が意図と異なる方向に進むリスクを大幅に軽減できます。

6.3 Plan Mode 駆動開発

▼

◆ Plan Mode の活用法

Plan Mode（Shift+Tab で切替）は読み取り専用モードです。以下のフローで使用します:

  1. 調査フェーズ: Plan Mode でコードベースを調査・理解
  2. 計画フェーズ: 変更計画を立案・レビュー
  3. 実行フェーズ: 通常モードに切り替えて実装

✓ インタビューパターン

Claude に質問を促すパターンも効果的です: 「この機能を実装する前に、確認したいことがあれば質問して」。Claude が要件の曖昧さを特定し、より良い実装に繋がります。

6.4 反復的改善

▼

✓ 効果的なプロンプトの原則

  • 具体例 > 散文: 「良いエラーメッセージを書いて」より「"User not found (id: 123)" のような形式で」
  • テスト駆動: 期待する動作をテストで定義してから実装を依頼
  • 小さな単位: 大きなタスクは分割して段階的に依頼
  • フィードバックループ: 結果を確認し、修正を繰り返す

6.5 CI/CD 統合

▼

◆ パイプモード (-p フラグ)

-p フラグを使うと、Claude Code を非対話モードで実行できます。CI/CD パイプラインでの自動化に最適です。

# CI/CD での使用例

# コードレビュー自動化
claude -p "このPRの変更をレビューして" --output-format json

# テスト生成
claude -p "変更されたファイルのテストを生成して"

# セキュリティチェック
claude -p "セキュリティ上の問題がないか確認して"

✓ CI/CD のベストプラクティス

  • --output-format json で構造化出力を取得し、パイプラインで処理
  • レビュー用に独立したインスタンスを使用（開発インスタンスとは分離）
  • コスト管理のために max_tokens を適切に設定

6.6 デュアルインスタンスパターン

▼

★ 計画と実行の分離

2つの Claude Code インスタンスを同時に使用するパターン:

  • インスタンス 1（Plan Mode）: 設計・計画・レビューに使用
  • インスタンス 2（通常モード）: 実際のコード変更に使用

これにより、計画のコンテキストと実行のコンテキストを分離でき、それぞれのコンテキストウィンドウを効率的に使用できます。

// .claude/hooks/dangerous-actions-blocker.sh

INPUT=$(cat)

  exit 0

// .claude/hooks/prompt-injection-detector.sh
#!/bin/bash
INPUT=$(cat)

# インジェクションパターンをチェック
if echo "$CONTENT" | grep -qiE 'ignore previous|disregard|new instructions'; then
  echo '{"decision": "block", "reason": "プロンプトインジェクションの可能性"}'
  exit 0
fi

クイズ

15問の理解度確認クイズ。全トピックをカバーしています。

Q1. Claude Code のマスターループで、ツール実行後に次のイテレーションに進むために必要な処理は？

正解: B — ツール結果は会話履歴に追加し、モデルに再送信する必要があります。これにより、モデルが新しい情報に基づいて次のアクションを判断できます。

Q2. Claude Code のコアツールとして正しくないものはどれか？

正解: C — Deploy はコアツールではありません。8つのコアツールは Bash, Read, Edit, Write, Grep, Glob, Task, TodoWrite です。デプロイは Bash ツール経由で実行します。

Q3. エージェントループの終了条件として最も信頼できるのはどれか？

正解: A — stop_reason == "end_turn" のみが信頼できる終了条件です。テキストブロックの存在はツール呼び出しと共存しうるため判定に使えません。自然言語やイテレーション回数も不適切です。

Q4. チームメンバーがプロジェクトの CLAUDE.md に書かれた規約に従わない。最も可能性の高い原因は？

正解: D — CLAUDE.md は3レベルの階層で読み込まれます。ユーザーレベル（~/.claude/CLAUDE.md）の設定がプロジェクトレベルの設定と矛盾している場合、予期しない動作の原因になります。/memory コマンドでデバッグしましょう。

Q5. テストファイル（*.test.ts）にのみ特定のルールを適用したい場合、最適な方法は？

正解: B — .claude/rules/ ディレクトリにマークダウンファイルを作成し、フロントマターで globs: **/*.test.ts を指定するのが最適です。パス固有のルールを明確かつ管理しやすい形で定義できます。

Q6. セキュリティ監査を自動化したい。Read と Grep のみ使い、書き込みは禁止したい場合、最適な機能は？

正解: C — エージェントのフロントマターで tools: [Read, Grep] を指定すれば、そのエージェントは読み取りツールのみ使用可能になります。特定の役割と制限付きツールセットの組み合わせはエージェントの典型的な使用例です。

Q7. スキルの SKILL.md で context: fork を指定する主な目的は？

正解: A — context: fork はスキル実行をサブエージェント内で行い、冗長な出力がメインの会話コンテキストに流れ込むのを防ぎます。メインのコンテキストウィンドウを保護する重要な機能です。

Q8. プロジェクト固有の MCP サーバーを設定するファイルはどれか？

正解: B — プロジェクト固有の MCP サーバーは .mcp.json で設定します。~/.claude.json は全プロジェクト共通のユーザーレベル設定です。

Q9. tool_choice を "any" に設定した場合の動作はどれか？

正解: D — tool_choice: "any" はモデルに何らかのツールの使用を強制します。"auto"（デフォルト）はモデルが自由に判断、特定ツール名の指定はそのツールを強制します。

Q10. Plan Mode で実行できない操作はどれか？

正解: C — Plan Mode は読み取り専用モードです。ファイルの読み取りや検索は可能ですが、書き込み（Edit, Write）や Bash コマンドの実行はできません。計画・調査フェーズに適しています。

Q11. CI/CD パイプラインで Claude Code を非対話モードで実行するフラグは？

正解: A — -p フラグ（パイプモード）で非対話実行できます。--output-format json と組み合わせると構造化出力も取得可能です。

Q12. Bash ツールで rm -rf / のような危険なコマンドをブロックしたい。最適な方法は？

正解: B — PreToolUse フックでコマンドを実行前に検査し、危険なパターンをブロックするのが最適です。CLAUDE.md の指示はモデルが無視する可能性があり、PostToolUse では実行後で手遅れです。

Q13. 新しい MCP サーバーを導入する際、最も重要なセキュリティ確認事項は？

正解: D — ソースコードの確認とツール定義の検証が最も重要です。ダウンロード数は人気の指標であってセキュリティの保証ではありません。MCP ラグプル攻撃に備え、バージョンを固定し自動更新を避けることも重要です。

Q14. コンテキストウィンドウの使用率が 80% に達した。推奨されるアクションは？

正解: C — 70-90% の範囲では /compact で会話履歴を要約・圧縮するのが推奨です。90% を超えたら /clear を検討しますが、80% の段階では圧縮で十分です。

Q15. サブエージェント（Task ツール）がメインのコンテキストを節約できる理由は？

正解: B — サブエージェントは独自のコンテキストウィンドウで作業し、完了後に結果を要約してメインエージェントに返します。そのため、メインのコンテキストは要約分しか消費されません。
