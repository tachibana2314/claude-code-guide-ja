# Plan Start — 5フェーズの計画

リクエストを分析し、構造化されたフェーズを通じて完全な実装計画を生成します。コードは書きません。重要な意思決定はすべて記録されます。このコマンドの後に `/plan-validate` を実行する前に `/clear` を実行してください。

---

## フェーズ 1: PRD & 設計分析

### ステップ 1.1 — PRD 分析

*PRD が存在しない場合はスキップ（リファクタリング、インフラ変更、バグ修正）。*

すべての PRD ファイルと、存在する場合は `docs/INFORMATION_ARCHITECTURE.md` を読み込みます。コードベースをスキャンして現在の実装状況を把握します。

所見を3つのバケツで表示します:

**不足している要件** — 欠落または不完全な受け入れ基準
**曖昧な要件** — 複数の有効な解釈を持つ項目
**コンプライアンス上の懸念** — セキュリティ、データプライバシー、API コントラクトへの影響

各所見について: 具体的な長所/短所を含むオプションを提示します。ユーザーと議論します。次に進む前にプランファイルの `## Decisions` セクションにすべての意思決定を記録します。未解決の曖昧さがある場合は先に進まない。

### ステップ 1.2 — 設計分析

*UI 変更がスコープに含まれない場合はスキップ。*

読み込む: `DESIGN_SYSTEM.md`、既存の UX ADR、CLAUDE.md の UX ルール。

以下の仕様を生成します:
- **画面インベントリ**: 新規/変更画面、ルート配置、コンポーネント再利用の監査
- **状態カタログ**: すべてのインタラクティブ要素の空、ロード中、入力済み、エラー、部分的状態
- **インタラクション仕様**: ユーザーフロー（ハッピーパス + 代替）、フォーカス/キーボード動作
- **アニメーション仕様**: 各インタラクションを既存キーフレームにマッピングまたは新規指定、`prefers-reduced-motion` フォールバック含む
- **レスポンシブ動作**: ブレークポイント、web/モバイルの分岐決定
- **アクセシビリティ**: WAI-ARIA パターン選択、ライブリージョン、エラーの可視性

重要な UX 決定（インタラクションパターンの選択、新しいアニメーション規約、プラットフォームの分岐）には Design ADR を作成します。小さなレイアウトの選択はプランファイルに直接記録します。

---

## フェーズ 2: 技術的分析

コードベースの調査のために1-2つの Explore エージェントをスポーンします。Task ツールを使ってバックグラウンドで実行します。

エージェントの実行中に確認します:
- `docs/adr/` 内の既存 ADR — 3つ以上の ADR が決定を確認している場合 → 確認なしで自動解決
- PATTERNS.md — 確認済みパターンを直接適用

エージェントが戻ったら: 各アーキテクチャ決定を2-3つのオプション、具体的な長所/短所、推奨事項と共に提示します。未解決の各決定についてユーザーの意見を求めます。

重要な各決定について:
1. 標準の Nygard フォーマット（Context / Decision / Status / Consequences）を使って `docs/adr/ADR-XXXX.md` を作成
2. 新しい観察で `docs/adr/PATTERNS.md` を更新

---

## フェーズ 3: スコープ評価

トリガールールを適用して必要なリサーチエージェントを決定します。各インクルードの正当化を含む提案チームを提示します。

**リサーチエージェントプール:**

| エージェント | トリガー | モデル |
|-------|---------|-------|
| `code-explorer` | 常時 | Sonnet |
| `arch-researcher` | 変更が2つ以上のアーキテクチャレイヤーに触れる | Sonnet |
| `database-analyst` | DB スキーマ変更がある | Sonnet |
| `security-analyst` | 認証、決済、PII、RBAC、レート制限 | Opus |
| `test-analyzer` | 非自明な機能（バグ修正のみは除く） | Sonnet |
| `cross-platform-specialist` | Web + モバイルの同等性が必要 | Sonnet |
| `native-app-specialist` | タスクがモバイル/ネイティブ UI パッケージに触れる | Sonnet |
| `design-system-researcher` | UI 変更がスコープに含まれる | Sonnet |
| `dependency-researcher` | 新しいパッケージが追加される | Sonnet |
| `devops-specialist` | Docker、環境変数、CI/CD 変更 | Sonnet |
| `integration-researcher` | 新しいサービス、ライブラリ、OTEL 設定 | Opus |
| `planning-coordinator` | 常時（2つ以上のエージェントが選択された場合） | Opus |

**ティアラベル**（説明的、規範的でない）:
- Tier 0（0エージェント）: Solo — インライン調査、スポーンなし
- Tier 1（1-3エージェント）: Focused
- Tier 2（4-6エージェント）: Standard
- Tier 3（7-9エージェント）: Comprehensive
- Tier 4（10+エージェント）: Full Spectrum

ユーザーに伝えます: 「**[Tier N - Label]** チームを推奨します: [各エージェントに1行の正当化付きエージェントリスト]。エージェントを追加または削除しますか？」

フェーズ 4 の前に承認を待ちます。

---

## フェーズ 4: リサーチ & プラン作成

**Tier 0**: インライン調査を実施。エージェントをスポーンせずに直接プランを書く。

**Tier 1+**: Task ツールを使って承認されたエージェントを並列にスポーン（run_in_background: true）。各エージェントに提供するもの:
- 具体的なリサーチスコープ
- 調査する関連ファイル/エリア
- 回答が必要な質問

TaskOutput ポーリングループでエージェントを監視します。進捗を報告: 「3/6エージェント完了...」

すべてのエージェントが戻ったら: `planning-coordinator` がスポーンされている場合、すべてのエージェントレポートを送って最終プランを合成させます。そうでない場合は直接合成します。

**プランファイル構造** (`docs/plans/plan-{name}.md`):

```markdown
# Plan: {feature-name}
Created: {date} | Branch: {branch-name} | Tier: {N}

## Summary
1段落: これが何を実装するか、なぜか。

## Decisions
フェーズ 1（PRD 分析）で記録された意思決定。

## Architecture
作成された ADR、適用されたパターン、行われたアーキテクチャの選択。

## Tasks
レイヤー付きの順序付きタスクリスト（1 = 基盤、2 = 1に依存、など）

### Layer 1
- [ ] タスク A — 説明、影響を受けるファイル、受け入れ基準
- [ ] タスク B — 説明、影響を受けるファイル、受け入れ基準

### Layer 2
- [ ] タスク C — A に依存 — 説明、影響を受けるファイル、受け入れ基準

## Test Plan
各タスクをどのように検証するか。TDD タスクは明示的にマーク。

## Integration Verification
実行後に実行するスモークテストコマンド（バックエンド/サービスがスコープに含まれる場合）。

## Out of Scope
このプランが明示的に対応しないもの。
```

コミット: プランファイル + ADR ファイル + エージェントレポートマニフェスト。

## フェーズ 5: メトリクスの最終化

`docs/plans/metrics/{name}.json` にタイムスタンプ、フェーズ期間、エージェント数、コスト見積もりを記録します。コミット。

---

## 自動遷移

フェーズ 1 で未解決の曖昧さが生成されず、フェーズ 2 で未解決の決定が生成されない場合: 確認なしで `/plan-validate` を自動開始。

人間との議論が発生した場合: 先に進む前に「このプランを検証しますか？」と確認。

---

## 使用法

```
/plan-start
```

プロンプトが表示されたら機能の説明を提供するか PRD ファイルを指定します。コマンドが残りをインタラクティブに処理します。

## 使用するタイミング

非自明な機能に使用します: 2つ以上のファイルに触れるもの、アーキテクチャの意思決定を含むもの、計画ミスが取り返しのつかないコストを引き起こす可能性があるもの。

単純な変更（誤字、些細なリファクタリング）には代わりに `/plan` モードを使用します。
