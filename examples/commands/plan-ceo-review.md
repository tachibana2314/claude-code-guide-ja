# /plan-ceo-review — 戦略的プロダクトゲート

実装前のコマンド。「リクエストがある」と「コーディングを始める」の間に明示的なゲートを挿入します。字義通りのリクエストに疑問を呈し、本当のプロダクトがどうあるべきかを問います。

**実装前のプランモードで使用します。**


## このコマンドが解決する問題

Claude Code はリクエストしたものを作るように最適化されています。「X を追加して」と言えば X を作ります。X が実際に適切なプロダクトかどうかを問うことはありません。このコマンドは、実装の本能が働く前に、明示的にプロダクト思考モードに切り替えることでこれを修正します。


## 使用するタイミング

- 重要な機能リクエストを実装する前
- 特にリクエストが具体的な場合（「写真アップロードを追加して」）— 具体性は多くの場合、リクエスト者がすでに解決空間を狭めているサインです
- 方向性にコミットする前にエンジニアリング時間を使ってテストしたい場合


## 3つのモード

コマンドは続行前にユーザーに選択を求めます:

| モード | スタンス | 使用するタイミング |
|------|---------|----------|
| **スコープ拡大** | 10スタープロダクトを見つけ、スコープを広げる | 方向性が曖昧、夢を見たい時 |
| **スコープ維持** | 方向性を受け入れ、計画を完全にする | 方向性が固定、厳密さが必要な時 |
| **スコープ縮小** | 最小限の実行可能版まで削ぎ落とす | バックログが過負荷、すぐに出荷が必要な時 |

アシスタントは選択されたモードにコミットし、レビュー中にブレません。


## プロンプトテンプレート

```markdown
# /plan-ceo-review

あなたは CEO/創業者のレビューモードにいます。何も実装しないことがあなたの仕事です。
プロダクトレベルの思考でプランや機能リクエストをレビューし、
より良いブリーフを返すことがあなたの仕事です。

## ステップ 0: モードの選択

（指定されていない場合）どのモードを使用するかユーザーに尋ねます:
- スコープ拡大: 10スタープロダクトを見つける。スコープを広げる。必然的で
  素晴らしいと感じるバージョンは何か？
- スコープ維持: 方向性を受け入れる。この計画を完璧にする。すべての
  失敗モードと暗黙の前提を特定する。
- スコープ縮小: コアアウトカムを達成する最小限の実行可能バージョンを見つける。
  それ以外はすべて削除する。

ユーザーが選択したら、レビュー全体を通じてそのモードにコミットします。

## ステップ 1: リクエストの再述

字義通りのリクエストを1-2文で要約する。正確に — 編集せずに。

## ステップ 2: 前提への疑問

より重要な質問をする: このプロダクトは実際に何のためにあるのか？

- ユーザーの本当の「やるべき仕事」は何か？
- 字義通りのリクエストがそれを解決する最良の方法か？
- リクエストが前提としていて間違っている可能性のある仮定は何か？

## ステップ 3: 本当のプロダクト（拡大）/ 完全な計画（維持）/ MVP（縮小）

**スコープ拡大**: このプロダクトの10スター版を説明する。
- 2倍の努力で10倍良くするには何が必要か？
- ユーザーが実際に求めているものは何か、求めているものではなく？
- 5-8個の具体的な機能または設計の意思決定をリストアップして、
  これを必然的に感じさせるものを明らかにする。

**スコープ維持**: 方向性を受け入れる。次に何が間違う可能性があるかすべて見つける。
- リクエストの暗黙の前提
- カバーされていないエッジケース
- 欠けているエラー状態
- UX のギャップ
- セキュリティまたは信頼境界の問題
- 運用上の懸念（モニタリング、ロールバック、データマイグレーション）

**スコープ縮小**: コアバリューを証明する最小限のバージョンは何か？
- これが必ずやるべき一つのことは何か？
- ポイントを失わずに何を削れるか？
- v2 に延期できるものは何か？

## ステップ 4: 推奨事項

次のいずれかを返す:
- **現状通り進める** — 元のリクエストが正しいプロダクト
- **再フレーム** — ここにより良いブリーフがある（具体的に）
- **却下** — これが間違った方向性である理由、代わりに何を作るべきか

コードを変更しない。これはレビューであり、実装ではない。
```


## 例

**入力**: 「出品者がリスティングに写真をアップロードできるようにして」

**出力（スコープ拡大）**:
> 「写真アップロード」が機能ではありません。本当の仕事は、実際に売れるリスティングを出品者が作れるようにすることです。
>
> 10スター版はこちら: 写真から自動的に商品を識別し、Web からSKU とスペックを取得し、タイトルと説明を自動的に下書きし、ヒーロー画像として最も高コンバージョンのアップロード写真を提案し、公開前に品質の低い写真（暗い、雑然とした、低信頼）を検出する。
>
> **推奨事項**: 再フレーム。ブリーフは「写真アップロード」ではなく「写真からのスマートリスティング作成」であるべきです。


## 他のコマンドとの統合

```
/plan-ceo-review    → プロダクトの方向性を固定
/plan-eng-review    → 技術アーキテクチャを固定
[実装]
/review             → 慎重なマージ前チェック
/ship               → リリース
```
