# コミット前の変更検証

output-evaluator エージェントを使用してステージされた git の変更を評価し、コミット前に問題を発見します。

## プロセス

### ステップ 1: ステージされた変更を確認

`git diff --cached --stat` を実行してステージされているものを確認します。何もステージされていない場合はユーザーに通知して終了します。

### ステップ 2: 完全な diff を取得

`git diff --cached` を実行してステージされたすべての変更の完全な diff を取得します。

### ステップ 3: 評価者を呼び出す

Task ツールを使用して diff と共に `output-evaluator` エージェントを起動します:

```
これらのステージされた変更の正確性、完全性、安全性を評価してください。
スコアと問題を含む JSON の判定を返してください。

Changes:
[ここに git diff を貼り付ける]
```

### ステップ 4: 判定を解析してアクションを実行

評価結果に基づいて:

**APPROVE の場合:**
- 変更が評価に合格したことをユーザーに伝える
- サマリーとスコアを表示
- コミットを続けるか確認する

**NEEDS_REVIEW の場合:**
- 見つかったすべての問題を表示（重大度別にグループ化）
- 評価者からの提案を表示
- 続行方法をユーザーに確認:
  - 問題を修正して再評価
  - とにかくコミット（リスクを承認）
  - 中止

**REJECT の場合:**
- 変更が却下されたことを明確に伝える
- 却下を引き起こしたクリティカルな問題を表示
- とにかくコミットを提案しない
- 具体的な修正を提案する

### ステップ 5: コミット（承認された場合）

ユーザーが確認した場合、標準のコミットフローを使用してコミットを作成します。

## 使用例

```
/validate-changes
```

出力:
```
Evaluating 3 staged files...

VERDICT: NEEDS_REVIEW

Scores:
  Correctness:  8/10
  Completeness: 6/10
  Safety:       9/10

Issues Found:
  [MEDIUM] src/api/handler.ts:45
    ネットワーク障害のエラーハンドリングが欠けている

  [LOW] src/utils/format.ts:12
    入力バリデーションの追加を検討

Suggestion: handler.ts の fetch 呼び出しの周りに try-catch を追加してください

How would you like to proceed?
  1. Fix issues and re-evaluate
  2. Commit anyway (1 medium issue)
  3. Abort
```

## コスト認識

このコマンドは LLM 評価を呼び出し、API トークンを使用します:
- **典型的なコスト**: 評価ごとに $0.01-0.05（Haiku を使用）
- **大きな diff**: トークン使用量が増えるためコストが高くなる場合がある

## 使用するタイミング

- コミット前の大きなコード変更後
- コードベースの不慣れな部分で作業している時
- セキュリティ上重要なコードに影響する変更の場合
- 共有ブランチにプッシュする前

## スキップするタイミング

- 些細な変更（誤字、フォーマット）
- ドキュメントのみの変更
- すでに十分に手動レビューを行った場合
- フィーチャーブランチで素早くイテレーションしている時

## Git フックとの統合

すべてのコミットで自動評価を行うには、`pre-commit-evaluator.sh` フックを参照してください。
このコマンドは評価をいつ実行するかを制御したい場合の手動の代替手段です。
