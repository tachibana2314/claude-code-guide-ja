# 実装前のプランレビュー

コードを変更する前に現在のプランを徹底的にレビューします。問題や推奨事項それぞれについて、具体的なトレードオフを説明し、意見のある推奨事項を提示し、方向性を仮定する前にユーザーの意見を求めます。

## エンジニアリング設定

推奨事項を導くためにこれらを使用します（プロジェクト固有の CLAUDE.md 設定があれば上書きされます）:

- DRY は重要: 重複を積極的にフラグする
- テストが十分なコードは絶対条件: テストが少なすぎるよりも多すぎることを好む
- コードは「十分にエンジニアリングされている」べき: 低すぎず（脆弱、ハック的）過剰でもない（時期尚早な抽象化、不要な複雑さ）
- より少ないエッジケースではなく、より多いエッジケースを処理する方向に偏る
- 賢いよりも明確を、速度よりも思慮深さを優先する

## レビューパイプライン

各セクションを順番に処理します。次のセクションに進む前に一時停止してフィードバックを求めます。

### 1. アーキテクチャレビュー

評価します:
- システム全体の設計とコンポーネント境界
- 依存関係グラフとカップリングの懸念
- データフローパターンと潜在的なボトルネック
- スケーリング特性と単一障害点
- セキュリティアーキテクチャ（認証、データアクセス、API 境界）

### 2. コード品質レビュー

評価します:
- コードの整理とモジュール構造
- DRY 違反（積極的に）
- エラーハンドリングパターンと欠けているエッジケース（明示的に指摘する）
- 技術的負債のホットスポット
- エンジニアリング設定に対して過剰または不足したエンジニアリングのエリア

### 3. テストレビュー

評価します:
- テストカバレッジのギャップ（ユニット、統合、e2e）
- テスト品質とアサーションの強さ
- 欠けているエッジケースカバレッジ（徹底的に）
- テストされていない失敗モードとエラーパス

### 4. パフォーマンスレビュー

評価します:
- N+1 クエリとデータベースアクセスパターン
- メモリ使用量の懸念
- キャッシュの機会
- 遅いまたは高複雑度のコードパス

## 問題報告フォーマット

発見された特定の問題（バグ、コードの臭い、設計上の懸念、リスク）それぞれについて:

1. ファイルと行参照を含めて問題を具体的に説明する
2. 「何もしない」が合理的な場合はそれを含めた2-3つのオプションを提示する
3. 各オプションについて次を指定する: 実装工数、リスク、他のコードへの影響、メンテナンス負担
4. 上記のエンジニアリング設定にマッピングして推奨オプションとその理由を示す
5. 進める前に、ユーザーが同意するか別の方向を選ぶかを明示的に確認する

## ワークフロー

- タイムラインやスケールに関する優先順位を仮定しない
- 各セクションの後、次に進む前に一時停止してフィードバックを求める
- 構造化された選択肢の選択に AskUserQuestion を使用する

## 開始前に

ユーザーに2つのオプションのどちらかを選ぶよう確認します:

1. **大きな変更**: インタラクティブに1セクションずつ作業する（アーキテクチャ → コード品質 → テスト → パフォーマンス）、各セクションで最大4つのトップ問題
2. **小さな変更**: インタラクティブにレビューセクションごとに1つの質問

## ヒント

- プロジェクト固有のレビュー基準には `.claude/rules/` ファイルと組み合わせる
- 上記のエンジニアリング設定はプロジェクトの CLAUDE.md で上書きできる
- より深い分析には Opus モデルでこのコマンドを使用する
