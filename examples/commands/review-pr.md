# プルリクエストレビュー

プルリクエストの包括的なコードレビューを実施します。

## 手順

1. PR 情報を取得: `gh pr view $ARGUMENTS --json title,body,files,additions,deletions`
2. 変更された各ファイルをレビュー
3. 構造化されたフィードバックを提供

## レビューチェックリスト

### コード品質
- [ ] コードが読みやすく、よく整理されている
- [ ] 関数が適切なサイズ
- [ ] コードの重複なし
- [ ] 意味のある変数/関数名

### 機能性
- [ ] ロジックが正しい
- [ ] エッジケースが処理されている
- [ ] エラーハンドリングが包括的
- [ ] 明らかなバグなし

### セキュリティ
- [ ] ハードコードされたシークレットなし
- [ ] 入力バリデーションが存在する
- [ ] インジェクション脆弱性なし
- [ ] 認可チェックが存在する

### テスト
- [ ] 新しいコードにテストが追加されている
- [ ] 既存のテストが引き続き通る
- [ ] エッジケースがテストされている

### ドキュメント
- [ ] コードが自己文書化されているまたはコメントがある
- [ ] 必要に応じて README が更新されている
- [ ] API の変更がドキュメント化されている

## 出力フォーマット

```markdown
## PR レビュー: #[number] - [title]

### サマリー
[1-2文の概要]

### 承認ステータス
[ ] 承認
[ ] 提案付きで承認
[ ] 変更要求

### 所見

#### クリティカル（必須修正）
- [ ] [問題の説明] - `file:line`

#### 提案（検討すべき）
- [ ] [改善点] - `file:line`

#### 細かい指摘（オプション）
- [ ] [軽微な提案] - `file:line`

### 良い点
- [うまくできていること]

### 質問
- [必要な説明]
```

## 使用法

```
/review-pr 123
/review-pr https://github.com/owner/repo/pull/123
```


## 上級: マルチエージェントレビュー

専門的な視点とハルシネーション防止のための保護機能が必要な本番グレードのレビュー向け。

### フライト前チェック

レビューの前に、提案を繰り返さないようにこれが既存のフォローアップパスかどうかを確認します:

```bash
# Claude がこの PR をすでにレビューしたか検出
git log --oneline -10 | grep "Co-Authored-By: Claude"
```

検出された場合は: 「これはフォローアップパスのようです。新しい問題に集中し、以前の提案を繰り返すことを避けます。」と注記します。

### マルチエージェントの専門化

3つの並列専門エージェントを起動します（[分割役割サブエージェント](../../guide/ultimate-guide.md#split-role-sub-agents) 参照）:

**エージェント 1: 整合性監査者**
```
フォーカス: DRY 違反、重複ロジック、パターンの不整合
確認事項:
- 重複したコードブロック（5行以上類似）
- 命名規則の不整合
- パターン違反（プロジェクトが X パターンを使用している場合、それを適用する）
```

**エージェント 2: SOLID 原則アナリスト**
```
フォーカス: 単一責任原則の違反、複雑さ
確認事項:
- 50行以上の関数（おそらくやりすぎ）
- 3レベルより深いネストされた条件
- サイクロマティック複雑度 > 10
- 単一コンポーネント内の混在した関心事
```

**エージェント 3: 防御的コード監査者**
```
フォーカス: サイレント失敗、マスクされたバグ、隠れたフォールバック
確認事項:
- 空の catch ブロック: try { } catch (e) { } // エラーを飲み込む
- サイレントフォールバック: return data || DEFAULT // データ不足を隠す
- チェックされていない null/undefined: バリデーションなしの user.name
- 無視された Promise の拒否: .catch() なしの async fn
```

### ハルシネーション防止ルール

**アサートする前に確認する**:
- 推奨する前に `Grep` または `Glob` でパターンを確認する
- 「既存の UserService パターンを使用する」と提案する場合は、まず UserService が存在することを確認する
- コードベースを実際に確認せずに「プロジェクトが X を使用している」と主張しない

**出現ルール**:
- 10回以上出現するパターン = 確立されている（提案レベル）
- 3回未満のパターン = 確立されていない（スキップまたはメンテナーに確認）
- diff 行だけでなくファイルのコンテキスト全体を読む

**不確実性マーカー**:
- プロジェクトの規約が不確かな場合は「❓ 要確認:」を使用
- オプションの改善には「💡 検討:」を使用
- クリティカルなバグ/セキュリティにのみ「🔴 必須修正:」を使用

### 調和

エージェントが所見を報告した後:

1. **重複を排除**: エージェント間で重複する提案を削除
2. **既存パターンを優先**: コードベースが X パターンを使用している場合、X を推奨（理想的な Y パターンではなく）
3. **スキップした提案にマークを付ける**: 「プロジェクトが [代替パターン] を使用するため [提案] をスキップ」
4. **推論を追跡**: 提案を維持またはスキップした理由を文書化

### 重大度の分類

```
🔴 必須修正（ブロッカー）
- セキュリティの脆弱性
- データ損失のリスク
- マイグレーションなしの破壊的変更
- バグをマスクするサイレント失敗

🟡 修正すべき（改善）
- メンテナンス問題を引き起こす SOLID 違反
- DRY 違反（重複が3つ以上）
- パフォーマンスのボトルネック（N+1 クエリ）
- クリティカルパスでのエラーハンドリングの欠如

🟢 スキップ可能（あれば良い）
- スタイルの不整合（リンターなしの場合）
- 軽微な命名の改善
- 適度にネストされたコード（3レベル未満の場合）
- ドキュメントのギャップ（コードが自己文書化されている場合）
```

### 自動修正ループ（オプション）

自動収束のために:

```
レビュー → 問題の特定 → 修正 → 再レビュー → 最小の変更になるまで繰り返す

保護機能:
- 無限ループを防ぐために最大3回の反復
- 各反復の前に tsc/lint チェックを実行
- 保護されたファイル（package.json、マイグレーションなど）の自動修正をスキップ
```

**プロンプト例**:
```
この PR を自動修正を有効にしてレビューする:
1. 上記の3つのエージェントを使ってレビュー
2. すべての 🔴 必須修正問題を修正
3. 修正を確認するために再レビュー
4. 🟡 修正すべき問題に対して繰り返す（最大2回の追加反復）
5. 🟢 スキップ可能なもののみが残ったら停止
```

### 条件付きコンテキストの読み込み

diff の内容に基づいて追加コンテキストを読み込みます（スタック非依存）:

| diff が含む場合... | 確認する内容... |
|---------------------|---------------|
| データベースクエリ | インデックス、N+1 パターン、クエリの最適化 |
| API エンドポイント | 認証ミドルウェア、入力バリデーション、レート制限 |
| 認証ロジック | パスワードハッシュ、セッション管理、CSRF トークン |
| ファイルアップロード | サイズ制限、MIME バリデーション、ストレージのセキュリティ |
| 日付/時刻操作 | タイムゾーン処理、DST エッジケース |
| 外部 API 呼び出し | タイムアウト設定、リトライロジック、エラーハンドリング |
| 環境変数 | .env.example での存在、起動時のバリデーション |

### 既存ツールとの統合

**SE-CoVe プラグイン**: レビュークレームの一般的なファクトチェックに使用（上記のハルシネーション防止ルールを補完）

**Worktrunk**: 変更を提案する前のコードベース全体のパターン分析

**AST-grep**: 構造的なパターンマッチング（例: すべての類似 try/catch ブロックを検索）
