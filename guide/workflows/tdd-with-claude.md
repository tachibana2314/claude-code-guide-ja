# ClaudeによるTDD

> **信頼度**: Tier 1 — Anthropicの公式ベストプラクティスと広範なコミュニティ検証に基づく。

Claude Codeを使ったテスト駆動開発には明示的なプロンプトが必要です。Claudeは自然に先に実装を書いてからテストを書こうとします。TDDにはその逆が必要です。

## 要約

```
レッド → グリーン → リファクタリング

ただし、Claudeに明示的にプロンプトする必要があります:
「[機能]のFAILINGなテストを書いてください。まだ実装は書かないでください。」
```


## 問題

明示的な指示がなければ、Claudeは:
1. 実装コードを書く
2. その実装に対してパスするテストを書く

これではTDDの目的が失われます: テストはデザインを駆動するものであり、既存のコードを検証するものではありません。


## セットアップ

### CLAUDE.mdの設定

プロジェクトのCLAUDE.mdに追加してください:

```markdown
## テスト規約

### TDDワークフロー
- 常に実装より先にFAILINGなテストを書く
- AAAパターンを使用: Arrange-Act-Assert
- できる限り1つのテストに1つのアサーション
- テスト名は振る舞いを説明: 「should_return_empty_when_no_items」

### テストファースト原則
- 機能を依頼されたら、まずテストを書く
- テストは最初にFAILするべき（実装が存在しない）
- テストを書いた後だけ、パスするための最小限のコードを実装する
```

### 自動テスト実行フック（任意）

`.claude/hooks/test-on-save.sh`を作成:

```bash
#!/bin/bash
# テストファイルが変更されたら自動でテストを実行
if [[ "$1" == *test* ]] || [[ "$1" == *spec* ]]; then
  npm test --watchAll=false 2>&1 | head -20
fi
```


## レッド・グリーン・リファクタリングサイクル

### フェーズ1: レッド（FAILするテストを書く）

**プロンプト**:
```
[機能の説明]のFAILINGなテストを書いてください。
まだ実装は書かないでください。
関数/メソッドが存在しないためテストがFAILするはずです。
```

**例**:
```
合計が$100を超えた場合に10%割引を適用して、
カート内の商品の合計価格を計算する関数のFAILINGなテストを書いてください。
まだ関数を実装しないでください。
```

**期待されるClaudeの動作**:
- テストケースを含むテストファイルを作成する
- テストは存在しない関数を参照する
- テストを実行すると「function not defined」などでFAILするはず

**検証**:
```bash
npm test  # 「calculateCartTotal is not defined」でFAILするはず
```

### フェーズ2: グリーン（最小限の実装）

**プロンプト**:
```
これらのテストをパスさせるための最小限のコードを実装してください。
現在のテストをパスさせるだけのコードを書いてください、それ以上は不要です。
```

**期待されるClaudeの動作**:
- 実装ファイルを作成する
- テストを満たす最小限のコードを書く
- 過度な設計を避ける

**検証**:
```bash
npm test  # パスするはず
```

### フェーズ3: リファクタリング（クリーンアップ）

**プロンプト**:
```
コード品質を改善するために実装をリファクタリングしてください。
リファクタリング後もテストはグリーンのままでなければなりません。
以下に焦点を当ててください: [可読性 / パフォーマンス / 重複の除去]
```

**期待されるClaudeの動作**:
- 振る舞いを変えずにコードを改善する
- テストを実行して引き続きパスすることを確認する
- 重要な変更を文書化する


## Claude Codeの機能との統合

### TodoWriteとの連携

TDDフェーズをタスクリストで追跡します:

```
ユーザー: 「TDDでユーザー認証を実装してください」

Claudeがtodosを作成:
- [ ] レッド: ログインのFAILINGなテストを書く
- [ ] グリーン: テストをパスさせるログインを実装する
- [ ] リファクタリング: ログイン実装をクリーンアップ
- [ ] レッド: ログアウトのFAILINGなテストを書く
- [ ] グリーン: ログアウトを実装する
- [ ] リファクタリング: クリーンアップ
```

### プランモードとの連携

テスト戦略の計画に使います:

```
[Shift+Tabでプランモードに入る]

TDDでショッピングカートを実装する必要があります。
コードを書き始める前にテストケースを計画してください。
```

Claudeは読み取り専用モードでコードベースを探索し、実装前にテスト計画を提案します。

### フックとの連携

PostToolUseフックを使って編集後に自動でテストを実行します:

```json
// .claude/settings.jsonに記述
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "command": "npm test --watchAll=false 2>&1 | head -20"
      }
    ]
  }
}
```

### サブエージェントとの連携

スコープに集中したエージェントにテスト作成を委任します:

```
test-writerエージェントを使って、UserServiceクラスの
すべてのエッジケースをカバーする包括的なテストを作成してください。
その後、それらのテストをパスさせるために実装します。
```


## アンチパターン

### やってはいけないこと

| アンチパターン | なぜ間違いか | 正しいアプローチ |
|--------------|----------------|-----------------|
| 「この機能のテストを書いてください」 | Claudeが先に実装する | 「まだ存在しないFAILINGなテストを書いてください」 |
| 「テストと実装を追加してください」 | テストファーストの恩恵を失う | 2つのプロンプトに分ける |
| 「テストがパスするようにしてください」 | 実装ファーストを促す | 「テストを書き、それから最小限に実装してください」 |
| リファクタリングフェーズをスキップ | 技術的負債が積み重なる | グリーン後は常にリファクタリングする |
| 一度に複数の機能 | フォーカスを失う | TDDサイクルごとに1つの機能 |

### よくある間違い

**間違い**: Claudeに既存のコードを「テスト」するよう頼む。
```
# 間違い
「既存のcalculateTotal関数のテストを書いてください」

# 正しい
「calculateTotalの振る舞いのテストを書いてください、関数は存在しないとして。
その後、既存の実装がパスするか確認します。」
```

**間違い**: レッドとグリーンのフェーズを組み合わせる。
```
# 間違い
「calculateTotalをテスト付きで実装してください」

# 正しい
「calculateTotalのFAILINGなテストを書いてください。そこで止めてください。」
[テストが書かれた後]
「それらのテストをパスさせるように実装してください。」
```


## 高度なパターン

### プロパティベースのテスト

```
sort関数のプロパティベースのテストを書いてください。
テストするプロパティ:
- 出力の長さは入力の長さと等しい
- すべての入力要素が出力に存在する
- 出力は順序付けられている
fast-checkまたは同様のライブラリを使用してください。
```

### ミューテーションテスト

```
テストがパスした後、弱い部分を見つけるためにミューテーションテストを実行してください。
ミューテーションを検出しないテストを特定してください。
```

### レガシーコードでのTDD

```
legacyFunctionをリファクタリングする必要があります。
まず、現在の振る舞いをキャプチャするキャラクタリゼーションテストを書いてください。
その後、自信を持ってリファクタリングします。
```


## セッション例

### ユーザーのリクエスト
```
TDDでURL短縮サービスを実装してください。
```

### フェーズ1: レッド
```
TDDを使いましょう。まず以下のFAILINGなテストを書いてください:
1. URLを短縮すると短いコードが返る
2. 短いコードを取得すると元のURLが返る
3. 無効なURLは拒否される
4. 期限切れのリンクはエラーを返す

まだ何も実装しないでください。
```

### フェーズ2: グリーン
```
テストが書かれてFAILしています。今、それらをパスさせる最小限の
コードを実装してください。今はインメモリストアを使ってください。
```

### フェーズ3: リファクタリング
```
テストがパスしています。今リファクタリングしてください:
- URL検証を別の関数に抽出する
- 適切なエラー型を追加する
- 変数名を改善する

変更のたびにテストを実行してグリーンのままか確認してください。
```
