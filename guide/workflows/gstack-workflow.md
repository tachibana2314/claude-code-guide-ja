# コグニティブモード切り替え

> **信頼度**: Tier 2 — 参照実装: Garry Tan（Y Combinator CEO）による[gstack](https://github.com/garrytan/gstack)、ローンチ24時間以内に1,100以上のスター（2026年3月）。

**読了時間**: 約10分
**前提条件**: Claude Codeスキルの基礎、プランモード
**関連**: [プランパイプライン](./plan-pipeline.md)、[プラン駆動開発](./plan-driven.md)


## 要約

汎用アシスタントはすべてのフェーズを混在させてしまいます。このパターンは各フェーズに明確なコグニティブモードを与えます: 仕事に適した脳を呼び出し、作業が変わったら切り替えます。

```
/plan-ceo-review  → 「正しいものを構築しているか？」
/plan-eng-review  → 「どうすれば構築可能になるか？」
/review           → 「本番で何が爆発するか？」
/ship             → リリースを実行、議論なし
/browse           → ブラウザで実際に動作するか？
/retro            → 今週のシッピングはどうだったか？
```

重要な洞察は、プランニング、レビュー、シッピングは根本的に異なるコグニティブ姿勢を必要とするということです — 汎用モードのままの単一のアシスタントはそれらを下手に混在させます。


## 6つのギア

| コマンド | 役割 | コアな問い | 切り替えるタイミング |
|---------|------|---------------|----------------|
| `/plan-ceo-review` | ファウンダー / CEO | 「正しいものを構築しているか？」 | コードを書く前 |
| `/plan-eng-review` | エンジニアマネージャー / テックリード | 「どうすれば構築可能になるか？」 | 方向性が決まった後 |
| `/review` | 慎重なスタッフエンジニア | 「本番でまだ何が壊れる可能性があるか？」 | マージ前 |
| `/ship` | リリースエンジニア | 「飛行機を着陸させる」 | ブランチが準備完了、議論はもう必要ない |
| `/browse` | QAエンジニア | 「実際に動作するか？」 | デプロイ後、ステージングまたは本番に対して |
| `/retro` | エンジニアリングマネージャー | 「シッピングはどうだったか？」 | 週次またはローンチ後 |


## このパターンが埋めるギャップ: 実装前の戦略的ゲート

AIコーディングアシスタントで正しく得ることが最も難しいのは実装ではありません。その前に来る問いです: **正しいものを構築しているか？**

Claude Codeは依頼されたものを構築するように最適化されています。「写真アップロードを追加して」と言うと、写真アップロードを追加します。写真アップロードが実際にプロダクトかどうかは問いません。それが`/plan-ceo-review`が解決する問題です。

**例**: Craigslistスタイルのリスティングアプリを構築しています。

- リクエスト: 「出品者が商品の写真をアップロードできるようにする」
- 字義通りの実装: ファイルピッカー + 画像の保存
- 本当のプロダクトは: 出品者が実際に売れるリスティングを作成するのを助けること

最初に`/plan-ceo-review`を実行すると、アシスタントは字義通りのリクエストに挑戦し、その中に隠れているプロダクトを見つけるように明示的に求められます。出力は全く異なるブリーフになります: 写真から商品を自動識別し、ウェブからスペックと価格比較を取得し、タイトルと説明を下書きし、ヒーロー画像を提案し、低品質の写真が公開される前に検出する。

それは異なる機能です。より良い機能です。そして、実装が始まる前に明示的なゲートを挿入することによってのみ得られます。

**`/plan-ceo-review`内の3つのモード**:
- **SCOPE EXPANSION** — 10スターのプロダクトを見つけ、「2倍の努力で10倍良くするには何が必要か？」と問う
- **HOLD SCOPE** — 方向性を受け入れ、プランを完璧にする
- **SCOPE REDUCTION** — 最小限の実行可能なバージョンに容赦なく削減する

ユーザーがモードを選択します。アシスタントはそれにコミットし、ドリフトしません。


## /plan-eng-review: アイデアを構築可能にする

方向性が決まったら、コグニティブモードはプロダクトの直感からエンジニアリングの厳密さに切り替わります。`/plan-eng-review`はアイデア出しが止まりアーキテクチャが始まる場所です。

生成すべきもの:
- アーキテクチャ図（コンポーネント、境界、データフロー）
- コアフローのステートマシン
- 同期と非同期の境界の決定
- 失敗モードとリトライロジック
- 信頼境界（どこで外部入力を受け入れるか？）
- テストマトリクス

重要なのは**図の生成を強制すること**です。図は散文が隠す隠れた仮定を明らかにします。シーケンス図は誰が何を呼び出すかを指定させます。ステートマシンはすべての失敗モードを列挙させます。それらなしでは、「システムが処理する」は漠然としたままです。


## /review: 慎重なスタッフエンジニアモード

テストがパスしてもブランチが安全であることを意味しません。`/review`はCIをくぐり抜けて本番に到達するクラスのバグのために存在します。

チェック内容:
- N+1クエリ
- レース条件（2つのタブが同じ状態を上書きする）
- 信頼境界違反（検証なしでクライアント提供のメタデータを受け入れる）
- 失敗パスでの孤立データ
- 欠落インデックス
- 悪いリトライロジック
- 実際の失敗モードを見逃しながらパスするテスト
- LLM出力がさらなる処理に流れる場合のプロンプトインジェクション

姿勢は意図的: 本番インシデントが起きる前にそれを想像する。


## /browse: 非MCPネイティブブラウザ自動化

`/browse`はgstackの中で最も技術的に特徴的な部分です。MCPサーバーではありません。永続的なヘッドレスChromiumデーモンを実行するコンパイルされたネイティブバイナリ（TypeScript + Bun）です。

**アーキテクチャが重要な理由**:

| アプローチ | コールドスタート | 後続の呼び出し | 状態の永続性 |
|----------|-----------|-----------------|-------------------|
| MCPブラウザサーバー | セッションごとに新しい接続 | 500ms以上 | セッション間で失われる |
| `/browse`ネイティブデーモン | 約3秒（1回のみ） | 約100〜200ms | Cookie、タブ、認証が永続する |

これはQAワークフローにとって重要です: ステージング環境に一度ログインしてから完全なナビゲーションシーケンスを実行すると、デーモンが再起動しないため速い状態が保たれます。MCPソケットのオーバーヘッドなし、セッションのリセットなし。

**利用可能な操作**: ナビゲート、ページテキストの読み取り、スクリーンショット、refを含むアクセシビリティツリーのスナップショット、refでクリック/入力、JavaScriptの実行、コンソールログの検査、ネットワークリクエストのキャプチャ。

**MCPブラウザツールよりこちらを好む場合**:
- レイテンシが敏感なQAループ（シーケンスで10以上のページチェック）
- MCPサーバー接続が制限されている環境
- 1つのセッション内の複数のコマンドでブラウザの状態（認証、Cookie）を永続させる必要がある場合

**MCPを使い続ける場合**: 単一ページのチェック、よりシンプルな環境、またはMCPブラウザツールがすでにある場合。


## フルサイクルのデモ

```
# 1. 戦略的ゲート — ブリーフに挑戦
[プランモード]
あなた: リスティングアプリに出品者の写真アップロードを追加したい。
     出品者は写真をアップロードでき、そこからリスティングを作成する。

あなた: /plan-ceo-review   (SCOPE EXPANSIONモードを選択)

Claude: 「写真アップロード」は機能ではありません。本当の仕事は
        出品者が実際に売れるリスティングを作成するのを助けることです。
        10スターバージョンはこうです:
        商品を自動識別し、ウェブからスペックと価格比較を取得し、
        タイトルと説明を下書きし、最良のヒーロー画像を提案し...

# 2. エンジニアリングゲート — アーキテクチャを確定
あなた: /plan-eng-review

Claude: [アーキテクチャ図、asyncジョブ境界、
        アップロード → 分類 → 充実 → 下書きパイプラインのステートマシン、
        失敗モード、信頼境界、テストマトリクス]

# 3. プランを実装
[プランモードを終了、コードを書く]

# 4. 慎重なレビュー — テストが見逃したものを見つける
あなた: /review

Claude: レース条件: 2つのタブがカバー写真の選択を上書きできる。
        信頼境界: ウェブデータを下書き生成に取り込むと
        プロンプトインジェクションベクターが作成される。
        欠落: 失敗したアップロードのオーファンクリーンアップ。

あなた: [問題を修正]

# 5. シップ
あなた: /ship

Claude: [mainを同期、テストを実行、ブランチをプッシュ、PRを開く — 完了]

# 6. ステージングに対するブラウザQA
あなた: /browse staging.myapp.com — リスティングフローをテスト

Claude: [ルートをナビゲート、アップロードフォームを入力、充実がレンダリングされることを確認、
        エラーのコンソールを確認、各ステップをスクリーンショット]
        すべてのページが正しくロードされます。リスティングフローはエンドツーエンドで動作します。
```


## インストール

```bash
# グローバルにインストール (~/.claude/skills/)
git clone https://github.com/garrytan/gstack.git ~/.claude/skills/gstack
cd ~/.claude/skills/gstack && ./setup
```

またはこれをClaude Codeに直接貼り付けると残りを処理します:

> Install gstack: run `git clone https://github.com/garrytan/gstack.git ~/.claude/skills/gstack && cd ~/.claude/skills/gstack && ./setup`

チームインストール（`git clone`でチームメンバーがそのまま使えるようにリポジトリにコミットされる）については[gstack README](https://github.com/garrytan/gstack)を参照してください。

> **注意（2026年3月）**: gstackは2026年3月11日にリリースされました。パターンは堅固ですが、実装は新しいです。本番ワークフローに採用する前に、リポジトリが積極的にメンテナンスされているか確認してください。


## これを使う場合 vs 他のワークフロー

| 状況 | このワークフロー | 代替 |
|-----------|---------------|-------------|
| 複雑な機能、方向性が不確か | まず`/plan-ceo-review` | [仕様ファースト](./spec-first.md) |
| 方向性は明確、アーキテクチャが複雑 | `/plan-eng-review` | [プランパイプライン](./plan-pipeline.md) |
| プランの独立した検証が必要 | [プランパイプライン](./plan-pipeline.md) `/plan-validate` | — |
| ブラウザ自動化、単一ページチェック | MCPブラウザツール | `/browse`（過剰） |
| ブラウザ自動化、マルチステップQAループ | `/browse` | MCPツール（より遅い） |
| 構造化されたADR学習ループが必要 | [プランパイプライン](./plan-pipeline.md) | — |

[プランパイプライン](./plan-pipeline.md)との主な差別化点: gstackは手動でコントロールする線形ギアシーケンスです。プランパイプラインはADRメモリと並行エージェントチームを持つより自動化されたオーケストレーションです。各フェーズを明示的にコントロールしたいソロ開発者には、gstackの方が早く採用できます。
