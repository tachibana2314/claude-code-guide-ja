# デュアルインスタンスプランニングワークフロー

> **信頼度**: Tier 2 — 実践者の経験（Jon Williams、2026年2月）に基づく。CursorからClaude Codeへの個人的な移行を6ヶ月かけて検証したパターン。

2つのClaudeインスタンスを異なる役割で使う: 1つはプランニングとレビュー用（Claude Zero）、もう1つは実装用（Claude One）。関心の分離によってプラン品質が向上し、実装エラーが減少します。

## 要約

```
1. Claude Zero（プランナー）を起動: 探索、プラン作成、レビュー
2. Claude One（実装者）を起動: プランを読む、コーディング、コミット
3. 人間がゲートキーパー: 実装前にプランを承認
4. プランディレクトリ: Review/ → Active/ → Completed/
5. コスト: 月約$100〜200（Borisの水平パターンの$500〜1Kに比べて）
```

**最適な用途**: ソロ開発者、仕様が多い作業、スピードより品質、月$300未満の予算


## このパターンを使う場面

### ✅ 使う場合

- **複雑な仕様**: 要件をインタビュー形式の質問で明確化する必要がある
- **品質が重要な機能**: セキュリティ、決済、データマイグレーション
- **学習フェーズ**: 新しいコードベース、不慣れなパターン
- **コーディングするプロダクトデザイナー**: 非開発者バックグラウンド、プランニングの厳密さが必要
- **予算の制約**: 月$100〜200（並列マルチインスタンスの$500〜1Kに比べて）
- **仕様が多いワークフロー**: 詳細な要件、多くのエッジケース

### ❌ 使わない場合

- **シンプルな変更**: タイポ修正、些細なリファクタリング（シングルインスタンスを使用）
- **探索的コーディング**: 問題空間が不明（プランニングのオーバーヘッドが正当化されない）
- **タイトな期限**: スピード > 品質（修正ループを受け入れる）
- **大量の並列機能**: 代わりにBorisパターン（セクション9.17）を使用
- **非常に限られた予算**: 月$100未満（Sonnetのシングルインスタンスを使用）

### 他のパターンとの比較

| パターン | スケーリング軸 | 月コスト | 最適な用途 |
|---------|--------------|------------|----------|
| **シングルインスタンス** | なし | $50〜100 | ほとんどの開発者、一般的な使用 |
| **デュアルインスタンス（Jon）** | 垂直（プラン ↔ 実装） | $100〜200 | 仕様が多い、品質重視 |
| **マルチインスタンス（Boris）** | 水平（5〜15並列） | $500〜1,000 | チーム、大量のシッピング |


## セットアップ

### ステップ1: ディレクトリ構造の作成

```bash
cd ~/projects/your-project
mkdir -p .claude/plans/{Review,Active,Completed}
```

**ディレクトリの役割**:
- `Review/` — 人間の承認を待つプラン
- `Active/` — 実装中の承認済みプラン
- `Completed/` — アーカイブされたプラン（学習リソース）

**.gitignoreに追加**:
```bash
# .gitignore
.claude/plans/Review/
.claude/plans/Active/
# 任意: チームの学習のためにCompleted/をコミット
```

### ステップ2: Claude Zero（プランナー）を起動

**ターミナル1**:
```bash
cd ~/projects/your-project
claude
```

**最初のメッセージ**（役割の強制）:
```
あなたはClaude Zero（プランナー）です。

あなたの役割:
- プランモード（Shift+Tabを2回）を使ってコードベースを探索する
- ユーザーに要件についてインタビューする
- .claude/plans/Review/に詳細なプランを書く
- Claude Oneが完了した後、実装をレビューする
- コードを直接編集してはいけない
- 変更をコミットしてはいけない

この役割を確認して始めてください。
```

Claude Zeroが確認: 「了解しました。私はClaude Zero（プランナー）です。探索、プラン作成、レビューを行いますが、コードには触れません。」

### ステップ3: Claude One（実装者）を起動

**ターミナル2**（新しいセッション）:
```bash
cd ~/projects/your-project
claude
```

**最初のメッセージ**（役割の強制）:
```
あなたはClaude One（実装者）です。

あなたの役割:
- .claude/plans/Active/から承認済みプランを読む
- 仕様通りに正確に実装する
- 各論理ステップの後に変更をコミットする
- 完了をユーザーに報告する
- プランを作成してはいけない
- 承認ステップをスキップしてはいけない

この役割を確認して始めてください。
```

Claude Oneが確認: 「了解しました。私はClaude One（実装者）です。承認されたプランのみを実行します。」


## 完全なワークフロー

### フェーズ1: プランニング（Claude Zero）

#### ステップ1.1: プランニングの開始

**あなた**（Claude Zeroに）:
```
# プランモードに入る（Shift+Tabを2回押す）、その後:

APIにJWT認証を実装してください:
- アクセストークン（15分の有効期限）
- リフレッシュトークン（7日間の有効期限）
- ルートを保護するミドルウェア
- ログアウト機能（リフレッシュトークンの無効化）
```

#### ステップ1.2: Claude Zeroが探索する

Claude Zero（プランモードで）:
- 既存の認証コードを読む
- コードベースの認証パターンを検索する
- 依存関係を特定する（ライブラリ、環境変数）

#### ステップ1.3: Claude Zeroがインタビューする

Claude Zeroが明確化のための質問をします:
```
プランを作成する前に明確にする必要があります:

1. ユーザーごとに複数の同時セッションをサポートすべきか？
   （例: 電話とラップトップに同時にログインしているユーザー）

2. リフレッシュトークンはどこに保存すべきか？
   - データベーステーブル
   - Redis
   - その他

3. どのルートを保護すべきか？
   - すべての/api/*ルート？
   - 特定のルートのみ？

4. ログイン試行にレート制限が必要か？

5. 「完了」の成功基準は何か？
   - テストパス？
   - Postmanコレクション？
   - ドキュメント更新？
```

**あなたが回答し**、Claude Zeroが理解を洗練させます。

#### ステップ1.4: Claude Zeroがプランを書く

Claude Zeroが`.claude/plans/Review/auth-jwt.md`を作成:

```markdown
# プラン: JWT認証

**作成日**: 2026-02-04
**著者**: Claude Zero
**推定工数**: 3〜4時間
**リスクレベル**: 中（セキュリティクリティカル）

## 要約
アクセス/リフレッシュトークンパターンを使ったJWTベースの認証を実装。
ユーザーごとに複数の同時セッションをサポート。
リフレッシュトークンは無効化機能付きのデータベースに保存。

## 明確化された要件
- ユーザーごとの複数セッション: YES
- リフレッシュトークンのストレージ: データベース（新しいテーブル）
- 保護されたルート: /api/auth/*を除くすべての/api/*
- レート制限: YES（15分に5回まで）
- 成功基準: テストパス + Postmanコレクション

## 作成するファイル
...（実装の詳細）

## 実装ステップ（順番に）
1. 依存関係のインストール
2. JWTユーティリティの作成
3. データベースマイグレーションの実行
...

## 成功基準
- [ ] POST /auth/loginがaccessToken + refreshTokenを返す
- [ ] 有効なアクセストークンなしでは保護されたルートが401を返す
...

**プランを承認？** → `.claude/plans/Active/auth-jwt.md`に移動
```

### フェーズ2: 人間によるレビュー

**あなたが** `.claude/plans/Review/auth-jwt.md`をレビュー:

**チェックリスト**:
- [ ] すべての要件がカバーされているか？
- [ ] このコードベースに対してアプローチは意味があるか？
- [ ] セキュリティの考慮事項が対処されているか？
- [ ] 推定工数は現実的か？
- [ ] 成功基準は明確でテスト可能か？
- [ ] 作成/変更するファイルのパスは正しいか？

**承認の場合**:
```bash
mv .claude/plans/Review/auth-jwt.md .claude/plans/Active/
```

**変更が必要な場合**、Claude Zeroに修正を依頼:
```
（Claude Zeroに）: プランを更新してください:
- リフレッシュトークンの有効期限を7日ではなく30日に変更
- パスワードリセットフローをスコープに追加
```

### フェーズ3: 実装（Claude One）

**あなた**（Claude Oneに）:
```
.claude/plans/Active/auth-jwt.mdを実装してください

プランに正確に従ってください。各論理ステップの後にコミットしてください。
完了したら報告してください。
```

Claude Oneが:
1. プランファイルを読む
2. 依存関係をインストールする
3. jwt.tsを作成する
4. データベースマイグレーションを作成する
5. マイグレーションを実行する
6. 認証ミドルウェアを作成する
7. ルートを更新する
8. 環境変数を追加する
9. テストを書く
10. Postmanコレクションを作成する

**Claude Oneが各ステップの後にコミット**:
```
feat: JWTユーティリティ関数を追加
feat: refresh_tokensテーブルマイグレーションを作成
feat: 認証ミドルウェアを追加
feat: JWT認証でAPIルートを保護
test: JWT認証フローのテストを追加
```

### フェーズ4: 検証（Claude Zero）

**あなた**（Claude Zeroに）:
```
Claude Oneが完了したJWT実装をレビューしてください。
.claude/plans/Active/auth-jwt.mdのプランと照らし合わせて確認してください。
```

Claude Zeroがレビュー:
- コード構造はプランと一致するか？
- すべての成功基準が満たされているか？
- セキュリティチェックリストが完了しているか？
- テストはパスしているか？
- コードスメルや問題はないか？

**Claude Zeroのレポート**:
```
✅ レビュー完了: auth-jwt.md

コード品質: 9/10
- すべてのファイルがプラン通りに作成された
- 成功基準が満たされた（9/9）
- セキュリティチェックリスト完了
- テストパス（15/15）

マイナーな提案:
1. リフレッシュトークンのローテーションを追加することを検討（セキュリティのベストプラクティス）
2. jwt.ts関数にJSDocコメントを追加
3. マジックナンバー（15分、7日）を設定に抽出することを検討

クリティカルな問題: なし

プランをCompleted/にアーカイブする準備ができました。
```

### フェーズ5: アーカイブ

**承認の場合**:
```bash
mv .claude/plans/Active/auth-jwt.md .claude/plans/Completed/
```

**プランは今後の参照とチームの学習のためにアーカイブされます。**

## コスト分析

### デュアルインスタンス vs 修正ありのシングルインスタンス

| シナリオ | シングルインスタンス | デュアルインスタンス | 節約 |
|----------|----------------|---------------|---------|
| **シンプルな機能**（ログインフォーム） | 1セッション × $5 = **$5** | 2セッション × $3 = $6 | +$1（シングルが有利） |
| **中程度の機能**（認証システム） | 1セッション × $15 + 修正2回 × $10 = **$35** | 2セッション × $12 = $24 | **$11節約** |
| **複雑な機能**（曖昧な仕様） | 1セッション × $20 + 修正3回 × $15 = **$65** | 2セッション × $18 = $36 | **$29節約** |

**損益分岐点**: 2回以上の修正ループが必要な機能 → デュアルインスタンスの方が安い。

### 月次予算の見積もり

**前提**:
- 月20営業日
- 1日2機能（シンプルと複雑の混合）
- Opus 4.5の価格（入力約$15/1Mトークン、出力$75/1Mトークン）

| プロファイル | 月次機能数 | シングルインスタンス | デュアルインスタンス | 節約 |
|---------|----------------|----------------|---------------|---------|
| **ライトユーザー** | 20シンプル | $100 | $120 | -$20（シングルが有利） |
| **モデレートユーザー** | 30混合（60%中程度、40%シンプル） | $650 | $480 | **$170節約** |
| **ヘビーユーザー** | 40複雑 | $2,000 | $1,200 | **$800節約** |

**推奨事項**:
- シンプルな機能のみ → シングルインスタンス
- 中程度/複雑な機能 → デュアルインスタンスはコストと時間を節約する


## ヒントとトラブルシューティング

### 役割の強制

**問題**: Claude Zeroがコードを編集し始める。

**解決策**: すべてのリクエストでリマインダーを付ける:
```
（Claude Zeroに）: 覚えておいてください: あなたはClaude Zero（プランナーのみ）です。
コードを編集しないでください。.claude/plans/Review/にプランを書いてください。
```

**防止策**: CLAUDE.mdを使って役割を強制する:

```markdown
# .claude/CLAUDE.md

## あなたがClaude Zero（プランナー）の場合:
- すべての探索にプランモード（Shift+Tabを2回）を使用する
- すべてのプランを.claude/plans/Review/[feature].mdに保存する
- コードを編集してはいけない
- 変更をコミットしてはいけない
- Claude Oneが完了した後、実装をレビューする

## あなたがClaude One（実装者）の場合:
- .claude/plans/Active/からプランを読む
- 仕様通りに正確に実装する
- 各論理ステップの後にコミットする
- プランを作成してはいけない
```

### コンテキストの汚染

**問題**: Claude Oneのコンテキストがプランニングの議論で汚染される。

**解決策**: 別のターミナルセッション（別のコンテキスト）を使用する:
- ターミナル1 = Claude Zero（プランニングコンテキスト）
- ターミナル2 = Claude One（実装コンテキスト）

**Claude ZeroとClaude Oneの間でコンテキストを共有しない。**

### プランのドリフト

**問題**: Claude Oneが実装中にプランから逸脱する。

**解決策**: プランにこれを含める:
```markdown
## Claude Oneへの実装ルール

- プランのステップを順番に従う（スキップや並べ替えをしない）
- ブロッカーに遭遇した場合は、STOPしてレポートする（即興しない）
- 各ステップの後にコミットする（粒度の細かい履歴）
- 不明な場合はユーザーに質問する（推測しない）
```

### オーバーヘッドの管理

**問題**: ディレクトリ間のファイル移動は手動のオーバーヘッドがある。

**解決策**: Bashエイリアスを作成する:

```bash
# ~/.bashrcまたは~/.zshrcに追加

# プランをActiveに移動（承認）
approve-plan() {
    mv ".claude/plans/Review/$1.md" ".claude/plans/Active/"
    echo "✅ 承認済み: $1.md → Active/"
}

# プランをCompletedに移動（アーカイブ）
complete-plan() {
    mv ".claude/plans/Active/$1.md" ".claude/plans/Completed/"
    echo "✅ 完了: $1.md → アーカイブ済み"
}

# ステータス別にプランをリスト
plans() {
    echo "📋 Review:"
    ls -1 .claude/plans/Review/ 2>/dev/null || echo "  (空)"
    echo ""
    echo "🔄 Active:"
    ls -1 .claude/plans/Active/ 2>/dev/null || echo "  (空)"
    echo ""
    echo "✅ Completed:"
    ls -1 .claude/plans/Completed/ 2>/dev/null | tail -5 || echo "  (空)"
}
```

**使用方法**:
```bash
plans                     # すべてのプランをリスト
approve-plan auth-jwt     # プランを承認
complete-plan auth-jwt    # 完了したプランをアーカイブ
```
