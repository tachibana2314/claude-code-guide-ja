# トーク準備パイプライン: アイデアからスライドまでAIと共に

> **信頼度**: Tier 2 — 実際のカンファレンストーク（DevWithAI Lyon、2026年）で本番検証済み。

生の記事、トランスクリプト、またはノートを、Kimiに対応したAI生成スライドのプロンプトを含む完全なカンファレンストークに変換します。6つのステージ、2つのモード、1つのヒューマンインザループチェックポイント。

## 要約

```
ソースマテリアル（記事 / トランスクリプト / ノート）
        │
        ▼
[ステージ1] EXTRACT ─────────────── {slug}-summary.md
        │
        ├──────────────────────────────────────┐
        │                                      │
        ▼ (--rex only)                         ▼
[ステージ2] RESEARCH               [ステージ3] CONCEPTS
  git-archaeology.md              concepts.md
  changelog-analysis.md           concepts-enriched.md
  timeline.md                         │
        │                             │
        └──────────────┬──────────────┘
                       │
                       ▼
              [ステージ4] POSITION
                angles.md
                titre.md
                descriptions.md
                feedback-draft.md
                       │
                  [チェックポイント]
             ユーザーがアングルとタイトルを選択
                       │
                       ▼
              [ステージ5] SCRIPT
                pitch.md
                slides.md
                kimi-prompt.md ──► Kimi.comにコピーペースト
                       │
                       ▼
             [ステージ6] REVISION
              revision-sheets.md
```

2つのモード: **REX**（実世界の証拠付きトーク — gitの履歴、メトリクス）と **Concept**（アイデア/論点ベース — ステージ2をスキップ）。

---

## 使う場面

このパイプラインは、以下のどちらかのトークを準備する場合に適しています:

- **伝えるべきREXがある**: 何かを構築して出荷した、実際のメトリクスがある — それを構造化されたカンファレンストークに変えたい
- **展開すべきコンセプトがある**: 記事、ノート、またはアイデアを構造化されたプレゼンテーションに変えたい

適したフォーマット:
- カンファレンストーク（20-45分）
- ミートアッププレゼンテーション（15-30分）
- 社内テックトーク
- ワークショップのオープニング

適さないもの: 定例会議のスライドデッキ更新、10分未満のライトニングトーク、作業を開始するための既存のマテリアルがない場合。

## 前提条件

**必須**:
- スキルがインストールされたClaude Code（[examples/skills/talk-pipeline/](../../examples/skills/talk-pipeline/)を参照）
- ソースマテリアル: 記事`.mdx`、トランスクリプト`.md`、ノート、またはミックス
- トークのメタデータ: slug、イベント名、日付、時間、聴衆の説明

**REXモードのみ**:
- 分析したいgitリポジトリへのアクセス
- オプション: リポジトリルートと異なる場合の`CHANGELOG.md`パス

**KimiによるスライドGenerationのため（ステージ5の出力）**:
- [kimi.com](https://kimi.com)の無料アカウント（APIは不要 — コピーペーストするだけ）

**任意だが推奨**:
- 出力ファイルのためのプロジェクトルートの`talks/`ディレクトリ
- ステージ4のフィードバック草稿のために利用可能な1-2人の信頼できる同僚

## パイプラインの概要

### モード別の出力ファイル

| ファイル | ステージ | REX | Concept |
|------|-------|-----|---------|
| `{slug}-summary.md` | 1 | ✓ | ✓ |
| `{slug}-git-archaeology.md` | 2 | ✓ | — |
| `{slug}-changelog-analysis.md` | 2 | ✓ | — |
| `{slug}-timeline.md` | 2 | ✓ | — |
| `{slug}-concepts.md` | 3 | ✓ | ✓ |
| `{slug}-concepts-enriched.md` | 3 | ✓ (リポジトリがある場合) | — |
| `{slug}-angles.md` | 4 | ✓ | ✓ |
| `{slug}-titre.md` | 4 | ✓ | ✓ |
| `{slug}-descriptions.md` | 4 | ✓ | ✓ |
| `{slug}-feedback-draft.md` | 4 | ✓ | ✓ |
| `{slug}-pitch.md` | 5 | ✓ | ✓ |
| `{slug}-slides.md` | 5 | ✓ | ✓ |
| `{slug}-kimi-prompt.md` | 5 | ✓ | ✓ |
| `{slug}-revision-sheets.md` | 6 | ✓ | ✓ |

REXモード: 13-14ファイル。Conceptモード: 10ファイル。

### 命名規則

すべての出力は `talks/{YYYY}-{slug}-{stage-label}.md` に従います。2026年のslug `devwithai` の例:

```

talks/2026-devwithai-git-archaeology.md
talks/2026-devwithai-concepts.md
talks/2026-devwithai-angles.md
...
```

## ステージバイステージガイド

### ステージ1: エクストラクト

**何をするか**: ソースマテリアルを読み込み、構造化されたサマリーを生成します — ナラティブアーク、主要なメトリクス、メインテーマ、ギャップ。

| | |
|--|--|
| **入力** | ソースファイル + メタデータ（slug、イベント、日付、期間、聴衆、モード） |
| **出力** | `{slug}-summary.md` |
| **使用ツール** | Read、Write、AskUserQuestion |
| **モード** | REX + Concept |

**主要なルール**:
- ソースタイプ（REX対Concept）をシグナルに基づいて自動検出（日付、メトリクス、「I shipped」対「I think」）
- すべての測定可能なメトリクスをそのソースと共に抽出 — 数字を発明しない
- ギャップを隠さず明示的にフラグを立てる

**呼び出し**:
```
/talk-stage1-extract
```

またはオーケストレーター経由:
```
/talk-pipeline --stage=extract --slug=my-talk --event="Conf 2026" --date=2026-06-15 --duration=30 --audience="senior devs"
```

**次に進む前にレビュー**:
- アークのナラティブが一貫している（汎用的でない: 「このトークはAIについてです...」）
- すべてのメトリクスに明示的なソースがある
- ギャップがリストされている（「主要なギャップなし」でも）
- タイプ検出が正しい（REX / Concept / Hybrid）

---

### ステージ2: リサーチ（REXモードのみ）

**何をするか**: gitの考古学 — 速度メトリクスを抽出し、CHANGELOGとクロスリファレンスし、gitで検証された（推定ではない）事実のタイムラインを構築します。

| | |
|--|--|
| **入力** | `{slug}-summary.md` + リポジトリパス |
| **出力** | `git-archaeology.md`、`changelog-analysis.md`、`timeline.md` |
| **使用ツール** | Bash（読み取り専用gitコマンド）、Read、Write |
| **モード** | REXのみ — **Conceptモードでは自動的にスキップ** |

**主要なルール**:
- 読み取り専用のgitコマンドのみ — リポジトリを変更しない
- gitで見つからない日付は「未検証」とマーク — 推定しない
- ソース間の矛盾はフラグを立てる、サイレントに解決しない

**使用されるgitコマンド**（読み取り専用）:
```bash
git log --pretty=format:"%Y-%m" | sort | uniq -c   # 月別の速度
git shortlog -sn --no-merges                         # コントリビューター
git tag --sort=version:refname                       # リリース
git log --merges --oneline | wc -l                   # マージされたPR
```

**次に進む前にレビュー**:
- タイムラインがサマリーの全期間をカバーしている
- 推定日付なし — すべて検証済み
- 速度のピークにコンテキストメモがある

---

### ステージ3: コンセプト

**何をするか**: マテリアル内のすべてのコンセプトの番号付き、スコア付きカタログを構築します。各コンセプトはトーク潜在スコア（HIGH / MEDIUM / LOW）を得ます。

| | |
|--|--|
| **入力** | `{slug}-summary.md` + `{slug}-timeline.md`（オプション） |
| **出力** | `{slug}-concepts.md`、`{slug}-concepts-enriched.md`（リポジトリが利用可能な場合） |
| **使用ツール** | Read、Write |
| **モード** | REX + Concept |

**スコア基準**:
- **HIGH**: 実証可能、直感に反する、検証された数字がある、30秒で実行可能
- **MEDIUM**: 有用だが予測可能、証拠や数字が不足
- **LOW**: 抽象的すぎる、過度にカバーされている、スライドで説明が難しい

**スコアリングの規律**: 最大30% HIGH — 選択的であることがポイント。

**次に進む前にレビュー**:
- 15以上のコンセプトが特定されている（リポジトリアクセスのあるREXで20以上）
- スコアが調整されている（全部HIGH、全部LOWではない）
- 各コンセプトに1-2文の具体的な説明がある

---

### ステージ4: ポジション + チェックポイント

**何をするか**: 戦略的なアングル、タイトル、説明、ピアフィードバック草稿を生成します。その後**停止して待ちます** — アングルとタイトルの選択を待ちます。

| | |
|--|--|
| **入力** | `{slug}-summary.md` + `{slug}-concepts.md` + イベント制約 |
| **出力** | `angles.md`、`titre.md`、`descriptions.md`、`feedback-draft.md` |
| **使用ツール** | Read、Write、AskUserQuestion |
| **モード** | REX + Concept |

**生成されるもの**:
- **3-4アングル**: それぞれに強み、弱み、聴衆への適合、評定（/5でスコア）
- **推奨**: 構造化された正当性を持つ明確な選択
- **アングルごとに3-5タイトル**
- **短い説明**（約100語の概要）+ **長い説明**（約250語のCFP）
- **フィードバック草稿**: ピアバリデーションのための送信準備済みメッセージ（3フォーマット: Slack DM、メール、LinkedInポスト）

**チェックポイント表示**（ステージ5前に必須）:

```
---
CHECKPOINT : アングルとタイトルの選択

4つのファイルを生成しました:
- talks/{YYYY}-{slug}-angles.md    → {n}個のアングルを分析
- talks/{YYYY}-{slug}-titre.md     → {n}個のタイトルオプション
- talks/{YYYY}-{slug}-descriptions.md
- talks/{YYYY}-{slug}-feedback-draft.md

スクリプト（ステージ5）を開始する前に、あなたの選択が必要です:

1. どのアングルを選ぶか？（推奨: アングル{X} — {名前}）
2. どのタイトルを好むか？（推奨: 「{タイトル}」）

修正、ミックス、または別の提案も可能です。
---
```

**ステージ5は明示的なユーザーの確認なしには開始できません。**

**確認前にレビュー**:
- フィードバック草稿を読んで、オプションで同僚に送った
- 推奨されたアングルが繰り返しなしに全期間を維持できる
- タイトルが具体的（専門用語なし、クリックベイトなし）

---

### ステージ5: スクリプト

**何をするか**: スピーカーノート付きの5幕のトーク全体、スライドの仕様、Kimiプロンプトを構築します。

| | |
|--|--|
| **入力** | サマリー + コンセプト + タイムライン（オプション） + **検証済みアングルとタイトル** |
| **出力** | `{slug}-pitch.md`、`{slug}-slides.md`、`{slug}-kimi-prompt.md` |
| **使用ツール** | Read、Write |
| **モード** | REX + Concept |

**3つの成果物**:

1. **`pitch.md`**: スピーカーノート、タイミング、主要な瞬間を含む5幕のナラティブ。スライドから読むのではなく、何を言うかです。

2. **`slides.md`**: スライドごとの仕様: タイトル、ビジュアルの説明、主要なテキスト（≤30語）、スピーカーノート、時間、幕番号。デザイナーに渡すまたはKimiに渡す準備ができています。

3. **`kimi-prompt.md`**: [kimi.com](https://kimi.com)用の完全なプロンプト — デザインシステム、カラーパレット、タイポグラフィ仕様、完全なスライドコンテンツ、スクリーンショットプレースホルダーを含む。コピーペースト準備済み。

**1スライド1アイデアルール**: スライドを説明するのに「and」が必要な場合は分割します。

**次に進む前にレビュー**:
- タイミングチェック: 合計 ≤ 期間 + 10%バッファ
- スピーカーノートが声に出して自然に読める（これをテストする）
- Kimiプロンプトに `{PLACEHOLDER}` が残っていない

---

### ステージ6: リビジョン

**何をするか**: トーク中とトーク後のリビジョンシートを生成します — 幕ごとのクイックナビゲーション、マスターコンセプトテーブル、Q&Aチートシート、用語集。

| | |
|--|--|
| **入力** | `pitch.md` + `slides.md` + `concepts.md` |
| **出力** | `{slug}-revision-sheets.md` |
| **使用ツール** | Read、Write |
| **モード** | REX + Concept |

**リビジョンシートの内容**:
- 幕ごとのアンカーリンク付き**ナビゲーション**
- **幕ごとの内訳**: 主要コンセプト + メトリクス + 逸話 + 確率的なQ&A
- **マスターテーブル**: コンセプト → 1-2文の定義 → 共有するURL
- **Q&Aチートシート**: 確率的な6-10の質問と短い回答（≤20秒で言える）
- **メトリクスブロック**: 一箇所にすべての数字
- **外部リソース**: トークで言及されるリンク
- **用語集**: 技術用語、各最大10語

**目的**: 誰かが質問する → セクションを見つける → 5秒でURLを共有する。

## Kimiへのハンドオフ

ステージ5は `{slug}-kimi-prompt.md` を生成します — [kimi.com](https://kimi.com)用の完全なプロンプトです。

**それを使って何をするか**:
1. 生成されたファイルを開く
2. `{PLACEHOLDER}` が残っていないことを確認する（ファイルを検索）
3. [kimi.com](https://kimi.com)に行く — 無料アカウント、APIは不要
4. 新しい会話を開始する
5. プロンプト全体をコピーペーストする
6. Kimiがプレゼンテーションを生成する（PowerPointまたはPDF）

**Kimiでの反復**:
- 最初の生成後、`slides.md`仕様に照らしてスライドをレビューする
- 個々の調整のためにフォローアップメッセージを追加: 「スライド7: 数字を大きくして、箇条書きを削除して」
- スクリーンショット: エクスポート後に `SCREENSHOT AREA` プレースホルダーを手動で置き換える

**テンプレートに組み込まれたデザインシステム**:
- ダークテーマ（#0a0a0a背景）
- オレンジのアクセント（#f97316）主要な数字とCTA
- Inter/SF Proタイポグラフィ
- スライドごと最大30語、数字をヒーローとして
- WCAG AAコントラスト比（プロジェクター安全）

**なぜKimiか？** 執筆時点で、Kimiは詳細なプロンプトから最も他の代替案より高品質なカンファレンスプレゼンテーションを生成します。テンプレートはKimiに合わせて調整されていますが、デザインシステムとスライド構造はどのAIプレゼンテーションツールでも機能します。

## ヒューマンインザループチェックポイント

パイプラインには2つの人間のチェックポイントがあります:

### チェックポイント1: ステージ1のメタデータ収集

トークのメタデータ（slug、イベント、日付、期間、聴衆、モード）が事前に提供されていない場合、ステージ1は `AskUserQuestion` を使って続行前に収集します。これにより、破棄するサマリーを生成することを避けます。

### チェックポイント2: ステージ4 — アングルとタイトルの選択（必須）

これはパイプラインのクリティカルゲートです。ステージ5は明示的な人間の選択なしには開始できません。

**なぜこれが重要か**: アングルとタイトルは後続するすべてを決定します — 5幕の構造、どのコンセプトが浮かび上がるか、Kimiプロンプトのトーン。ここでの自動化された選択は汎用的なトークを生成します。これはあなたのものでなければならない一つの決定です。

**チェックポイントで何をするか**:
1. `angles.md` を読む — 推奨はあなたのコンテキストに対して間違っている可能性があるのでスキップしない
2. オプションで `feedback-draft.md` を信頼できる同僚に送る（10分かかり、2時間の手戻りを節約）
3. 選択を返答する（推奨、修正、または全く別のものも可能）

## パイプラインの適用

### ライトニングトーク（10-15分）

- ステージ1、3、4、5を保持 — REXモードでもステージ2をスキップ
- ステージ3: 8-10コンセプトに制限（HIGHのみに容赦なくフィルタリング）
- ステージ4: 最大2アングルを生成
- ステージ5: 約8-10スライドを目標、約2分/スライド
- ステージ6をスキップ（短いフォーマットには不要）

### 45分トーク

- フルパイプライン、全ステージ
- ステージ3: 25-35コンセプトを目標（5つの充実した幕を埋めるのに十分）
- ステージ5: 20-25スライド、平均3分/スライドを許可
- ステージ6が重要になる（Q&Aは10-15分続く）

### ワークショップ（90分以上）

- ステージ4までパイプラインを実行
- ステージ5: slides.mdをアクティビティ仕様に置き換える（演習、タイミング、ブレイクアウトグループ）
- Kimiプロンプトのセクションは任意になる（ワークショップのマテリアルには関係が薄い）

### gitリポジトリがない場合（コードなしのREX）

- 他のソース（アナリティクス、ダッシュボード、インシデントレポート）からメトリクスがある場合は `--rex` モードを使用
- ステージ2: gitコマンドをそれらのソースからの手動データ収集に置き換える
- ソーシングにより厳格になる — 「未検証」のメトリクスはトークを生き残れない

## 実際の例

**トーク**: 「Dev with AI」REX — AIツールで7ヶ月で複雑なプロジェクトをどのように出荷したか

**モード**: REX
**イベント**: DevWithAI Lyon、2026年2月
**期間**: 30分
**ソースマテリアル**: `.mdx`内の12,000語の記事

**生成されたファイル（合計16個）**:

```
talks/2026-devwithai-summary.md              (ステージ1)
talks/2026-devwithai-git-archaeology.md      (ステージ2)
talks/2026-devwithai-changelog-analysis.md   (ステージ2)
talks/2026-devwithai-timeline.md             (ステージ2)
talks/2026-devwithai-concepts.md             (ステージ3)
talks/2026-devwithai-concepts-enriched.md    (ステージ3)
talks/2026-devwithai-angles.md               (ステージ4)
talks/2026-devwithai-titre.md                (ステージ4)
talks/2026-devwithai-descriptions.md         (ステージ4)
talks/2026-devwithai-feedback-draft.md       (ステージ4)
talks/2026-devwithai-pitch.md                (ステージ5)
talks/2026-devwithai-slides.md               (ステージ5)
talks/2026-devwithai-kimi-prompt.md          (ステージ5)
talks/2026-devwithai-revision-sheets.md      (ステージ6)
```

**ステージ2で浮かび上がった主要なメトリクス**:
- 7ヶ月で1,200コミット（`git log` で検証済み）
- 主なコントリビューター3名
- 特定のマイグレーション後に97%のトラフィック削減（CHANGELOG v1.1.0から取得）
- 月4の速度ピーク（通常の2倍のペース）

**選択したアングル**（生成された3つから）: 「ビルダーの旅」 — AIツールで月をまたいで構築するのが実際にどのようなものかを示すREXアングル（機能デモではない）

**Kimiの出力**: ダークテーマのデッキ、20スライド、数字ヒーローデザイン、約90秒で生成

## よくある落とし穴

### ソースのないメトリクス

ステージ1はメトリクスを抽出しますが検証しません。ステージ2が検証します。Conceptモードにいる場合、トークで言及するメトリクスはサマリーに明示的にソースが記載されているか削除されている必要があります — 聴衆は「その数字はどこから来たのか？」と聞き、「調べました」は答えになりません。

### 過負荷なスライド

Kimiプロンプトはスライドごと30語を強制しますが、ステージ5で書く`pitch.md`は箇条書きリストにドリフトする可能性があります。1スライド1アイデアルールをテストします: スライドの内容を説明するのに「and」が必要な場合は分割します。

### チェックポイントをスキップする

検証されたアングルとタイトルなしにステージ5を実行すると、間違ったトークに対して技術的に正しいスクリプトが生成されます。ステージ4の推奨は良い出発点であり、最終的な答えではありません — あなたの聴衆の知識が重要です。

### フィードバック草稿を送るのが遅すぎる

フィードバック草稿はステージ4で生成されます、スクリプトが存在する前に。それは意図的です — アングル/タイトルの段階でのピアフィードバックは実行可能です。完成したスクリプトへのフィードバックはほとんど後悔を生むだけです。

### 汎用的なスピーカーノート

`pitch.md`のスピーカーノートは自然な話し言葉として読める必要があります。「このスライドでは、議論します...」と書いていたら、部屋に実際に言うことに書き直してください。Kimiプロンプトはこれらのノートをコピーします — 会話的である必要があります。

## 紹介するデザインパターン

このパイプラインはClaude Codeの観点から興味深いです — 1つの一貫したシステムでいくつかの高度なパターンを示しているからです。

### ファイルベースの状態によるスキルチェーン

各ステージは次のステージが読み込むファイルを書きます。状態はファイルシステムを通じてスキル呼び出し間で持続します — インメモリカップリングなし。ステージ2の1週間後にステージ3を実行しても、コンテキストを失いません。

```
ステージ1 → {slug}-summary.mdを書く
ステージ2 → {slug}-summary.mdを読む → 3つの新しいファイルを書く
ステージ3 → サマリー + タイムラインを読む → 2つの新しいファイルを書く
...
```

### ツールパーミッションのスコープ

ステージ2だけがBashを必要とします（gitコマンドのため）。他のすべてのステージはRead + Writeのみです。これは意図的です — 各ステージの最小限のフットプリントはミスの表面を減らします。

```yaml
# ステージ2のみ
allowed-tools:
  - Write
  - Read
  - Bash
```

### ヒューマンインザループゲート

ステージ4は利便性としてではなく、構造的な要件として `AskUserQuestion` を使って チェックポイントを表面化させます。スキルは明示的な人間の応答なしにステージ5に進みません。これが「Claudeが提案し、人間が決定する」のパターンです。

### AIからAIへのハンドオフ

ステージ5は2番目のAIシステム（Kimi）のプロンプトを生成します。ClaudeはスライドをGenerationしません — 別のAIが実行する仕様を生成します。このパターンで強みを組み合わせることができます: Claudeは構造化されたナラティブ推論、Kimiはビジュアルプレゼンテーション生成のために。

```
Claude（ステージ5）→ kimi-prompt.md → Kimi.com → slides.pptx
```

### 条件付きステージスキップを持つ2つの実行モード

`--rex` / `--concept` フラグはどのステージが実行されるかを制御します。Conceptモードではステージ2が自動的にスキップされます。オーケストレーター（`/talk-pipeline`）がルーティングを処理します — 個々のステージスキルはモードに依存しません。
