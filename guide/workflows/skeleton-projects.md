# スケルトンプロジェクトワークフロー

ゼロから始める代わりに、実績のある既存リポジトリを新規プロジェクトのスキャフォールドとして使います。


## 使う場面

- **既知の技術スタックで新規プロジェクトを開始する**
- **複数のサービスにまたがるチームパターンを標準化する**
- **アーキテクチャの決定がすでに完了している迅速なプロトタイピング**
- **実際に動くリファレンスを通じた新しいチームメンバーのオンボーディング**

**使わない場面**: 未知の技術を探索する場合（代わりに[バイブコーディング](../ultimate-guide.md#98-vibe-coding--skeleton-projects)を使用）、または要件が既存のテンプレートに合わないほどユニークな場合。


## 前提条件

- Claude Codeのインストールと設定
- リファレンスリポジトリへのGitアクセス
- ターゲットプロジェクトの要件の明確な理解


## ステップバイステップガイド

### フェーズ1: スケルトンの発見と評価

ゼロから構築しないでください。ターゲットアーキテクチャに一致する既存のリポジトリを見つけましょう。

**ステップ1: 候補を探す**

```bash
# Claudeにリファレンスリポジトリの発見を手伝ってもらう
claude -p "次の条件を持つNext.js 15アプリのスケルトンが必要です:
- App Router
- Prisma ORM with PostgreSQL
- 型安全なAPIのためのtRPC
- Tailwind CSS
- Jest + Playwrightテスト

最も管理されているスターターテンプレートをGitHubで探してください。
上位3つを以下で評価してください: 最終コミット日、スター数、依存関係の新鮮さ、テストカバレッジ。"
```

**ステップ2: クローンして監査する**

```bash
git clone <candidate-repo> skeleton-eval
cd skeleton-eval
claude
```

```markdown
ユーザー: このリポジトリをプロジェクトの潜在的なスケルトンとして監査してください:
1. すべての依存関係とそのバージョンをリストアップ（古いものにはフラグを立てる）
2. コード品質を評価: パターン、一貫性、テストカバレッジ
3. 残すものと削除するものを特定する
4. セキュリティ上の懸念を指摘する（脆弱な依存関係、露出した秘密情報）
5. 具体的な根拠を持って全体的な適合性を評価する（1〜5）
```

**ステップ3: サブエージェントで評価する**（徹底的な分析のため）

```markdown
ユーザー: このスケルトンを複数の視点から評価してください:

エージェント1（セキュリティ）: 脆弱性、ハードコードされた秘密情報、安全でないパターンを確認
エージェント2（アーキテクチャ）: モジュール性、関心の分離、スケーラビリティを評価
エージェント3（DX）: 開発者体験を評価 - セットアップ時間、ドキュメント、ツール

調査結果をGO/NO-GOの推奨にまとめてください。
```

### フェーズ2: フォークとカスタマイズ

**ステップ4: スケルトンからプロジェクトを作成する**

```bash
# スケルトンから新しいリポジトリを作成
mkdir my-project
cp -r skeleton-eval/. my-project/
cd my-project
rm -rf .git
git init
```

**ステップ5: Claudeでストリップしてアダプトする**

```markdown
ユーザー: このスケルトンをプロジェクト「Acme Dashboard」用にカスタマイズしてください:

1. 削除: サンプルルート、デモデータ、サンプルテスト
2. 残す: 設定構造、認証セットアップ、データベーススキーマパターン、CIパイプライン
3. 更新: package.json（名前、説明、バージョン0.1.0）
4. 追加: プロジェクト規約を含む私たちのCLAUDE.md
5. 確認: 変更後に`pnpm install && pnpm build && pnpm test`がすべてパスする

重要: 動作するスケルトンを壊さないでください。各削除の後にビルドチェックを行ってください。
```

### フェーズ3: スケルトンからMVPへの拡張

**ステップ6: 最初の本物の機能を構築する**

```markdown
ユーザー: このスケルトンで確立されたパターンを使って、最初の機能を実装してください:
ユーザー認証（ログイン + 登録 + パスワードリセット）

スケルトンの既存パターンに従ってください:
- ルート構造（サンプルルートパターンに一致させる）
- サービスレイヤー（既存のサービスパターンに一致させる）
- テスト構造（サンプルテストパターンに一致させる）
- エラーハンドリング（既存のエラーパターンに一致させる）

実装を開始する前にタスクプランを作成してください。
```

**ステップ7: スケルトンの整合性を検証する**

```markdown
ユーザー: 本物の機能が1つできたので、スケルトンがまだ機能するか確認してください:
1. 完全なテストスイートを実行する
2. CIパイプラインがパスするか確認する
3. スケルトンのパターンが壊れていないか確認する
4. 新しいコードが一貫してスケルトンの規約に従っているか確認する
```

### フェーズ4: ドキュメントと反復

**ステップ8: CLAUDE.mdに決定事項を文書化する**

```markdown
ユーザー: CLAUDE.mdを以下で更新してください:
1. どのスケルトンから始めたか（リポジトリURL、コミットハッシュ）
2. 何を残してなぜか
3. 何を削除してなぜか
4. 元のスケルトンからのパターンの逸脱
5. その上に追加した規約
```


## スケルトン拡張タイムライン

```
スケルトン（1日目）     →    MVP（第1週）      →    本番（第1ヶ月）
────────────────────────────────────────────────────────────────────
1つのサンプルルート      →    5つの実ルート      →    20以上のルート
1つのサンプルテスト       →    30のテスト          →    200以上のテスト
基本的な設定           →    環境ベースの設定    →    マルチ環境 + シークレット
SQLite/ローカルDB       →    Docker PostgreSQL  →    マネージドDB + マイグレーション
CIなし                →    基本的なCI          →    完全なCI/CDパイプライン
READMEのみ            →    CLAUDE.md + ADR    →    完全なドキュメント
```


## 実際の例: スケルトンからのマイクロサービス

```bash
# 1. 実績のあるスケルトンをクローン
git clone https://github.com/example/express-prisma-starter skeleton
cd skeleton && claude

# 2. 監査（2分）
ユーザー: 「このスケルトンを監査してください。課金マイクロサービスに適していますか？」
# Claudeが報告: 依存関係、パターン、適合性スコア

# 3. カスタマイズ（5分）
ユーザー: 「例を削除して、billing-serviceに名前変更して、私たちのCLAUDE.mdを追加してください」
# Claudeが実行: デモコードを削除、設定を更新、プロジェクトコンテキストを追加

# 4. 最初の機能（30分）
ユーザー: 「スケルトンパターンに従って請求書作成エンドポイントを実装してください」
# Claudeが作成: ルート、サービス、リポジトリ、スケルトンの規約に一致するテスト

# 5. 確認（2分）
ユーザー: 「すべてのテストを実行して、ビルドを確認して、スケルトンパターンが保たれているか確認してください」
# Claudeが確認: すべてグリーン、パターンが一貫している
```


## よくある落とし穴

| 落とし穴 | 症状 | 解決策 |
|---------|---------|--------|
| スケルトンが複雑すぎる | 構築よりストリッピングに時間がかかる | よりシンプルなスケルトンを選ぶ、または自分でミニマルなものを構築する |
| 依存関係が古い | インストール時にセキュリティ警告 | クローン前に最終コミット日を確認（理想は6ヶ月以内） |
| スケルトンパターンの破壊 | 新しいコードがスケルトンの規約から乖離する | スケルトンパターンをCLAUDE.mdに制約として追加する |
| デッドコードを残す | 使われていないサンプルコードがプロジェクトを散らかす | フェーズ2で徹底的にストリップし、各削除後にビルドを確認する |
| ドキュメントなし | なぜスケルトンが選ばれたか忘れる | 即座にCLAUDE.mdに文書化する（フェーズ4） |
