## これは何ですか？

エージェントチームが存在することは知っています。理論は読みました。でも**実際のプロジェクトではいつ使うべきか？**

このガイドが提供するもの:
- ✅ **5分のセットアップ**（環境 → 最初のテスト）
- ✅ **コピー＆ペースト可能な4つのパターン**（GuideとRTKの実プロジェクト用）
- ✅ **判断マトリクス**（YESの場合、NOの場合）
- ✅ **ROIを測定するメトリクス**
- ✅ **無駄を避けるためのレッドフラグ**

**スキップする場合**: 理論が知りたい → 代わりに[エージェントチームの完全ドキュメント](./agent-teams.md)を読む。

## 1. 5分セットアップ

### ステップ1: 前提条件の確認

```bash
# Claude Codeバージョンを確認（v2.1.32以上が必要）
claude --version

# モデルの利用可能性を確認
claude
> /model opus
# 表示されるべき: "Model changed to opus (claude-opus-4-6-20250624)"
```

**最小要件**:
- Claude Code v2.1.32以上
- Opus 4.6モデル
- Gitリポジトリ（エージェントチームはgitを調整に使用）

### ステップ2: 機能の有効化

```bash
# 環境変数を設定（~/.bashrcまたは~/.zshrcに追加して永続化）
export CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1

# Claude Codeを起動
claude
```

### ステップ3: 確認

```
> エージェントチームは有効ですか？
```

**期待されるレスポンス**:
```
はい、このセッションでエージェントチームは有効です。以下を使って
複雑なタスクを並行して処理するエージェントチームを作成できます:
- マルチエージェント調整
- Gitベースのタスク取得
- 自律的なチーム調整
```

**無効の場合**: 環境変数が設定されているか確認してください（`echo $CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS`）。

### ステップ4: 最初のテスト（2エージェント）

```
> このREADMEを分析する簡単なテストチームを作成してください:
> - エージェント1: 構造を確認（セクション、目次、バッジ）
> - エージェント2: コンテンツ品質を確認（明確さ、例、完全性）
```

**起きること**:
1. Claudeが2つのエージェントを生成（「Creating team...」メッセージが表示される）
2. エージェントが並行して動作（「Idle」メッセージが表示されることがある - 正常）
3. Claudeが統合された調査結果を提示（収束点 + ユニークな洞察）

**ナビゲーション**:
- `Shift+Down`: チームメンバーの出力をサイクル（インプロセスモード）
- メインビュー: 統合された要約

**所要時間**: シンプルな2エージェントタスクで1〜2分。

## 2. プロジェクト用パターン

### 2.1 Claude Codeガイド - リリース前レビュー

**ユースケース**: 一貫性の問題（壊れたリンク、同期が取れていない数、バージョンの誤り）を検出するためのバージョンアップ前の系統的な監査

**トリガー**: すべての`/release`コマンド実行前

**所要時間**: 3〜5分

**チーム構成**:
```
チーム: pre-release-audit（3エージェント）
├─ accuracy-auditor → クレーム、統計、バージョン、外部リンクを確認
├─ consistency-checker → テンプレート数、eval数、ガイド行数がファイル間で一致するか確認
└─ breaking-checker → 前回のリリースからの破壊的な変更を特定
```

**コピー＆ペースト用プロンプト**:
```
> リリース前監査チームを作成してください:
> - Accuracy: CHANGELOG.md、README.md、guide/ultimate-guide.mdのすべてのクレーム、統計、バージョン番号、外部リンクを確認
> - Consistency: テンプレート数（examples/のファイルを数える）、eval数（docs/resource-evaluations/のファイルを数える）、ガイド行数（wc -l guide/ultimate-guide.md）がREADME.md、guide/cheatsheet.md、machine-readable/reference.yamlで一致するか確認
> - Breaking: CHANGELOG.md [Unreleased]セクションを分析してv3.23.0からの破壊的な変更を特定
```

**ROI**: 以下のようなバグを検出:
- LinkedInのURL破損（実際の監査で検出）
- ガイド/ランディング間の同期ずれ（テンプレート数）
- 複数ファイルにわたる誤ったバージョン番号
- 壊れた外部リンク

**スキップする場合**: シンプルなタイポ修正（バージョン/数/リンクの変更なし）。

**実際の例**（2026-02-08のテスト）:
```
調査結果:
- Accuracy: 1つのクリティカル（LinkedInのURL不正形式）、3つの警告（確認が必要な外部リンク）
- Consistency: 2つのクリティカル（READMEとランディング間のテンプレート数不一致、reference.yamlの行番号が古い）
- Breaking: v3.23.0からの破壊的な変更なし（クリーンなリリース）

収束: 2つのエージェントがテンプレート数の問題にフラグ（高信頼度）
時間: 4分12秒
評価: ✅ 高価値、3つのクリティカルを出荷前に検出
```

### 2.2 Claude Codeガイド - ランディング同期

**ユースケース**: 手動スクリプトを実行せずにガイド/ランディングの同期（バージョン、数、コンテンツ）を確認

**トリガー**: 重要なガイド変更後（バージョンアップ、テンプレート追加、FAQ変更）

**所要時間**: 2〜3分

**チーム構成**:
```
チーム: landing-sync（2エージェント）
├─ guide-scanner → バージョン、テンプレート数、eval数、ガイド行数、FAQコンテンツを抽出
└─ landing-scanner → index.html、examples.htmlと比較して同期状態を確認
```

**コピー＆ペースト用プロンプト**:
```
> ガイド/ランディングの同期を検証してください:
> - ガイドスキャナー: VERSIONファイルからバージョンを抽出、テンプレート数（find examples/ -type f | wc -l）、eval数（find docs/resource-evaluations/ -name "*.md" | wc -l）、ガイド行数（wc -l guide/ultimate-guide.md）、README.mdのFAQエントリを抽出
> - ランディングスキャナー: /Users/florianbruniaux/Sites/perso/claude-code-ultimate-guide-landing/index.htmlとexamples.htmlをフッター+FAQのバージョン、バッジのテンプレート数、eval数、ガイド行数の近似（~9800+）について確認
>
> レポート: 同期済み ✅ / 修正が必要な行番号を含む不一致
```

**ROI**:
- 本番環境への同期ずれのデプロイゼロ
- 手動の`./scripts/check-landing-sync.sh`実行を回避
- スクリプトより速い（2分 vs スクリプト実行+修正の5分）

**スキップする場合**: 純粋なコード変更（ドキュメント/数に影響なし）。

**成功基準**:
```
✅ すべて同期: バージョン、テンプレート数、eval数が一致
⚠️ 不一致: index.htmlで修正が必要な具体的な行番号
```

### 2.3 Claude Codeガイド - マルチファイルドキュメント更新

**ユースケース**: 複数のファイル（ultimate-guide.md、reference.yaml、README.md）に新機能のドキュメントを追加し、相互参照の一貫性を保つ

**トリガー**: 新しい機能セクション（50行以上）、破壊的な変更、アーキテクチャの更新

**所要時間**: 5〜8分

**チーム構成**:
```
チーム: doc-update（3エージェント）
├─ content-writer → 例を含むultimate-guide.mdのメインセクションを執筆
├─ index-updater → 目次、reference.yamlのエントリ、READMEナビゲーションを更新
└─ consistency-checker → 相互参照、行番号、アンカーの動作を確認
```

**コピー＆ペースト用プロンプト**:
```
> 新しい「[機能名]」機能のドキュメントを更新してください:
> - コンテンツスコープ: guide/ultimate-guide.mdのセクション[X.Y]を以下で執筆:
>   - 概要（何/なぜ/いつ）
>   - 2〜3の具体的な例
>   - ベストプラクティス + 落とし穴
>   - 関連セクションへのリンク
>   コンテキスト: guide/ultimate-guide.mdのセクション[X.Y]のみ
> - インデックススコープ: 以下を更新:
>   - guide/ultimate-guide.mdの目次（セクション[X.Y]を追加）
>   - machine-readable/reference.yaml（行番号を含むエントリを追加）
>   - README.mdナビゲーション（主要機能の場合はリンクを追加）
>   コンテキスト: インデックスファイルのみ（目次、reference.yaml、README.md）
> - 一貫性スコープ: 以下を確認:
>   - すべての相互参照が正しく解決される
>   - reference.yamlの行番号が実際のコンテンツと一致する
>   - READMEのアンカーが正しいセクションを指している
>   - 壊れた内部リンクがない
>   コンテキスト: 相互参照検証のための修正されたすべてのファイル
```

**ROI**:
- リンク切れゼロ（consistency-checkerがすべて検出）
- 逐次処理より60%速い（執筆 → インデックス → 確認）
- 並行作業で待機時間を削減

**スキップする場合**: 単一ファイルの編集（50行未満）、相互参照不要。

**実際の例**（エージェントチームセクションの追加）:
```
タスク: 「エージェントチーム」をセクション9.20として追加（300行）
変更したファイル: 3（ultimate-guide.md、reference.yaml、README.md）

逐次処理の見積もり: 12〜15分（執筆 → インデックス → 確認）
エージェントチーム: 7分30秒（3エージェント並行）
節約: 40%の時間 + 手動の相互参照チェックゼロ
```

### 2.4 RTK - セキュリティPRレビュー

**ユースケース**: 外部コントリビューターのPRを、セキュリティ問題（インジェクション、トークン漏洩）、Rustのイディオム、パフォーマンスについてレビュー

**トリガー**: コアでないコントリビューターが開いたPR、機密コードに触れるPR（認証、外部コマンド、正規表現）

**所要時間**: 5〜8分

**チーム構成**:
```
チーム: security-pr-review（3エージェント）
├─ rust-expert → 所有権パターン、エラーハンドリング（anyhow/thiserror）、イディオマティックコードを確認
├─ security-auditor → インジェクションリスク、トークン漏洩、入力サニタイゼーションをスキャン
└─ perf-analyzer → アロケーション、asyncパターン、コンパイル済み正規表現をレビュー
```

**コピー＆ペースト用プロンプト**:
```
> PR #[番号]をスコープに集中した分析でレビューしてください:
> - Rustスコープ: 以下を確認:
>   - 所有権パターン（StringよりSplit &strを優先、cloneを最小化）
>   - エラーハンドリング（.context()を使ったanyhow::Result、テスト以外でunwrapなし）
>   - イディオマティックコード（型の後にimpl、#[cfg(test)] mod tests）
>   - Clippyコンプライアンス（警告ゼロ）
>   コンテキスト: 修正されたすべての.rsファイル
> - セキュリティスコープ: 以下をスキャン:
>   - コマンドインジェクション（シェルエスケープ、引数サニタイゼーション）
>   - トークン/認証情報の漏洩（ハードコードされたシークレット、ログ、エラーメッセージ）
>   - 入力サニタイゼーション（パストラバーサル、正規表現DoS）
>   - ファイル操作（パス検証、パーミッション）
>   コンテキスト: 入力処理、認証、ファイルI/Oのコード
> - パフォーマンススコープ: 以下をレビュー:
>   - 不要なアロケーション（String::fromと&str）
>   - asyncパターン（CPUバウンドの作業にはspawn_blocking）
>   - コンパイル済み正規表現（ホットパスにはlazy_static!）
>   - アルゴリズムの複雑さ（O(n)とO(n²)）
>   コンテキスト: ホットパス、ループ、async関数
```

**ROI**:
- ブラインドスポットの検出: セキュリティ + Rust + パフォーマンス = ソロレビュアーが見逃す領域
- 一貫したレビュー品質（レビュアーの気分や集中力に依存しない）
- 逐次処理より速い（3エージェント並行 vs 3パスレビュー）

**スキップする場合**: 信頼できるコントリビューターからの内部PR、些細な変更（ドキュメント、コメント、テストのみ）。

**成功基準**:
```
✅ 収束: 2つ以上のエージェントが同じクリティカルな問題にフラグ（高信頼度）
✅ ユニークな洞察: 各エージェントがドメイン固有の問題を発見（Rust/セキュリティ/パフォーマンス）
❌ 偽陽性: 調査結果の20%未満が無効
```

**実際の例**（架空の外部PR）:
```
PR: 新しいgitフィルターコマンドを追加
エージェントの調査結果:
- Rust: 3つの問題（本番コードでunwrap、.context()がない、非イディオマティックなエラーハンドリング）
- セキュリティ: 2つのクリティカル（ユーザー入力経由のシェルインジェクション、エラーメッセージのトークン漏洩）
- パフォーマンス: 1つの問題（毎回呼び出しでコンパイルされる正規表現、lazy_staticではない）

収束: セキュリティとRustが入力サニタイゼーションの欠如にフラグ（高信頼度）
時間: 6分40秒
評価: ✅ クリティカルなセキュリティ問題を検出、PRの修正が必要
```

## 3. 判断マトリクス: いつ使うか

| 状況 | エージェントチーム？ | 理由 |
|-----------|---------------|--------|
| **リリース前レビュー（ガイド）** | ✅ YES | 複数層の監査（正確さ + 一貫性 + 破壊的変更）は並行した視点が必要 |
| **シンプルなタイポ修正** | ❌ NO | 過剰、1エージェント = 10秒、3エージェント = コストの無駄 |
| **外部PR（RTK）** | ✅ YES | セキュリティ + Rust + パフォーマンス = ブラインドスポットの検出、高リスクレビュー |
| **マルチファイルドキュメント更新（ガイド）** | ✅ YES | コンテンツ + インデックス + 一貫性 = リンク切れゼロ、並行作業 |
| **ランディング同期確認** | ⚠️ MAYBE | 同期ずれが疑われる場合はエージェントチーム、そうでなければ`./scripts/check-landing-sync.sh`の方が速い |
| **CHANGELOG更新** | ❌ NO | 逐次タスク（線形的な執筆）、並列化の恩恵なし |
| **単一ファイル編集（RTK）** | ❌ NO | 調整不要、逐次処理で可 |
| **小さなREADMEの調整（50行未満）** | ❌ NO | 相互参照なし、複雑さなし、単一エージェントの方が速い |
| **アーキテクチャ設計** | ✅ YES | 複数の視点（フロントエンド、バックエンド、インフラ、セキュリティ）がブラインドスポットを明らかにする |
| **バグ調査** | ⚠️ MAYBE | シンプルなバグ → NO、複雑なマルチコンポーネントの失敗 → YES |

### 目安

**エージェントチームを使う場合**:
- ✅ 「X、Y、Zを確認すべき」と自然に思う
- ✅ 高リスク（本番リリース、外部コントリビューター、セキュリティ機密）
- ✅ マルチスコープ分析が必要（Rustスコープ + セキュリティスコープ + パフォーマンススコープ）
- ✅ クロスファイルの一貫性が重要（リンク、数、バージョンの同期）
- ✅ 並行作業が可能（独立したタスク、逐次依存なし）

**エージェントチームを使わない場合**:
- ❌ シンプルなタスク（5ファイル未満、100行未満、1ドメイン）
- ❌ 逐次ワークフロー（ステップBがステップAの結果に依存）
- ❌ 予算が限られている（3倍のトークン、高価値タスクのために確保する）
- ❌ 書き込みが多い（同じファイルへの多くの編集 = マージコンフリクト）

### サンプルプロンプト（コピー＆ペースト対応）

#### リリース前ガイド監査

```
> リリース前監査チームを作成してください:
> - Accuracy: CHANGELOG.md、README.md、guide/ultimate-guide.mdのすべてのクレーム、統計、バージョン番号、外部リンクを確認
> - Consistency: テンプレート数（examples/のファイルを数える）、eval数（docs/resource-evaluations/のファイルを数える）、ガイド行数（wc -l guide/ultimate-guide.md）がREADME.md、guide/cheatsheet.md、machine-readable/reference.yamlで一致するか確認
> - Breaking: CHANGELOG.md [Unreleased]セクションを分析してv3.23.0からの破壊的な変更を特定
```

#### セキュリティPRレビュー（RTK）

```
> PR #42をスコープに集中した分析でレビューしてください:
```

## 5. 成功メトリクス

### エージェントチームのROIを測定する方法

| メトリクス | 目標 | 測定方法 |
|--------|--------|----------------|
| **収束率** | >50% | 2つ以上のエージェントがフラグを立てた調査結果数 / 総調査結果数。高い収束 = 高い信頼度。 |
| **ユニークな洞察** | 各エージェント≥1 | 各エージェントが自分のドメインで少なくとも1つのユニークな問題を見つけなければならない。ユニークな問題が0 = トークンの無駄。 |
| **偽陽性率** | <20% | 無効な調査結果数 / 総調査結果数。偽陽性が多すぎる = 悪いプロンプト。 |
| **時間節約** | 60〜70% | エージェントチームの時間 vs 逐次処理（3タスクに対して1エージェントの3倍の時間と見積もる）を比較。 |
| **バグ検出率** | >80% | エージェントが検出したクリティカルなバグ数 / 出荷後に見つかった総バグ数。高い = 効果的な防止。 |

### 実際の例: リリース前レビューテスト（2026-02-08）

```
タスク: v3.23.1のリリース前監査
エージェント: 3（accuracy-auditor、consistency-checker、breaking-checker）
所要時間: 4分12秒

調査結果（生）: 45件
├─ Accuracy: 12件（1つのクリティカル: LinkedInのURL不正形式、11件の警告）
├─ Consistency: 18件（2つのクリティカル: テンプレート数の同期ずれ、行番号が古い）
└─ Breaking: 15件（破壊的な変更なし、15件の情報メモ）

調査結果（重複排除）: 約30件のユニークな問題

収束分析:
├─ 高信頼度（2〜3エージェント）: 4件の問題
│   ├─ テンプレート数の不一致（consistency + accuracy）
│   ├─ 行番号が古い（consistency + accuracy）
│   ├─ 外部リンクの確認が必要（accuracy + breaking）
│   └─ ファイル間のバージョン同期（3エージェント全員）
└─ ユニークな洞察:
    ├─ Accuracy: LinkedInのURL破損（このエージェントのみ検出）
    ├─ Consistency: 目次構造の逸脱（このエージェントのみ）
    └─ Breaking: Changelogフォーマットの改善提案（このエージェントのみ）

メトリクス:
├─ 収束率: 4/30 = 13%（目標より低いが、複数のエージェントがフラグを立てた4つのクリティカルな問題 = 重要な点での高信頼度）
├─ ユニークな洞察: 3/3エージェント = 100%（各エージェントがドメイン固有の問題を発見）
├─ 偽陽性率: 2/30 = 6.6%（20%の目標以下 ✅）
├─ 時間節約: 4分 vs 推定12分の逐次処理 = 66%の節約 ✅
├─ バグ検出率: 出荷されるはずだった3つのクリティカルなバグを検出 = 本番問題を防止 ✅

評価: ✅ リリース前監査に高い価値
```

### メトリクスの追跡方法

**エージェントチームタスクの後に**:

1. **調査結果を数える**: エージェントごとの生の調査結果を記録し、重複を排除する
2. **収束にマーク**: 2つ以上のエージェントがフラグを立てた問題はどれか？
3. **ユニークな洞察を確認**: 各エージェントはドメイン固有の問題を少なくとも1つ見つけたか？
4. **偽陽性を確認**: いくつの調査結果が無効/ノイズだったか？
5. **時間比較**: エージェントチームの所要時間 vs 推定逐次処理時間
6. **出荷後の検証**: エージェントチームは出荷されたはずのバグを検出したか？

**ログを保持する**（プロジェクトドキュメントのMarkdownテーブル）:

```markdown
| 日付 | タスク | エージェント数 | 所要時間 | 調査結果数 | 収束率 | ユニーク数 | 偽陽性率 | 時間節約 | バグ検出数 |
|------|------|--------|----------|----------|-------------|--------|--------|------------|-------------|
| 2026-02-08 | リリース前 v3.23.1 | 3 | 4m12s | 30 | 13%（4クリティカル） | 3/3 | 6.6% | 66% | 3 |
```

**メトリクスが失敗した場合はプロンプトを調整する**:
- 収束率が低い（<30%） → スコープが狭すぎる、コンテキストの境界をもっと重複させる
- ユニークな洞察なし → スコープが似すぎている、分析の角度を多様化させる
- 偽陽性が多い（>20%） → プロンプトが曖昧すぎる、具体的な基準を追加する

## 6. 制限とレッドフラグ

### エージェントチームがしないこと

| 制限 | 意味 | 対策 |
|------------|---------------|-----------|
| **3倍のトークン** | 各エージェント = 別のモデル呼び出し = 3倍のコスト | 高リスクタスクのために確保する（リリース前、セキュリティPR、タイポ修正ではなく） |
| **アイドルスパム** | 調整中に「Idle」メッセージを表示する | 正常な動作、バグではない、スパムを無視する |
| **実験的** | リサーチプレビュー = 安定性保証なし | バグを予期する、エージェントチームを本番クリティカルなワークフローに依存しない |
| **調整オーバーヘッド** | 最大3〜5エージェント、10ではない（調整の複雑さが増大） | 2〜4エージェントに留める、「10人チーム」プロンプトを避ける |
| **コンテキスト分離** | エージェントはお互いの発見を見ない（独立して作業） | Claudeが調査結果を統合するが、エージェントはタスクの途中でお互いの作業の上に構築できない |

### レッドフラグ: 使わない場合

❌ **シンプルなタスク**（5ファイル未満、100行未満、1ドメイン）
- 例: README.mdのタイポを修正
- 避ける理由: 10秒のタスクに3倍のトークン = 無駄

❌ **逐次ワークフロー**（ステップBがステップAの結果に依存）
- 例: 機能を実装 → テストを書く → デプロイ
- 避ける理由: エージェントは並行して作業する、依存関係を処理できない

❌ **予算が限られている**（3倍のトークン、コストを最適化）
- 例: 限られたAPIクレジットの個人プロジェクト
- 避ける理由: エージェントチーム = 高リスクタスクのための贅沢品、日常のワークフローではない

❌ **書き込みが多い**（同じファイルへの多くの編集）
- 例: コードベース全体の構造をリファクタリング
- 避ける理由: マージコンフリクト、調整オーバーヘッド、エージェントが踏み合う

❌ **低リスクレビュー**（内部PR、信頼できるコントリビューター、シンプルな変更）
- 例: チームメンバーが小さなバグを修正
- 避ける理由: 過剰、単一エージェントレビューの方が速くて安い

### 使うべき場合（コストにもかかわらず）

✅ **高リスク**（本番リリース、セキュリティ機密、外部コントリビューター）
✅ **マルチドメイン**（Rust + セキュリティ + パフォーマンス = ブラインドスポット）
✅ **並行処理に適している**（独立したタスク、逐次依存なし）
✅ **一貫性が重要**（クロスファイルの同期、数、バージョン）
✅ **学習機会**（ブラインドスポットを理解する、プロンプトを改善する）

- ❌ 予算が限られている
