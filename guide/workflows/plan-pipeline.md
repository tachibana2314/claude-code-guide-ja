# プラン・バリデート・エグゼキュートパイプライン

> **信頼度**: Tier 2 — AIファースト製品をスケールで出荷する本番チームによって実戦テスト済み。ネイティブ `/plan` モードを構造化されたエージェントオーケストレーションと組織的メモリで拡張。

3つのコマンドによる完全な開発ワークフロー: ダイナミックなリサーチチームでプランし、独立した専門家レビュアーでバリデーションし、並行エージェントで実行。各実行はADR学習ループを通じて次の実行を改善し、人間への割り込みを段階的に減らします。

**読了時間**: 約25分
**前提条件**: サブエージェント、タスクツール、worktree、基本的なADRの概念
**関連**: [プラン駆動開発](./plan-driven.md)、[エージェントチーム](./agent-teams.md)、[仕様ファースト](./spec-first.md)

## 要約

```
/plan-start    → 5フェーズのプランニング: PRD分析 + ダイナミックリサーチチーム + ADR
/plan-validate → 2レイヤーのレビュー: 構造チェック + トリガーベースの専門家エージェント
/plan-execute  → worktree + TDD + 並行実行 + PR + マージ + クリーンアップ
```

**`/plan` モードとの違い**:
- リサーチは順次ではなく専門化されたエージェントが並行して行う
- バリデーションはプランニングから独立（確認バイアスなし）
- 重要な決定はすべてADRを生成し、将来の決定を自動解決
- 実行はgit worktree内でタスクごとにエージェントを生成し、タスクごとにコミット、マージされたPRまですべてを処理

**各コマンドの間に `/clear` を実行**してコンテキストをリセットし、圧縮オーバーヘッドを避けます。

## 哲学

### 非指示的AIファースト

Claudeに**どのように**実装するかではなく**何を**達成すべきかを伝えます。実装の詳細を指示した瞬間、あなたは自分の知識を天井として使い、Claudeの知識を床として使うことになります。

新しいプロジェクトの冒頭に適した質問:
```
How should I use you most effectively to build this platform?
```

Claudeにアーキテクチャを提案させます。あなたの仕事は意思決定を検証することであり、それを指示することではありません。

### バンドエイドなし、回避策なし

パイプライン内のすべてのエージェントへのハードルール:

> 私たちはstate-of-the-artなソフトウェアを構築します。常に最高のアーキテクチャ、最も堅牢なパターン、業界標準のアプローチを選択します。

構築時間と労力はアーキテクチャの決定には関係ありません。実装の複雑さをオプション評価に含めることは決してありません。正しい解決策は常に最良の解決策です。

**実施チェックリスト**（実装前に適用）:
- [ ] 後方互換性フラグ、シム、またはレガシーモードを使用しているか？
- [ ] 現在の公式ドキュメントに従う新しいプロジェクトはこのようにするか？
- [ ] 新しいパターンを学ぶ代わりに古いパターンを移植しているか？
- [ ] システムレベルで修正すべきところを1つのコンポーネントにパッチを当てているか？

「はい」の答えがある場合: 止めて、正しいレベルで修正します。

### なぜ独立したバリデーションが必要か？

プランを書かなかったバリデーターはその仮定に縛られていません。研究によれば、敵対的なフレーミングによるマルチエージェントレビューは、自己レビューよりも有意に多くの問題を検出します。平均的なプランは独立したチームに挑戦されると約18の問題を生み出します — その約95%は既存のADRと第一原理から自動解決されます。

## 3つのコマンド

### `/plan-start` — 5フェーズのプランニング

**フェーズ1: PRDとデザイン分析** *(インタラクティブ、エージェントなし)*

PRDを読み、エージェント作業の前に3つのバケットで問題を表面化させます:
- 欠落している要件（不明確な受け入れ基準、未指定のエッジケース）
- 曖昧な要件（複数の有効な解釈）
- コンプライアンスの懸念（セキュリティ、データプライバシー、APIコントラクト）

長所・短所を含むオプションを提示し、決定を記録します。PRD以外の作業（リファクタリング、インフラ、バグ修正）の場合はスキップします。

UIの変更がスコープにある場合は、デザイン分析まで拡張します: 画面インベントリ、状態カタログ（空/読み込み中/populated/エラー）、インタラクション仕様、アニメーションパターン、アクセシビリティ（ARIA）、デザイントークンの更新。

**フェーズ2: 技術分析** *(1-2個のExploreエージェント + インタラクティブ)*

最初に既存のADRとPATTERNS.mdを確認します。3つ以上の確認済みADRが決定と一致する場合 → 確認なしで自動解決します。それ以外の場合:
- ターゲットを絞ったコードベースリサーチのためにExploreエージェントを生成
- オプションと推奨事項を含むアーキテクチャ決定を提示
- 重要な決定のためのADRドキュメントを作成（[ADR学習ループ](#adr学習ループ)を参照）
- PATTERNS.mdを更新

**フェーズ3: スコープ評価** *(自動 + ユーザー承認)*

エージェントプールに対してトリガールールを適用します（[ダイナミックエージェントプール](#ダイナミックエージェントプール)を参照）。各エージェントの正当性を含む提案チームを提示します。ユーザーはリサーチ開始前にエージェントを追加または削除できます。

| ティア | エージェント数 | ラベル |
|------|-------------|-------|
| 0 | 0 | ソロ（インラインリサーチ） |
| 1 | 1-3 | フォーカス |
| 2 | 4-6 | スタンダード |
| 3 | 7-9 | コンプリヘンシブ |
| 4 | 10+ | フルスペクトル |

**フェーズ4: リサーチとプラン作成** *(ダイナミックチーム)*

- ティア0: インラインリサーチ、エージェントなし
- ティア1+: 承認されたエージェントを並行して生成（バックグラウンド）、リードがTaskOutputループで監視
- `planning-coordinator`（Opus）がすべてのレポートを最終プランに統合
- プランファイル、ADR、作成アーティファクトをコミット

出力: `docs/plans/plan-{name}.md` + `docs/adr/ADR-XXXX.md` + `docs/plans/metrics/{name}.json`

**自動遷移**: 未解決の曖昧さなし → 自動で `/plan-validate` を開始

---

### `/plan-validate` — 2レイヤーのバリデーション

**レイヤー1: 構造** *(インライン、即時)*

エージェントを必要としない機械的なチェック:
- プランの形式と完全性（必要なセクションがすべて存在するか）
- タスクの順序と依存関係チェーン（循環依存なし）
- ファイル存在チェック（変更対象として記載されたファイルが実際に存在するか）
- ADRの一貫性（プランはADRに沿っているか）
- CLAUDE.mdルールへの準拠

**レイヤー2: 専門家レビュー** *(トリガーベース、0-8エージェント)*

| エージェント | トリガー | モデル |
|-------|---------|-------|
| `security-reviewer` | 認証、決済、PII、RBAC、新しいAPI | Opus |
| `db-migration-reviewer` | 新しいテーブル、カラム、インデックス、マイグレーション | Opus |
| `performance-reviewer` | 新しいリゾルバー、クエリ、ルート、新しい依存関係 | Sonnet |
| `design-system-reviewer` | 新しいUIコンポーネント、ビジュアルスタイリング | Sonnet |
| `ux-reviewer` | 新しいページ、フォーム、インタラクション | Sonnet |
| `cross-platform-reviewer` | Web + モバイル、または共有パッケージ | Sonnet |
| `native-app-reviewer` | モバイル画面、ネイティブUIパッケージ | Sonnet |
| `integration-reviewer` | 新しいサービス、ライブラリ、OTEL設定 | Opus |

些細なプランにはエージェントが自動的に選択されません。決済機能では4つ以上がトリガーされる場合があります。

**自動修正フェーズ**

すべての問題を解決する必要があります — スキップは不可。トリアージ:
1. 既存のADRの決定と一致する問題 → 自動解決
2. 確認済みのPATTERNS.mdエントリと一致する問題 → 自動解決
3. 第一原理から解決できる問題 → 自動解決
4. 残余 → 人間の決定 → 新しいルール → 次回は自動解決

**自動遷移**: すべての問題が解決 → 自動で `/plan-execute` を開始

---

### `/plan-execute` — マージされたPRまでの実行

単一コマンドがすべてを処理します:

1. **Worktree作成** — 現在のブランチから分離されたブランチ
2. **TDDスキャフォールディング** — TDDマーク付きタスクに対して最初に失敗するテストを書く
3. **レベルベースの並行実行** — 独立したタスクを検出し、タスクごとにエージェントを生成し、タスクごとにコミット
4. **ドリフト検出** — 実装がプランから逸脱した場合にフラグを立てる
5. **品質ゲート** — 並行テスト + 統合スモークテスト（GraphQLプローブ、コンテナログスキャン、プランで定義されたスモークコマンド）
6. **PR前のドキュメント更新** — PRD調整 + プランアーカイブ（worktree内）
7. **PRの作成とマージ** — スカッシュマージ、クリーンなコミットメッセージ
8. **マージ後のメトリクス** — 実行データをメトリクスファイルにコミット
9. **Worktreeのクリーンアップ** — ブランチとworktreeを削除

品質ゲートが失敗した場合: 専用のデバッグエージェントによる最大3回の自動修正試行。それでも失敗 → 人間に通知。

## ダイナミックエージェントプール

エージェントはCLAUDE.mdにハードコードされていません。呼び出し時に定義されます — 説明、トリガー基準、モデル選択がそれらが生成されるプランフェーズに埋め込まれます。これによりCLAUDE.mdを軽量に保ちながら、各エージェントに役割の完全なコンテキストを与えます。

### リサーチプール（`/plan-start`）

| エージェント | トリガー | モデル |
|-------|---------|-------|
| `code-explorer` | 常時 | Sonnet |
| `arch-researcher` | 多層変更（2層以上） | Sonnet |
| `database-analyst` | DBスキーマの変更 | Sonnet |
| `security-analyst` | 認証、決済、PII、RBAC | Opus |
| `test-analyzer` | 非自明な機能 | Sonnet |
| `cross-platform-specialist` | モバイルの同等性が必要 | Sonnet |
| `native-app-specialist` | タスクがモバイル/UIに触れる | Sonnet |
| `design-system-researcher` | UIの変更がスコープ内 | Sonnet |
| `dependency-researcher` | 新しいパッケージを追加 | Sonnet |
| `devops-specialist` | Docker、環境変数、CI/CD | Sonnet |
| `integration-researcher` | 新しいサービス、ライブラリ、OTEL | Opus |
| `planning-coordinator` | 常時（2エージェント以上の場合） | Opus |

**主要な設計選択**:
- Opusは高リスクな役割のみ（セキュリティ、統合、調整）
- Sonnetは標準的なリサーチ（良質、低コスト）
- `planning-coordinator` は2エージェント以上が選択された場合のみ生成 — 統合するがリサーチはしない

### バリデーションプール（`/plan-validate`）

上のレイヤー2のテーブルを参照。これらはリサーチプールとは異なるエージェントです — バリデーターは作成プロセスによってバイアスされません。

## ADR学習ループ

すべての重要なアーキテクチャ決定はADRを生成します。時間の経過とともに、ADRは人間への割り込みを減らす組織的メモリとして蓄積されます。

### ADRをトリガーするもの

**常にADRを作成する:**
- 複数の有効なインタラクションパターンの選択（オーバーレイ対ページ、ドロワー対モーダル）
- 既存の規約にない新しいアニメーションやトランジションパターン
- プラットフォームの差異決定（Webとモバイルの動作）
- 新しいパターンを導入するロード状態戦略
- 認証戦略、DBスキーマのアプローチ、サービス境界の決定
- アーキテクチャへの影響を持つ新しい依存関係の選択

**ADRを作成しないもの:**
- 承認されたソースや既存の規約によって決定された事項
- 確立されたパターン内のマイナーなレイアウトの選択
- 明白な状態カタログエントリ（標準的な空/読み込み中/エラー状態）

### 成熟度レベル

```
1 ADR  → Watching   — 追跡中、まだ規定的ではない
2 ADR  → Emerging   — 先例コンテキストと共に推奨デフォルトとして提示
3+ ADR → Confirmed  — プランニング中に自動解決（人間の入力不要）
          → CLAUDE.mdへのハードルールとして昇格候補
```

### ループ

```
/plan-start フェーズ2     →  ADRが作成される
                               ↓
                        PATTERNS.mdが更新される
                               ↓
/adr-review（定期的）    →  ADR全体のパターンを検出
                               ↓
                        CLAUDE.mdへの昇格を提案
                               ↓
将来の /plan-start      ←  確認済みルールが決定を自動解決
```

`/adr-review` を10-15のプランごとに実行して、パターンをバッチ分析しCLAUDE.mdへの追加を提案します。

**複利効果**: 20のプランを持つプロジェクトはアーキテクチャ決定の約80%を自動解決します。人間の入力は本当に新規の決定のみに集中します。

## CLAUDE.mdの規律

### ハードリミット: 120行

CLAUDE.md内のすべての行はすべてのリクエストでコンテキストコストがかかります。300行のCLAUDE.mdは、すべての単一のプロンプトの前に実行されるオーバーヘッドです。ハードリミットを設定して強制します。

**CLAUDE.mdに入る資格があるもの:**
- 第一原理（エージェントの好みを上書きするハードルール）
- 確認済みのADRパターン（3回以上の発生）
- エージェントがコードベースから推測できないプロジェクト固有の規約
- サブファイルへのポインター

**CLAUDE.mdに含めてはいけないもの:**
- デザインシステム、環境設定、アーキテクチャドキュメントの完全な内容
- タスクの10%未満に適用されるルール
- 説明と根拠（ADRに書く）

### ポインター戦略

すべてのコンテキストをCLAUDE.mdに読み込む代わりに、ポインターを使用します:

```markdown
## コンテキストファイル（関連する場合のみ読み込む）
- @docs/DESIGN_SYSTEM.md    — UIの変更がスコープ内の場合
- @docs/ARCHITECTURE.md     — サービス境界が触れられる場合
- @docs/ENV_CONFIG.md       — DockerまたはenvVarが変更される場合
- @docs/ADR_PATTERNS.md     — プランニングフェーズ中
```

エージェントはタスクが必要とするものだけを読み込みます。バックエンドタスクはデザインシステムを読み込まない。コンテキストはクリーンに保たれます。

### 定期的なトリミング

`/adr-review` と並行して10-15のプランごとにCLAUDE.mdをレビューします。確認済みのパターンを昇格させ、コードベースの規約で明らかになったルールを削除し、参照されていないものをトリミングします。

## コンテキスト管理

### ステップ間で `/clear`

`/plan-start`、`/plan-validate`、`/plan-execute` の間に `/clear` を実行します。各コマンドは自己完結型です — ディスク上のプランファイルがハンドオフアーティファクトであり、インメモリのコンテキストではありません。

`/clear` なし: コンテキストがすべてのフェーズにわたって蓄積し、圧縮が早くトリガーされ、エージェントが前のフェーズから無関係なコンテキストを引き継ぎ、トークンコストが大幅に増加します。

### なぜこれが機能するか

各コマンドはディスクから入力を読み込みます（プランファイル、ADR、コードベース）。ステップ間のコンテキストウィンドウに生存する必要がある状態はありません。ステップ間でクリアする規律こそが、コンテキスト制限に達することなくパイプラインが大きなプロジェクトに拡張できる理由です。

## 使う場面

### このパイプラインを使う場合

- 機能が複数のファイルとレイヤーを必要とする（API + DB + UI）
- セキュリティに敏感な変更（認証、決済、PII）
- 複雑なDBマイグレーション
- 新しい外部サービスの統合
- プランニングのミスが取り消しにコストがかかる場合
- 決定の履歴が重要なチームプロジェクト

### 使わない場合

- タイポ修正、些細なリファクタリング（標準の `/plan` モードを使用）
- 要件が不明な探索的プロトタイピング
- 時間プレッシャー下のホットフィックス（代わりにデュアルインスタンスプランニング）
- アーキテクチャ決定なしで2ファイル以下の変更

### ティア0のショートカット

小さいが非自明な変更の場合でも、パイプラインを実行しますが、システムがティア0のスコープを検出し、エージェントの生成をスキップします — リサーチはインラインで行われ、バリデーションはレイヤー1のみ、実行はシングルエージェント。同じコマンド、低いオーバーヘッド。

## コストプロファイル

| フェーズ | コストドライバー | おおよその範囲 |
|-------|-------------|-------------------|
| `/plan-start` ティア0 | インラインリサーチのみ | $0.10-0.30 |
| `/plan-start` ティア1-2 | 2-6個のSonnetエージェント | $0.50-2.00 |
| `/plan-start` ティア3 | 7+エージェント + Opusコーディネーター | $2.00-8.00 |
| `/plan-validate` | 0-8エージェント | $0.20-3.00 |
| `/plan-execute` | タスクごとのエージェント + 品質ゲート | $0.50-5.00 |
| **典型的な機能（ティア2）** | フルパイプライン | **$2-10** |

ADRカバレッジが増えるにつれてコストは複利的に下がります: 必要なエージェントが少なく、バリデーションの問題が少なく、実行が速くなります。

`/plan-metrics` を定期的に使用して、過去のコスト傾向をレビューし見積もりを調整します。
