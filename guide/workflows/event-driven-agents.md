# イベント駆動エージェント自動化

> **信頼度**: Tier 3 — 新興のパターン、初期採用者は良い結果を報告しているが、ツールはまだ成熟中。

各タスクのためにClaude Codeを手動で呼び出すのではなく、外部イベントが作業を駆動させます。LinearでカードがIn Progressに移動すると、Claudeが自動的に受け取ります。GitHubのイシューに`claude-fix`ラベルが付くと、数秒以内にエージェントが作業を開始します。

これはプル型（「ねえClaude、これをやって」）からプッシュ型（「イベントがエージェントをトリガーする」）へのシフトです。

## コアコンセプト

従来のClaude Codeの使用はインタラクティブです: ターミナルを開き、プロンプトを入力し、反復します。イベント駆動の自動化では、トリガーステップから人間が取り除かれます。人間は依然として出力（PR、コードの変更）をレビューしますが、開始は既存のプロジェクト管理ワークフローを通じて行われます。

```
イベントソース → イベントフィルター → コンテキスト抽出 → エージェント選択 → Claude Codeエージェント → 出力ルーティング
                                                                                                     ↓
                                                                              PR、コメント、カード更新としてイベントソースにフィードバック
```

ループは自己強化的です: エージェントの出力（PR、ステータス更新）はイベントソースにフィードバックされ、次のステップをトリガーできます。


## Linear駆動エージェントループ

最もドキュメント化されたパターンは、Damian Galarza（damiangalarza.com、2026年2月）のワークフローから来ています。Linearが何をすべきかの唯一の情報源として機能し、Claude Codeがエンドツーエンドの実装を処理します。

### フロー

```
開発者がカードをIn Progressに移動
    ↓（Linearウェブフック）
エージェントがカードを受け取る
    ↓
カードの説明 + 受入基準を読む
    ↓
Claude Codeが機能を実装する
    ↓
テスト + Lintを実行する
    ↓ パスの場合
PRを自動的に開く
    ↓
カードをIn Reviewに移動する
    ↓
人間がPRをレビュー
    ↓ 承認 + マージの場合
カードをDoneに移動する
```

### うまくいく理由

カードの説明がプロンプトとして機能します。明確な受入基準を持つ良いカードは良いコードを生成します。曖昧なカードは曖昧なコードを生成します、人間の開発者と同じように。チケットの品質が自動化の品質を直接決定します。

Linearの構造化されたフィールド（説明、受入基準、ラベル、優先度）はClaude Codeのニーズに自然にマッピングされます: 何を構築するか、どのように確認するか、どの制約が適用されるか。

### 主な要件

- カードは明確な受入基準を持つ必要がある（タイトルだけでなく）
- リポジトリには自動検証のための堅固なテストスイートが必要
- ブランチ命名規則は決定論的である必要がある（例: `feat/LINEAR-123-card-title`）
- PRテンプレートはエージェントの出力を標準化するのに役立つ


## 汎用イベントからエージェントへのパターン

Linearの例は特定的ですが、パターンはどのイベントソースにも一般化されます。パイプラインは5つのコンポーネントで構成されます:

### 1. イベントソース

トリガーが発生する場所。プロジェクト管理ツール、CIシステム、監視アラート、またはカスタムウェブフックの場合があります。

### 2. イベントフィルター

すべてのイベントがエージェントを生成するべきではありません。フィルターはどのイベントがアクション可能かを決定します:

```bash
# 例: 「claude-auto」ラベルが付いたカードのみ処理
if [[ "$CARD_LABELS" != *"claude-auto"* ]]; then
    echo "スキップ: claude-autoラベルなし"
    exit 0
fi
```

### 3. コンテキスト抽出

イベントペイロードから関連するデータを取り出し、Claude Codeプロンプトとしてフォーマットします。ここでツールのスキーマから自然言語の指示に変換します。

### 4. エージェント選択

異なるイベントタイプは異なるエージェント設定が必要な場合があります。バグレポートは機能リクエストとは異なるCLAUDE.mdコンテキストが必要です。許可されるツール、モデル、または安全制約が異なる場合があります。

### 5. 出力ルーティング

結果はどこへ行くか？通常、以下の組み合わせです:
- Gitブランチ + PR（コードの変更）
- 元のイシュー/カードへのコメント（ステータス更新）
- カードの状態遷移（次の列に移動）
- Slack通知（人間への認識）


## 実装例

Linearをポーリングして「In Progress」カードのClaude Codeエージェントを生成する最小限のBashループ:

```bash
#!/bin/bash
# linear-agent-loop.sh
# In Progressのカードのためにエージェントを生成する

LINEAR_API_KEY="${LINEAR_API_KEY:?Missing LINEAR_API_KEY}"
TEAM_ID="${LINEAR_TEAM_ID:?Missing LINEAR_TEAM_ID}"
PROCESSED_FILE="/tmp/linear-agent-processed.txt"
MAX_CONCURRENT=3

touch "$PROCESSED_FILE"

poll_linear() {
    curl -s -X POST https://api.linear.app/graphql \
        -H "Authorization: $LINEAR_API_KEY" \
        -H "Content-Type: application/json" \
        -d '{
            "query": "query { team(id: \"'"$TEAM_ID"'\") { issues(filter: { state: { name: { eq: \"In Progress\" } }, labels: { name: { eq: \"claude-auto\" } } }) { nodes { id title description } } } }"
        }' | jq -r '.data.team.issues.nodes[] | "\(.id)|\(.title)|\(.description)"'
}

spawn_agent() {
    local issue_id="$1"
    local title="$2"
    local description="$3"

    echo "[$(date)] エージェントを生成: $title ($issue_id)"

    claude --print --dangerously-skip-permissions \
        "次のLinearカードを実装してください:
        タイトル: $title
        説明: $description

        要件:
        1. feat/$issue_idという名前のフィーチャーブランチを作成する
        2. 説明された機能を実装する
        3. テストを実行して失敗を修正する
        4. カードタイトルでPRを作成する" \
        2>&1 | tee "/tmp/agent-$issue_id.log"

    echo "$issue_id" >> "$PROCESSED_FILE"
}

while true; do
    active_agents=$(jobs -r | wc -l)
    if [ "$active_agents" -ge "$MAX_CONCURRENT" ]; then
        echo "[$(date)] 最大同時エージェントに達した ($MAX_CONCURRENT)、待機中..."
        sleep 30
        continue
    fi

    poll_linear | while IFS='|' read -r id title description; do
        if grep -q "$id" "$PROCESSED_FILE"; then
            continue  # 既に処理済み
        fi
        spawn_agent "$id" "$title" "$description" &
    done

    sleep 60  # ポーリング間隔
done
```

これは出発点であり、本番コードではありません。実際のデプロイには適切なエラーハンドリング、永続的な状態ストア（テキストファイルではない）、ポーリングではなくウェブフックベースのトリガーが必要です。


## イベントソースの互換性

| イベントソース | トリガーイベント | エージェントのユースケース | インテグレーション方法 |
|-------------|----------------|----------------|-------------------|
| **Linear** | カード状態変更、ラベル追加 | 機能実装、バグ修正 | GraphQL API / MCPサーバー |
| **GitHub Issues** | イシュー作成、ラベル付け | バグトリアージ、調査、修正PR | GitHub Actions / ウェブフック |
| **GitHub PR** | PR開封、レビューリクエスト | コードレビュー、自動修正 | GitHub Actions |
| **Jira** | トランジション、スプリント割り当て | 機能作業、技術的負債のクリーンアップ | REST API / ウェブフック |
| **Slack** | チャンネルのメッセージ、絵文字リアクション | クイックフィックス、調査 | Slack API / ボット |
| **PagerDuty** | インシデント作成 | 診断スクリプト、初期トリアージ | ウェブフック |
| **カスタムウェブフック** | 任意のHTTP POST | 何でも | 直接HTTPエンドポイント |


## ガードレール

イベント駆動エージェントは設計上、人間の監視が少ない状態で実行されるため、ガードレールが重要になります。

### 冪等性

エージェントが同じイベントを2回処理する可能性があります（ネットワークリトライ、重複ウェブフック）。エージェントは開始前に作業がすでに存在するかどうかを確認する必要があります:

```bash
# このカードのブランチがすでに存在するか確認
if git ls-remote --heads origin "feat/$ISSUE_ID" | grep -q "feat/$ISSUE_ID"; then
    echo "ブランチがすでに存在します、スキップ"
    exit 0
fi
```

### レート制限

イベントのバーストで50のエージェントが同時に生成されないようにします。ハード制限を設定:

- **最大同時エージェント数**: ほとんどのチームで3〜5
- **クールダウン期間**: エージェント生成間の最低30秒
- **日次予算上限**: 1日あたりの最大トークン支出を設定

### サーキットブレーカー

特定のタイプのタスクでエージェントが繰り返し失敗する場合は、試みを停止します:

```bash
FAILURE_COUNT=$(grep -c "FAILED" "/tmp/agent-failures.log" 2>/dev/null || echo 0)
if [ "$FAILURE_COUNT" -gt 5 ]; then
    echo "サーキットブレーカーが作動: 失敗が多すぎる"
    # 人間に通知、自動化を一時停止
    exit 1
fi
```

### 人間がループに介在するチェックポイント

完全に自動化されたフローでも、重要なポイントで人間をループに保ちます:

- PRレビューは手動のまま（エージェントがPRを作成し、人間が承認）
- データベースマイグレーションは自動適用しない
- デプロイは別の、人間がトリガーするステップ
- 認証、課金、または個人情報に触れるカードは明示的な人間の承認が必要


## アンチパターン

| アンチパターン | 問題 | 解決策 |
|-------------|---------|----------|
| **アグレッシブなポーリング** | 5秒ごとにAPIを叩くとリソースを無駄にし、レート制限を受ける | 可能な場合はウェブフックを使用、60秒より速くポーリングしない |
| **サーキットブレーカーなし** | 同じタスクでエージェントが繰り返し失敗し、トークンを際限なく消費する | タスクごとの失敗を追跡、3回の試みの後に停止して人間に通知 |
| **デッドレターキューなし** | 失敗したイベントが消えて、作業が見逃されたことを誰も知らない | 手動レビューのために失敗したイベントを永続ストアにログ記録 |
| **無制限の並行性** | 20枚のカードが一度に移動、20のエージェントが生成、マシンがクラッシュ | 同時エージェントにハード上限（3〜5が合理的） |
| **プロンプトとして曖昧なカード** | 「あれを修正して」がゴミのようなコードを生成する | カード品質標準を強制、受入基準のないカードはスキップ |
| **状態の永続化なし** | スクリプトが再起動し、すべてを最初から再処理する | 処理済みのイベントIDをメモリではなくデータベースに保存する |
| **PRレビューのスキップ** | エージェントがmainに直接プッシュする | 常にPRフローを通じて、人間が出力をレビュー |


## ツールとリソース

### MCPサーバー

- **linear-kanban-mcp**（GitHubの0xikarus）: ClaudeCodeから直接kanbanボード管理のためにLinear APIを公開。エージェントコンテキストを離れずにカードの読み取り、状態の更新、ラベルの管理が可能。

### スキルとプラットフォーム

- **skillsllm.com**: Linearカードから始まるプランニング、検証、実行の完全なサイクルをオーケストレーションするスキルを提供。カードメタデータから構造化されたClaude Codeプロンプトへの変換を処理。

### エージェントテンプレート

- **Scrum Masterエージェント**（lobehub.com）: Claude DesktopまたはClaude Codeのどちらで実行しているかを自動検出し、それに応じて動作を適応させる。コンテキスト対応エージェント設計の出発点として便利。
