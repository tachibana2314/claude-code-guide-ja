## 1. 概要

### エージェントチームとは？

エージェントチームは、**複数のClaudeインスタンスがgitベースのシステムを通じて調整しながら異なるサブタスクを並列に処理する**ことを可能にします。別々のClaudeセッションを自分で調整する手動マルチインスタンスワークフローとは異なり、エージェントチームにはエージェントがタスクを要求し、継続的に変更をマージし、コンフリクトを自動的に解決する組み込みの調整機能があります。

**主な特徴**:
- ✅ **自律的な調整** — チームリードが委譲し、チームメイトはメールボックス経由で通信
- ✅ **ピアツーピアメッセージング** — エージェント間の直接通信（階層的なものだけでない）
- ✅ **gitベースのロック** — エージェントは共有ディレクトリへの書き込みでタスクを要求
- ✅ **継続的なマージ** — 手動介入なしに変更をpull/push
- ✅ **独立したコンテキスト** — 各エージェントが独自の100万トークンコンテキストウィンドウを保有（隔離）
- ⚠️ **実験的** — リサーチプレビュー、安定性は保証されない
- ⚠️ **トークン集中型** — 複数の同時モデル呼び出し = 高コスト

### エージェントチームと他のパターンの比較

| パターン | 調整方法 | セットアップ | 最適な用途 |
|---------|---------|------------|-----------|
| **エージェントチーム** | 自動（組み込み） | 実験的フラグ | 調整が必要な複雑な読み取り重視タスク |
| **マルチインスタンス** | 手動（人間が調整） | 複数ターミナル | 調整不要の独立した並列タスク |
| **デュアルインスタンス** | 手動（人間が監視） | 2ターミナル | 品質保証、計画と実行の分離 |
| **Taskツール** | 自動（サブエージェント） | ネイティブ機能 | 単一エージェントのタスク委譲、逐次作業 |

**主な違い**:
- **マルチインスタンス** = あなたが調整を管理（独立したプロジェクト、共有状態なし）
- **エージェントチーム** = Claudeが調整を管理（共有コードベース、gitベースの通信）

### 大規模チームが正当化される場合

上記の「5以上のエージェント」ルールは合理的なデフォルトですが、コーディネーションのオーバーヘッドよりもコストが有利になる特定のシナリオでは成り立ちません。本当の問題は「何人のエージェント？」ではなく「コーディネーションのオーバーヘッドはコンテキストオーバーフローよりもコストが低いか？」です。

**決定要因としてのコンテキストウィンドウ**: 50K行以上のコードベースでの単一のClaude Codeエージェントは、関連ファイルを読み込むだけでコンテキストウィンドウの80〜90%を消費します（出典: atcyrus.com）。その時点で、エージェントには実際の推論の余地がほとんど残りません。複数のエージェントに分割することで、各エージェントがコンテキスト使用量を約40%に保て、実際の問題解決のための余裕が生まれます。

| シナリオ | 単一エージェント | 3エージェントチーム | 5エージェントチーム |
|---------|--------------|-----------------|-----------------|
| 1万行のコードベース | コンテキスト約30%、快適 | 過剰 | 過剰 |
| 5万行のコードベース | コンテキスト80〜90%、推論が低下 | 理想的な分割 | 本当に並列なモジュールがあれば正当化 |
| 10万行以上のコードベース | コンテキストオーバーフロー、ファイルを見逃す | エージェントごとにオーバーフローの可能性も | 正当化、さらに多くを検討 |

**エージェントを増やすべき場合**:
- 共有状態がゼロの独立したモジュール（調整のオーバーヘッドなし）
- 隔離されたファイルツリーにわたる並列リファクタリング（フロントエンド vs バックエンド vs インフラ）
- 各エージェントが異なるサブシステムをカバーする読み取り重視の分析
- コードベースが1つのエージェントのコンテキストに余裕を持って収まらない場合

**エージェントを増やすと逆効果な場合**: エージェントが互いの出力を常に読む必要があったり、共有ファイルを修正する必要がある場合、エージェントを追加するとマージコンフリクトと調整メッセージが発生し、節約しようとしていたコンテキストを食いつぶします。

> **モデル選択に関する注記（2026年3月時点）**: チームの全エージェントは同じモデル（エージェントチームに必要なOpus 4.6）で実行されます。コミュニティは、チームリードがOpusで計画立案し、実装エージェントがSonnetで速度を優先し、テストエージェントがHaikuでコスト効率を実現するロールベースのモデル選択を要望しています。これはまだサポートされていません。現在の回避策は明示的な`--model`フラグを付けて別々のClaude Codeプロセスを生成することですが、組み込みの調整と共有タスクリストが失われます。これはコミュニティ機能リクエストとして追跡されています。

より広い業界的文脈として：Gartnerは2026年末までにエンタープライズアプリケーションの40%がタスク固有のエージェントを組み込むと予測しています。Claude Codeや類似ツールで現在確立されているチーム調整パターンは、おそらく標準的な実践になるでしょう。

### コスト・ベネフィット分析

**エージェントチーム**対**手動マルチインスタンス**:

| 側面 | エージェントチーム | マルチインスタンス（手動） |
|-----|----------------|----------------------|
| **セットアップ時間** | 30〜60分（フラグ + git設定） | 5〜10分（新しいターミナル） |
| **調整** | 自動（gitベース） | 手動（人間が調整） |

**エージェントチームが有利な場合**: 複雑なリファクタリング、大規模分析、調整された複数ファイルの変更
**マルチインスタンスが有利な場合**: 独立した機能、プロトタイプ探索、シンプルな並列化


## 2. アーキテクチャ詳細

### リード-チームメイトアーキテクチャ

```
┌─────────────────────────────────────────────────┐
│         チームリード（メインセッション）            │
│  - タスクをサブタスクに分解                       │
│  - チームメイトセッションを起動                   │
│  - 全エージェントの知見を統合                     │
│  - 共有タスクリスト + メールボックスで調整         │
└─────────────────┬───────────────────────────────┘
                  │
        ┌─────────┴─────────┐
        │                   │
┌───────▼────────┐  ┌───────▼────────┐
│  チームメイト1  │◄─┼────────────────►│  チームメイト2  │
│                │  │ ピアツーピア    │                │
│ - 独自コンテキ  │  │ メールボックス  │ - 独自コンテキ  │
│   スト（1M    │  │ 経由メッセージ  │   スト（1M    │
│   トークン）   │  │                 │   トークン）   │
│ - タスクを要求 │  │                 │ - タスクを要求 │
│ - チーム/      │  │                 │ - チーム/      │
│   ピアへの     │  │                 │   ピアへの     │
│   メッセージ   │  │                 │   メッセージ   │
└────────────────┘  └─────────────────┘
```

### gitベースの調整

**仕組み**:

1. **タスク要求**: エージェントが共有ディレクトリ（`.claude/tasks/`）にロックファイルを書き込む
2. **作業実行**: 各エージェントが自分のコンテキストで独立して作業
3. **継続的マージ**: エージェントが共有gitリポジトリにpull/push
4. **コンフリクト解決**: 自動マージ（制限あり、[§6](#6-制限事項と注意点)を参照）
5. **結果統合**: チームリードが知見を収集して統一された回答を提示

**ロックファイル構造の例**:
```
.claude/tasks/
├── task-1.lock        # エージェントAが要求
├── task-2.lock        # エージェントBが要求
└── task-3.pending     # まだ要求されていない
```

### 通信アーキテクチャ

**サブエージェントとの主な違い**: エージェントチームは単なる階層的なレポートではなく、メールボックスシステムを通じた**真のピアツーピアメッセージング**を実装します。

**アーキテクチャコンポーネント**（出典: [Addy Osmani](https://addyosmani.com/blog/claude-code-agent-teams/)、2026年2月）:

1. **チームリード**: チームを作成し、チームメイトを起動し、作業を調整
2. **チームメイト**: 独自のコンテキスト（各100万トークン）を持つ独立したClaude Codeインスタンス
3. **タスクリスト**: 依存関係追跡と自動ブロック解除を持つ共有作業項目
4. **メールボックス**: エージェント間の直接通信を可能にする受信箱ベースのメッセージングシステム

**通信パターン**:
- **リード → チームメイト**: 直接メッセージまたは全員へのブロードキャスト
- **チームメイト → リード**: 進捗更新、質問、知見の報告
- **チームメイト ↔ チームメイト**: 直接ピアツーピアメッセージング（アプローチへの挑戦、解決策の議論）
- **最終統合**: チームリードが全知見を集約してユーザーに提示

**メッセージングフローの例**:
```
チームリード: 「このPRのセキュリティ問題をレビューしてください」
├─ チームメイト1（セキュリティ）: 分析 → チームメイト2にメッセージ: 「45行目に認証問題を発見」
├─ チームメイト2（コード品質）: レビュー → 返信: 「確認、OWASPの違反も発見」
└─ チームリード: 知見を統合 → 統一された回答をユーザーに提示
```

**これが可能にすること**:
- ✅ エージェントが互いのアプローチに積極的に挑戦できる
- ✅ 人間の介入なしに解決策を議論できる
- ✅ 独立して調整できる（自己組織化）
- ✅ ワークフロー途中での発見の共有（コンテキストではなくメッセージ経由）

**制限**: コンテキストの隔離は維持される — エージェントは完全なコンテキストウィンドウを共有せず、明示的なメッセージのみを共有する。

### エージェント間のナビゲーション

**組み込みのナビゲーション**:
- **Shift+Down**: インプロセスモードでチームメイトを切り替え
- **tmux/iTerm2**: `teammateMode: "tmux"` でスプリットペインモード（tmuxまたは`it2` CLIが必要なiTerm2が必要）
- **直接引き継ぎ**: 必要に応じて任意のエージェントの作業を引き継げる

**例**:
```bash
# ターミナル1：チームリード（環境変数を設定）
export CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1
claude

# Claudeがチームメイトを自動的に起動
# Shift+Downでチームメイトを切り替えられる（インプロセスモード）
```

### コンテキスト管理

**エージェントごとのコンテキスト**:
- 各エージェントが**100万トークンのコンテキストウィンドウ**（Opus 4.6）を保有
- セッションあたり約30,000行のコード
- **コンテキストの隔離**: エージェントは完全なコンテキストウィンドウを共有しない
- **通信**: メールボックスシステム経由（ピアツーピア + チームリードの統合）

**総コンテキスト容量**（3エージェントの例）:
- チームリード: 100万トークン
- チームメイト1: 100万トークン
- チームメイト2: 100万トークン
- **合計**: チーム全体で300万トークン（コンテキストは隔離されているが、メッセージ経由で通信）

**重要な違い**:
- ❌ **コンテキストは共有されない**: エージェント1の完全な100万トークンのコンテキストはエージェント2には見えない
- ✅ **メッセージは共有される**: エージェントはメールボックス経由で明示的なメッセージを送信（知見、質問、議論）


## 3. セットアップと設定

### 前提条件

**必須**:
- ✅ Claude Code v2.1.32以降
- ✅ Opus 4.6モデル（`/model opus`）
- ✅ Gitリポジトリ（調整のため）

**推奨**:
- ✅ [サブエージェント](../ultimate-guide.md#sub-agents)の理解
- ✅ gitワークフローへの習熟
- ✅ 予算意識（トークン集中型の機能）

### 方法1：環境変数

**最もシンプルなアプローチ** — Claude Code起動前に環境変数を設定:

```bash
# このセッションでエージェントチームを有効化
export CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1

# Claude Codeを起動
claude
```

**恒久的なセットアップ**（bash/zsh）:
```bash
# ~/.bashrcまたは~/.zshrcに追加
echo 'export CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1' >> ~/.bashrc
source ~/.bashrc
```

### 方法2：設定ファイル

**恒久的な設定** — `~/.claude/settings.json`を編集:

```json
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}
```

**メリット**:
- ✅ セッションをまたいで永続化
- ✅ 環境変数を覚える必要がない
- ✅ dotfilesでバージョン管理できる

**編集後**、変更を有効にするためClaude Codeを再起動してください。

### 確認方法

**有効かどうかを確認**:

```bash
# Claude Codeセッション内で
> エージェントチームは有効になっていますか？
```

Claudeは次のように確認するはず:
> 「はい、エージェントチームは有効です（実験的機能）。適切な場合に複数のエージェントを起動して並列作業させることができます。」

**代替確認**（環境変数を確認）:
```bash
echo $CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS
# 「1」が出力されるべき
```

### マルチターミナルのセットアップ

**パターン**（実践者からの報告）:

```bash
# ターミナル1：調査 + バグ修正
export CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1
claude

# ターミナル2：ビジネスオペレーション
export CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1
```

## 6. 制限事項と注意点

### 読み取り重視 vs 書き込み重視のトレードオフ

**コアの制限**: エージェントチームは読み取り重視のタスクに優れていますが、複数のエージェントが同じファイルを変更する書き込み重視のタスクには苦労します。

**これが重要な理由**:
```
読み取り重視（✅ チームに適している）:
- コードレビュー: エージェントがコードを読んで分析を提供
- バグトレース: エージェントがログを読んで実行を追跡
- アーキテクチャ分析: エージェントが構造を読んでパターンを特定

書き込み重視（⚠️ チームにはリスクがある）:
- 共有タイプのリファクタリング: 複数のエージェントが同じファイルを変更 → マージコンフリクト
- データベーススキーマの変更: ファイル全体にわたる調整された移行
- APIコントラクトの更新: インターフェース変更には同期が必要
```

**軽減策**:
1. **明確な境界**: エージェントに重複しないファイルセットを割り当てる
2. **インターフェースファースト**: 並列実装の前にコントラクトを定義
3. **単一ライターパターン**: 1つのエージェントが共有ファイルを書き込み、他は読み取りのみ
4. **人間によるレビュー**: 発生したマージコンフリクトを手動で解決

### マージコンフリクトのシナリオ

**自動解決が機能する場合**:
- ✅ 異なるエージェントが異なるファイルを変更
- ✅ 同じファイルの異なる関数（クリーンなgitマージ）
- ✅ 加算的な変更（新しい関数、編集なし）

**自動解決が困難な場合**:
- ❌ 同じ行が変更された（典型的なマージコンフリクト）
- ❌ ロジックの競合（エージェントAがバリデーションを削除、エージェントBが追加）
- ❌ 循環依存（エージェントAがエージェントBの出力を必要とし、その逆も然り）

**コンフリクトの例**:
```typescript
// エージェント1の変更:
function processUser(user: User) {
  validateEmail(user.email); // バリデーションを追加
  return save(user);
}

// エージェント2の変更（同時）:
function processUser(user: User) {
  return save(sanitize(user)); // サニタイズを追加
}

// コンフリクト: 両方が同じ関数を変更
// 解決: 人間が順序を決める（validate → sanitize → save）
```

### トークン集中型の影響

**なぜトークン集中型なのか**:
- 各エージェントが**別々のモデル推論**を実行（3エージェント = 3倍のベースコスト）
- 各エージェントのコンテキスト読み込み（100万トークン × 3 = 300万トークン容量）
- 調整オーバーヘッド（チームリードの統合）

**予算への影響例**（Opus 4.6の価格）:
```
単一エージェントセッション:
- 入力: 5万トークン @ $15/M = $0.75
- 出力: 5千トークン @ $75/M = $0.38
- 合計: $1.13

エージェントチーム（3エージェント）:
- 入力: 15万トークン @ $15/M = $2.25
- 出力: 1.5万トークン @ $75/M = $1.13
- 合計: $3.38

コスト倍率: 3倍
```

**正当化が必要な場合**:
- ✅ 節約される時間 > コスト増加（本番問題）
- ✅ 品質が重要（金融サービス、医療）
- ✅ 並列化を正当化する複雑性（多層分析）
- ❌ シンプルなタスク（単一エージェントを使う）
- ❌ 個人的な学習プロジェクト（予算制約）

### 実験的ステータスの注意点

**「実験的」の意味**:
- ⚠️ **安定性の保証なし**: 機能が変更または削除される可能性がある
- ⚠️ **バグが予想される**: Anthropicへの報告（GitHub Issues）
- ⚠️ **パフォーマンスの変動**: 調整速度が変動する可能性
- ⚠️ **ドキュメントが進化中**: 公式ドキュメントはまだ最小限

**本番使用の考慮事項**:
1. **フォールバック計画**: 問題が発生した場合に単一エージェントに戻す準備
2. **監視**: トークンコストを慎重に追跡（急速にエスカレートする可能性）
3. **検証**: エージェントチームの出力を人間がレビュー（盲目的に信頼しない）
4. **フィードバック**: バグ/経験を報告してAnthropicの機能改善を支援

**実践者の報告**（2026年2月時点）:
- ✅ Paul Rayner: 「かなり印象的」（本番使用が検証済み）
- ✅ Fountain: 50%高速（本番にデプロイ）
- ✅ CRED: 速度2倍（ユーザー1500万人、金融サービス）
- ⚠️ コミュニティ: まちまちの報告（一部でマージコンフリクトの問題）

### コンテキストの隔離

**エージェントができないこと**:
- ❌ **コンテキストウィンドウを共有**: エージェント1の完全なコンテキスト（100万トークン）はエージェント2には見えない
- ❌ **発見の自動同期**: エージェント2はエージェント1の知見を明示的にメッセージ送信されるまで見えない
- ❌ **タイミングの調整**: エージェントは独立して作業し、異なる時間に終了する可能性がある

**エージェントができること**:
- ✅ **メッセージを送る**: メールボックスシステム経由（ピアツーピアまたはチームリード経由）
- ✅ **アプローチに挑戦**: 解決策を議論し、互いに質問する
- ✅ **知見を共有**: 明示的なメッセージング（自動的なコンテキスト共有ではない）

**影響**:
```
シナリオ: エージェント1がエージェント2の作業に影響する重大なバグを発見

メッセージングなしでは:
- エージェント2はエージェント1の発見を自動的に見えない
- エージェント2は誤った仮定を持って続ける可能性がある

メッセージング付き（組み込み）:
- エージェント1がエージェント2にメッセージ: 「45行目に認証問題を発見」
- エージェント2がメッセージに基づいてアプローチを調整
- チームリードが最後に全知見を統合

軽減策:
- エージェントはメールボックスシステム経由で互いにメッセージを送れる
- チームリードが全エージェント完了後に知見を統合
- 人間はワークフロー途中でエージェントに割り込んで方向を変えられる（Shift+Downでチームメイトを切り替え）
- エージェント間の依存関係を最小限にするようにタスクを設計
```

### エージェントチームを使わない場合

**単一エージェントが優れている場合**:
- ❌ **シンプルなタスク**: 単純な実装（過剰）
- ❌ **小さなコードベース**: 5ファイル未満の影響（調整オーバーヘッドが正当化されない）
- ❌ **書き込み重視のタスク**: 多くの共有ファイルの変更（マージコンフリクトのリスク）
- ❌ **逐次依存関係**: タスクBがタスクAの完了を必要とする（並列化のメリットなし）
- ❌ **予算制約**: 個人プロジェクト、学習（トークンコスト倍率）
- ❌ **密な相互依存**: タスク間の循環依存

**適合しない例**:
```
タスク: 共有auth.tsファイルの認証ロジックを更新

なぜ単一エージェントが優れているか:
- 1ファイルの変更（並列化のメリットなし）
- 書き込み重視（同じファイルへの複数の変更）
- 明確なサブタスク境界なし（ロジックが絡み合っている）
- 逐次フロー（各変更後にテスト）

結果: エージェントチームはマージコンフリクトを作成し、時間節約なし
```


## 7. 意思決定フレームワーク

### チーム vs マルチインスタンス vs デュアルインスタンス

**比較表**:

| 基準 | エージェントチーム | マルチインスタンス | デュアルインスタンス |
|-----|--------------|--------------|--------------|
| **調整** | 自動（gitベース + メールボックス） | 手動（人間） | 手動（人間） |
| **セットアップ** | 実験的フラグ | 複数ターミナル | 2ターミナル |
| **最適な用途** | 調整が必要な読み取り重視タスク | 独立した並列タスク | 品質保証（計画と実行の分離） |
| **通信** | ピアツーピアメッセージング + チームリードの統合 | 手動コピーペースト | 手動同期 |
| **コンテキスト共有** | 隔離（エージェントあたり100万、自動同期なし） | 隔離（別々のセッション） | 隔離（2セッション） |
| **コスト** | 高い（3倍以上のトークン） | 中程度（2倍のトークン） | 中程度（2倍のトークン） |
| **認知負荷** | 低い（観察者） | 高い（調整者） | 中程度（レビュアー） |
| **マージコンフリクト** | 自動解決（制限あり） | N/A（別々のリポジトリ） | 手動解決 |
| **成熟度** | 実験的（v2.1.32+） | 安定 | 安定 |

```
  │
```

### ユースケースマッピング

**エージェントチーム（✅ 使用）**:
- 多層コードレビュー（セキュリティ + API + フロントエンド）
- 並列仮説テスト（デバッグ）
- 大規模リファクタリング（明確な境界）
- コードベース全体の分析（アーキテクチャレビュー）
- 複雑な機能調査（複数のアプローチを探索）

**マルチインスタンス（✅ 使用）**:
- 別々のプロジェクト（フロントエンドリポジトリ + バックエンドリポジトリ）
- 独立した機能（共有状態なし）
- 異なる技術（PythonマイクロサービスとReactアプリ）
- 並列実験（3つの異なるアーキテクチャを試す）

**デュアルインスタンス（✅ 使用）**:
- 計画と実行のパターン（計画セッション + 実行セッション）
- 品質レビュー（実装 + コードレビュー）
- テストファースト開発（テストを書く + 実装）

**単一エージェント（✅ 使用）**:
- シンプルな実装（5ファイル未満）
- 書き込み重視のタスク（共有ファイルの変更）
- 逐次ワークフロー（ステップバイステップのチュートリアル）
- 予算制約のあるプロジェクト

### チームフレームワーク vs Beadsフレームワーク

**Beadsフレームワーク**（Steve Yegge）:
- **アーキテクチャ**: イベントソースMCPサーバー（Gas Town） + SQLiteデータベース（beads.db）
- **調整**: 永続的なメッセージストレージ、履歴のリプレイ
- **成熟度**: コミュニティ管理、実験的
- **セットアップ**: Gas Townのインストール + agent-chat UIが必要
- **ユースケース**: オンプレミス/エアギャップ環境、完全な調整コントロール

**エージェントチーム**（Anthropic）:
- **アーキテクチャ**: ネイティブClaude Code機能、gitベースの調整
- **調整**: リアルタイムのgitロック、自動マージ
- **成熟度**: Anthropicの公式機能（実験的）
- **セットアップ**: 機能フラグのみ（`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`）
- **ユースケース**: 迅速なプロトタイピング、クラウドベースの開発

**比較**:

| 側面 | Beadsフレームワーク | エージェントチーム |
|-----|----------------|--------------|
| **制御** | 完全（イベントソーシング、リプレイ） | 限定（ブラックボックス調整） |
| **セットアップ** | 複雑（Gas Town + agent-chat） | シンプル（機能フラグ） |
| **永続性** | SQLite（beads.db） | gitコミット |
| **可視性** | agent-chat UI（Slackライク） | ネイティブClaude Codeインターフェース |
| **環境** | オンプレミス対応 | クラウドファースト |
| **成熟度** | コミュニティ主導 | Anthropic公式 |

**Beadsを使うべき場合**:
- ✅ オンプレミス/エアギャップ要件（クラウドAPIコールなし）
- ✅ イベントリプレイが必要（調整のデバッグ）
- ✅ カスタム調整ロジック（gitベースを超えるもの）
- ✅ 永続的なエージェント通信（監査トレイル）

**エージェントチームを使うべき場合**:
- ✅ クラウド開発（Anthropic APIアクセス）
- ✅ 迅速なセットアップ（インフラ不要）
- ✅ gitネイティブのワークフロー（すでにgitを使用）
- ✅ 公式サポートパス（Anthropicが管理）

## 8. ベストプラクティス

### タスク分解の戦略

**明確な境界の原則**:
```
良い分解:
- エージェント1: バックエンドAPIエンドポイント（/api/users/*）
- エージェント2: フロントエンドコンポーネント（src/components/users/*）
- エージェント3: データベースマイグレーション（db/migrations/users/）

なぜ良いか:
- 重複しないファイルセット（マージコンフリクトなし）
- 明確なインターフェース（APIコントラクト）
- 独立したテスト（各レイヤーが個別にテスト可能）
```

```
悪い分解:
- エージェント1: ユーザー認証
- エージェント2: ユーザー認可
- エージェント3: ユーザーセッション管理

なぜ悪いか:
- 重複するファイル（auth.tsが3つ全てに触れる）
- 相互依存（認証はセッションを必要とし、セッションは認証を必要とする）
- 逐次結合（効果的に並列化できない）
```

**インターフェースファーストアプローチ**:
1. **コントラクトを定義**: 並列作業の前に関数シグネチャ、APIスキーマに合意
2. **型スタブ**: TypeScriptの型/インターフェースを先に作成し、別々に実装
3. **モック境界**: 各エージェントは最初にモックされた依存関係を使って作業
4. **統合フェーズ**: チームリードが最終統合を調整

**例**:
```typescript
// チームリードが最初にインターフェースを定義
interface UserService {
  authenticate(email: string, password: string): Promise<User>;
  authorize(user: User, resource: string): Promise<boolean>;
}

// エージェント1がauthenticateを実装
// エージェント2がauthorizeを実装
// マージコンフリクトなし（異なる関数）
```

### 調整パターン

**ファンアウト、ファンイン**:
```
チームリード
  │
  ├─ エージェント1: タスクA ──┐
  ├─ エージェント2: タスクB ──┼──> チームリードが統合
  └─ エージェント3: タスクC ──┘
```

**並列化を伴う逐次フェーズ**:
```
フェーズ1（逐次）:
  チームリード: アーキテクチャを定義

フェーズ2（並列）:
  ├─ エージェント1: バックエンドを実装
  ├─ エージェント2: フロントエンドを実装
  └─ エージェント3: テストを書く

フェーズ3（逐次）:
  チームリード: 統合 + 検証
```

**階層的な委譲**:
```
チームリード
  │
  ├─ エージェント1（バックエンドリード）
  │   ├─ エージェント1a: コントローラー
  │   └─ エージェント1b: サービス
  │
  └─ エージェント2（フロントエンドリード）
      ├─ エージェント2a: コンポーネント
      └─ エージェント2b: 状態管理
```

### gitワークツリー管理

**ワークツリーが重要な理由**:
- 各エージェントが別々のgitワークツリーで作業（隔離されたファイルシステム）
- ファイルロックのコンフリクトを防ぐ
- 並列ファイル変更を可能にする

**セットアップ**:
```bash
# メインリポジトリ
git worktree add ../project-agent1 main

# エージェント1はproject-agent1/で作業
# エージェント2はproject-agent2/で作業
# チームリードはproject/で作業

# 全てgitコミット経由で同期
```

**ベストプラクティス**:
- ✅ エージェントごとに1つのワークツリー
- ✅ 頻繁なコミット（継続的なマージ）
- ✅ 説明的なブランチ名（`agent1-backend-api`、`agent2-frontend-ui`）
- ❌ 調整なしにワークツリー全体で同じファイルを変更しない

### コスト最適化

**トークン節約の戦略**:

1. **遅延生成**: 並列化が明らかに有益な場合のみエージェントを生成
   ```
   悪い例: 「このボタンを実装するために3エージェントを生成してください」
   良い例: 「多層セキュリティレビューにエージェントを生成してください」
   ```

2. **コンテキストの剪定**: 関係ないファイルをエージェントのコンテキストから削除
   ```
   # エージェントに何を無視するか伝える
   「バックエンドAPIをレビューしてください。フロントエンドファイルは無視してください」
   ```

3. **段階的なエスカレーション**: 単一エージェントから始め、必要ならチームに昇格
   ```
   ステップ1: 単一エージェントがタスクを試みる
   ステップ2: 複雑度が高い場合、チームを生成
   ```

4. **結果キャッシング**: 類似タスク全体でエージェントの知見を再利用
   ```
   「エージェント1はauth.tsのセキュリティ問題を発見した。
   エージェント2、user.tsに同じパターンがあるか確認してください。」
   ```

### 品質保証

**検証チェックリスト**:
- [ ] **全エージェントが完了**: ハンギングタスクなし
- [ ] **マージコンフリクトを解決**: クリーンなgit履歴
- [ ] **テストが通過**: 自動テストスイートがグリーン
- [ ] **人間によるレビュー**: コードの検査（盲目的に信頼しない）
- [ ] **エージェント間の一貫性**: 命名、パターンが整合している

**危険信号**:
- ⚠️ エージェントが大きく異なる時間に終了（負荷の不均衡）
- ⚠️ 多くのマージコンフリクト（タスク分解が不適切）
- ⚠️ マージ後にテストが失敗（統合の問題）
- ⚠️ 一貫しないコードスタイル（エージェントが共有標準に従わなかった）

**軽減策**:
```bash
# エージェントチーム完了後
git diff main..agent-teams-branch  # 全変更をレビュー
npm test                           # フルテストスイートを実行
npm run lint                       # コードスタイルを確認
```


## 9. トラブルシューティング

### よくある問題

#### 問題：エージェントが生成されない

**症状**:
- エージェントチームのプロンプトが受け入れられたが、チームメイトが作成されない
- チームリードセッションのみが実行されている

**原因**:
1. 機能フラグが正しく設定されていない
2. モデルがOpus 4.6でない（チームはOpusが必要）
3. タスクが十分に複雑でない（Claudeが単一エージェントで十分と判断）

**解決策**:
```bash
# フラグを確認
echo $CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS  # 「1」または「true」が出力されるべき

# 設定を確認
cat ~/.claude/settings.json | grep agentTeams  # trueであるべき

# モデルを強制
/model opus

# 明示的に要求
「このタスクのために3エージェントを生成してください（チームリード + 2チームメイト）」
```

#### 問題：マージコンフリクトが多すぎる

**症状**:
- エージェント完了後に多くのgitコンフリクト
- 手動解決が頻繁に必要

**原因**:
- タスク分解が不適切（ファイルセットが重複）
- 書き込み重視のタスク（複数のエージェントが共有ファイルを変更）

**解決策**:
```
予防:
1. 明確な境界: 重複しないファイル割り当て
2. インターフェースファースト: 実装前にコントラクトを定義
3. 単一ライター: 1つのエージェントが共有ファイルを書き込み、他は読み取り

回復:
1. 元に戻す: git reset --hard before-agent-teams
2. 逐次実行: 単一エージェントで再実装
3. 手動マージ: コンフリクトを手動で解決（git mergetool）
```

#### 問題：トークンコストが高い

**症状**:
- トークン使用量が予想より3倍以上高い
- 予算がすぐに消耗する

**原因**:
- エージェントの過剰生成（シンプルなタスクに3以上のエージェント）
- 長時間のセッション（エージェントがアイドル状態）
- エージェントごとの大きなコンテキスト（100万トークン × 3）

**解決策**:
```
即時対応:
1. 余分なエージェントを終了: Shift+Down、エージェントセッションを終了
2. スコープを縮小: タスク境界を狭める
3. 単一エージェントに切り替え: /model sonnet（コストが安い）

長期的な対応:
1. コスト監視: セッションごとのトークン使用量を追跡
2. 遅延生成: 必要な場合のみ生成
3. 段階的なエスカレーション: 小さく始めて、必要に応じてスケールアップ
```

#### 問題：エージェントがスタック/ハングしている

**症状**:
- 1つのエージェントが終了し、他は長時間処理中のまま
- 進捗の更新がない

**原因**:
- タスク配分の不均衡（1つのエージェントが80%の作業を担当）
- 依存関係を待つエージェント（逐次結合）
- git調整のバグ（まれ）

**解決策**:
```bash
# スタックしたエージェントに移動
Shift+Down  # エージェントを切り替え

# ステータスを確認
「何を作業中ですか？進捗の更新をください」

# 必要に応じて手動引き継ぎ
「現在のタスクを停止し、これまでの知見を報告してください」

# 終了して再配布
エージェントを終了 → チームリードがタスクを再配布
```

#### 問題：エージェント間で結果が一致しない

**症状**:
- エージェント1が「問題なし」と言い、エージェント2が同じコードベースで10のバグを発見
- 相反する推奨事項

**原因**:
- 異なるコンテキストウィンドウ（エージェントが異なるファイルを確認）
- 曖昧な指示（エージェントが異なる解釈）
- モデルの変動性（確率的な出力）

**解決策**:
```
予防:
1. 明確な指示: 「全エージェント: SQLインジェクションを確認してください」
2. 共有コンテキスト: 全エージェントを同じリファレンスドキュメントに誘導
3. 検証: 人間が全エージェントの出力をレビュー

回復:
1. 照合: 「エージェント1とエージェント2の知見を比較し、コンフリクトを解決してください」
2. 第三の意見: エージェント3を仲裁に生成
3. 人間の判断: どちらのエージェントの推奨を採用するか自分で決める
```

### ナビゲーションの問題

**エージェントセッションが見つからない**:
```bash
# 全セッションをリスト
claude --list

# エージェントセッションでフィルタリング
claude --list | grep agent

# 特定のエージェントを再開
claude --resume <session-id>
```

**どのエージェントがどれかわからない**:
```
解決策: チームリードのプロンプトでエージェントに明示的に名前を付ける

良い例:
「3エージェントを生成してください:
- エージェント Security: 脆弱性を確認
- エージェント Performance: ボトルネックをプロファイル
- エージェント Tests: テストスイートを書く」

悪い例:
「このコードベースレビューのために3エージェントを生成してください」
```

**tmuxナビゲーションが機能しない**:
```bash
# tmuxセッションを確認
tmux list-sessions

# セッションにアタッチ
tmux attach -t claude-agents

# ナビゲート
Ctrl+b, n  # 次のウィンドウ
Ctrl+b, p  # 前のウィンドウ
```

### パフォーマンスの最適化

**調整が遅い**:
```bash
# gitリポジトリのサイズを確認
du -sh .git/  # 1GB超の場合はクリーンアップを検討

# gitオブジェクトをクリーンアップ
git gc --aggressive --prune=now

# エージェントにシャロークローンを使用
git clone --depth 1 <repo>
```

**コンテキスト読み込みの遅延**:
```
# エージェントごとのコンテキストを削減
「エージェント1: src/backend/*ファイルのみ読み込んでください」
「エージェント2: src/frontend/*ファイルのみ読み込んでください」

# 関係ないファイルを除外
echo "node_modules/" >> .gitignore
echo "dist/" >> .gitignore
```
