## 要約

```
1. 明確な目標を持つ初期プロンプト
2. Claudeが出力を生成
3. 基準に対して評価
4. 具体的なフィードバック: 「YのためにXを変更してください」
5. 完了するまで繰り返す
```

重要な洞察: **具体的なフィードバック > 曖昧なフィードバック**

## ループ

### ステップ1: 初期プロンプト

明確な意図と制約から始めます:

```
ユーザープロフィールカードのReactコンポーネントを作成してください。
- アバター、名前、プロフィール文章を表示する
- 編集ボタンを含める
- Tailwind CSSを使用する
- モバイル対応
```

### ステップ2: 出力を評価

Claudeがコードを生成します。評価する:
- 要件を満たしているか？
- 何が不足しているか？
- 何が間違っているか？
- 何が改善できるか？

### ステップ3: 具体的なフィードバック

ターゲットを絞った修正を提供します:

```
良いスタートです。変更が必要:
1. アバターは正方形ではなく丸くすること
2. 編集ボタンは自分のプロフィールのみに表示すること（isOwner propを追加）
3. プロフィール文章は3行で切り捨て「もっと表示」を追加すること
```

### ステップ4: 繰り返す

満足するまで続けます:

```
良くなりました。もう一つ:
- データをフェッチ中のローディングスケルトン状態を追加する
```

## フィードバックパターン

### 効果的なフィードバック

| パターン | 例 |
|---------|---------|
| **具体的な場所** | 「23行目: `===`を`==`に変更」 |
| **明確なアクション** | 「フォームの周りにエラーバウンダリを追加」 |
| **理由を示す** | 「console.logを削除、ユーザーデータが漏洩するため」 |
| **優先度を示す** | 「重要: SQLインジェクションを修正。あると良い: ページネーションを追加。」 |

### 効果的でないフィードバック

| アンチパターン | なぜ失敗するか | より良い代替 |
|--------------|--------------|-------------------|
| 「良くしてください」 | 方向性なし | 「バリデーションロジックを抽出して可読性を改善してください」 |
| 「これは間違い」 | 具体的でない | 「日付フォーマットはUnixタイムスタンプではなくISO 8601にすべき」 |
| 「好きじゃない」 | 主観的 | 「クラスコンポーネントの代わりに関数コンポーネントを使ってください」 |
| 「バグを直してください」 | 曖昧すぎる | 「修正: 1) 12行目のnullチェック、2) ループのオフバイワン」 |

## 自律ループ

Claudeは明確な完了基準で自己反復できます。

### Ralphパターン

自己改善ループパターンにちなんで名付けられました:

```
以下になるまでコード品質を改善し続けてください:
1. すべてのテストがパス
2. TypeScriptエラーなし
3. ESLintが警告ゼロを表示

各反復の後、チェックを実行して問題を修正してください。
すべての基準が満たされたら停止してください。
```

### 完了基準の例

```
以下になるまで反復する:
- 95パーセンタイルのレスポンスタイム < 100ms
- テストカバレッジ > 80%
- すべてのアクセシビリティチェックをパス
- バンドルサイズ < 200KB
```

### 反復制限

無限ループを防ぐために常に制限を設定します:

```
アルゴリズムのパフォーマンスを改善してください。
最大5回の反復。
反復間の改善が5%未満の場合は早期停止。
```

## Claude Codeとの統合

### タスクツールとの連携

`TaskCreate`と`TaskUpdate`を使ってリファインメントの反復を追跡します:

```
TaskCreate: 「初期バージョンを実装」
TaskCreate: 「修正: 空の配列を処理」
TaskCreate: 「修正: 入力バリデーションを追加」
TaskCreate: 「最適化: 高コストな計算をメモ化」
# 進めながらTaskUpdateで完了をマーク
```

### フックとの連携

各変更の後、Claude Codeフック（`/hooks`コマンドまたは`settings.json`経由で設定）を使って自動検証します。例えば、`Edit`ツールの`PostToolUse`フックはリンティングとテストを自動的に実行できます。Claudeは失敗を見て自己修正できます。

### /compactとの連携

反復中にコンテキストが増えた場合:

```
/compact

検索アルゴリズムのリファインメントを続けてください。
良い進捗を遂げました、残っている問題に焦点を当ててください。
```

### チェックポイント

大きな進捗の後:

```
良い進捗です。チェックポイントを設定しましょう:
- 現在のものをコミット
- 残っている問題をリストアップ
- 次の優先事項を続ける
```

## スクリプト生成ワークフロー

スクリプトと自動化の生成はイテレーティブ・リファインメントで最高のROIをもたらします — 実践者の報告では70〜90%の時間節約。スクリプトは自己完結型で、独立してテスト可能で、即座に価値をもたらします。

### 3〜7回の反復パターン

ほとんどの本番対応スクリプトは3〜7回の反復の後に登場します:

| 反復 | フォーカス | プロンプトパターン |
|-----------|-------|----------------|
| 1 | 基本的な機能 | 「[目標]を行うスクリプトを作成してください」 |
| 2〜3 | 制約 + エッジケース | 「[制約]を追加。[エッジケース]を処理。」 |
| 4〜5 | 強化 | 「エラーハンドリング、ロギング、入力バリデーションを追加」 |
| 6〜7 | ポリッシュ | 「[指標]のために最適化。使用方法のドキュメントを追加。」 |

### 例: KubernetesポッドマネージャーPowerShell

**反復1 — 基本**
```
KubernetesネームスペースでポッドをリストアップするPowerShell関数を作成してください。
```

**反復2 — フィルタリングを追加**
```
追加: ラベルセレクターとポッドステータスでフィルタリング。
表示: ポッド名、ステータス、経過時間、再起動回数。
```

**反復3 — アクションを追加**
```
追加: フィルターに一致するポッドを削除する機能。
要件: 削除前に確認を求める。
```

**反復4 — エラーハンドリング**
```
処理: kubectlが見つからない、無効なネームスペース、権限なし。
追加: -Verboseフラグを使った詳細なロギング。
```

**反復5 — 本番対応**
```
追加: ドライランモード、パイプ用のJSON出力、ヘルプドキュメント。
確認: Windows、Linux、macOSで動作する。
```

### よくある落とし穴

| 落とし穴 | 例 | 対策 |
|---------|---------|------------|
| ハルシネーションされたコマンド | macOSで`apt-get` | OSを指定: 「Ubuntu 22.04のみ」 |
| セキュリティギャップ | 入力バリデーションなし | 常にリクエスト: 「すべてのユーザー入力を検証」 |
| 過度な設計 | 不要なライブラリを追加 | リクエスト: 「依存関係を最小限に、stdlibを優先」 |
| コンテキストのドリフト | 5回目の反復後に要件を忘れる | チェックポイントプロンプト: 「次の変更前に現在の要件を要約して」 |
| プラットフォームの仮定 | shでbashの機能を仮定する | 指定: 「POSIX準拠」または「bash 4以上」 |

### スクリプト反復テンプレート

```
現在のスクリプト: [貼り付けるか参照]

反復の目標: [具体的な改善]

制約:
- 保持すべき: [保持する既存の動作]
- してはいけない: [避けること]
- ターゲット環境: [OS、シェル、ランタイム]

成功基準: [この反復が機能することを確認する方法]
```

## 反復戦略

### 幅優先

より深く進む前に同じレベルのすべての問題を修正:

```
最初のパス: すべての型エラーを修正
2回目のパス: すべてのLint警告を修正
3回目のパス: テストカバレッジを改善
4回目のパス: パフォーマンスを最適化
```

### 深さ優先

次に移る前に一つの領域を完全に完成させる:

```
1. 認証フローを完璧にする（すべての側面）
2. それからユーザー管理に移る
3. それから設定に移る
```

### 優先度ベース

重要度で対処:

```
この順番で反復する:
1. セキュリティ問題（重要）
2. データ整合性のバグ（高）
3. UXの問題（中）
4. コードスタイル（低）
```

## アンチパターン

### 動くターゲット

```
# 間違い
「実際には、アプローチを完全に変えましょう...」
（5回繰り返す）

# 正しい
アプローチにコミットして、その中で反復する。
アプローチが間違っている場合は、明示的に再スタートする。
```

### 完璧主義ループ

```
# 間違い
永遠に改善し続ける

# 正しい
明確な「十分に良い」基準を設定する:
- テストがパス
- 主要なユースケースを処理
- 重要な問題なし
→ リリースして後で改善する
```

### 失われたコンテキスト

```
# 間違い
50回の反復の後、目標が何だったか忘れる

# 正しい
定期的に目標を再述する:
「リマインダー: レートリミッターを構築しています。
現在の状態: 基本的な実装が動作している。
次: Redisバックエンドを追加。」
```

## レビュー自動修正ループ

コードレビューに特化した反復パターンで、ClaudeがレビューしてFixして再レビューして収束するまで繰り返します。

### パターン

```
┌─────────────────────────────────────────┐
│   レビュー自動修正ループ                │
│                                          │
│   レビュー（問題を特定）                │
│        ↓                                 │
│   修正（修正を適用）                    │
│        ↓                                 │
│   再レビュー（修正を検証）              │
│        ↓                                 │
│   収束（最小限の変更） → 完了           │
│        ↑                                 │
│        └──── 繰り返す（最大反復数）     │
└─────────────────────────────────────────┘
```

### プロンプトテンプレート

```
このPRを自動修正でレビューしてください:
1. マルチエージェントレビュー（3つのスコープに集中したエージェント）
2. すべての🔴 Must Fix問題を修正
3. 修正が新しい問題を導入しないか確認するために再レビュー
4. すべての🟡 Should Fix問題を修正
5. 最後にもう一度再レビュー
6. 🟢 Can Skipのみが残るまで停止

最大反復数: 3
変更が5行未満の反復では早期停止
```

### セーフガード

| セーフガード | 目的 | 実装 |
|-----------|---------|----------------|
| **最大反復数** | 無限ループを防ぐ | ハード制限: 3回の反復 |
| **品質ゲート** | 修正が有効か確認 | 各反復前に`tsc && lint`を実行 |
| **保護ファイル** | リスクの高い変更を防ぐ | 自動修正をスキップ: package.json、マイグレーション、.env |
| **変更閾値** | 収束したら停止 | 反復が5行未満の変更の場合は終了 |
| **ロールバック能力** | 悪い修正から回復 | 各反復の前にgitコミット |

### セッション例

**反復1: 初期レビュー**
```
Claude: 8つの問題を発見:
- 🔴 3 Must Fix（SQLインジェクション、空のcatch、認証の欠落）
- 🟡 4 Should Fix（DRY違反、N+1クエリ）
- 🟢 1 Can Skip（命名スタイル）
```

**反復2: Must Fixを修正 + 再レビュー**
```
Claude: 3つのMust Fix問題を修正しました。
再レビュー: すべての🔴が解決。新しい問題なし。
残り: 4つの🟡 Should Fix、1つの🟢 Can Skip
```

**反復3: Should Fixを修正 + 再レビュー**
```
Claude: 4つのShould Fix問題を修正しました。
再レビュー: すべての🟡が解決。新しい問題なし。
残り: 1つの🟢 Can Skip（任意の改善）
```

**収束**
```
Claude: 収束しました。任意の改善のみ残っています。
この反復の変更: 2行（閾値以下）。
レビュー完了。 ✅
```

### 比較: 1パスレビュー vs 収束ループ

| 側面 | 1パスレビュー | 収束ループ |
|--------|-----------------|------------------|
| **検出** | 一度すべての問題を見つける | 問題を見つける → 修正 → 検証 → 繰り返す |
| **フォローアップの認識** | git logの「Co-Authored-By: Claude」を確認 | 各反復が前の反復を認識している |
| **偽陽性** | すでに修正されたコードの修正を提案する可能性 | 再レビューがこれをキャッチする |
| **信頼度** | 単一の検証 | 複数の検証パス |
| **時間コスト** | 最速（1回のレビュー） | 遅い（3回以上のレビュー） |
| **品質** | 経験豊富な開発者向けに良い | セキュリティクリティカルなコードに適している |

**使う場面**:
- **1パス**: シンプルなPR、経験豊富なチーム、時間的プレッシャー
- **収束ループ**: セキュリティクリティカルなコード、ジュニアチーム、高リスクの本番

### マルチエージェントレビューとの統合

最高品質のために収束ループとマルチエージェントレビューを組み合わせる:

```
各反復:
├─ エージェント1: 一貫性監査員
├─ エージェント2: SOLID原則アナリスト
└─ エージェント3: 防御的コード監査員
     ↓
  問題を修正
     ↓
  3つのエージェントを再実行
     ↓
  修正を検証 + 新しい問題を確認
     ↓
  収束するまで繰り返す
```

### 収束基準

以下のいずれかが真の場合、反復を停止:

1. **問題なし**（理想的な結果）
2. **最大反復数に達した**（デフォルト3回）
3. **変更閾値**（反復が5行未満の変更）
4. **品質ゲートの失敗**（修正後にtsc/lintが失敗）
5. **手動停止**（ユーザーが停止を要求）

## コミュニティパターンと既知の制限

コミュニティはClaude Codeの反復ループの上にいくつかのパターンを構築しました。一部は実際の問題を解決し、他のものは知っておく価値のある現在の制限を公開しています。

### Ralphループ（テスト駆動の自律反復）

出典: nathanonn.com、2026年2月。

Ralphループは毎回フルスイートを実行する代わりに、サイクルごとに1つのテストケースに自律反復を制限します。これによって各サイクルが集中した状態に保たれ、エージェントが複数の失敗を一度に追いかけるのを防ぎます。

仕組み:

1. 1つの失敗テストケースを選ぶ
2. 修正し、パスすることを確認する
3. 進捗をJSONステートファイルに保存する
4. 次の失敗テストケースに移る
5. 同じケースで3回失敗した後、`known_issue`とマークしてスキップする

```json
{
  "current_case": "test_auth_token_refresh",
  "attempts": 2,
  "known_issues": ["test_legacy_migration_edge_case"],
  "completed": ["test_login", "test_logout", "test_session_timeout"]
}
```

ステートファイルがここでの重要なイノベーションです。コンテキストのリセット、`/compact`操作、セッションの再起動さえも生き残ります。エージェントは各サイクルの開始時にファイルを読み取り、どこで止まったか、どのケースが完了したか、どれをスキップするかを正確に知ります。

3回の試みの制限は、朴訥な自律ループを悩ます無限ループのトラップを防ぎます。固執するテストケースでトークンを消費するのではなく、エージェントは前進して後で人間がレビューするために問題にフラグを立てます。

### Auto-Continueスキル

出典: mcpmarket.com。

エージェントが続けるべきか人間の入力のために停止すべきかを決定する信頼ベースの継続システム。固定された反復カウントの代わりに、各サイクルの後に状況を評価します:

**自動継続する場合**:
- テストがパス
- ビルドが成功
- 新しいエラータイプが検出されない
- 信頼スコアが閾値以上

**人間の入力のために停止する場合**:
- 信頼スコアが閾値を下回る
- 新しいカテゴリのエラーが現れる（既知エラーの新しいインスタンスではなく）
- エージェントがこれまで見たことのない方法でビルドまたは型チェックが失敗する

これはClaude CodeのStopフックとうまく組み合わせられます。スキルはポストタスク検証をトリガーし、結果に基づいて再開するかどうかを決定できます。

### 自動検証のためのStopフック

Claude Codeのフックシステムを反復間の自動品質ゲートに変えるパターン:

1. Claudeがタスク（または反復）を完了する
2. `TodoWrite`の`PostToolUse`フックが検証スクリプトをトリガーする
3. スクリプトが型チェック、Lint、テストを実行する
4. エラーがClaudeに自動的にパイプされる
5. Claudeが人間の介入なしに問題を修正する

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "TodoWrite",
        "command": "bash -c 'npm run typecheck 2>&1; npm run lint 2>&1; npm test 2>&1'"
      }
    ]
  }
}
```

Claudeがタスクを完了とマークするたびにフックが発火します。検証が何かをキャッチすると、Claudeが出力を見て次のタスクに移る前に自己修正できます。

### エスカレーション戦略

同じ問題で3回の反復が失敗した場合の対処方法。永遠にループするか諦めるのではなく、構造化されたエスカレーションパスを辿ります:

1. **分解**: 失敗しているタスクを独立して取り組める2〜3つの小さなサブタスクに分解する
2. **コンテキストを収集**: すべてのエラーメッセージ、スタックトレース、試みた修正を構造化ファイルにダンプする
3. **モデルのエスカレーション**: Sonnetを使っている場合、特定の失敗したケースをより深い推論のためにOpusで再試行する
4. **人間へのエスカレーション**: モデルのアップグレードで解決しない場合、完全なエラーコンテキストとともにGitHubイシューを作成し、タスクを`known_issue`とマークする

```bash
# 実際のエスカレーション
if [ "$ATTEMPT_COUNT" -ge 3 ]; then
    # コンテキストを収集
    cat errors.log attempts.log > escalation-context.md

    # Opusで試す
    claude --model claude-opus-4-6 \
        "この失敗テストを修正してください。コンテキスト: $(cat escalation-context.md)"

    # それでも失敗する場合は、イシューを作成
    if [ $? -ne 0 ]; then
        gh issue create \
            --title "自動エスカレーション: $TEST_NAME が3回の試みの後に失敗" \
            --body "$(cat escalation-context.md)" \
            --label "known_issue,needs-human"
    fi
fi
```

目標は作業を黙ってドロップしないことです。すべての失敗は、解決されるか、エスカレーションされるか、明示的に追跡されます。

### 既知の制限

まだ機能していないことについて正直にあることで、存在しない解決策を再発明する時間を無駄にしないようにします。

**ネイティブのリトライ/検証/再開なし**（GitHubイシュー #28489）: Claude Codeのヘッドレス自動化は、リトライロジック、検証ゲート、セッション再開のネイティブサポートが欠けています。自律ループを実装するすべてのチームがこれの独自バージョンを構築します。ステートファイル、フックベースの検証、エスカレーションスクリプトはすべてプラットフォームのギャップのためのコミュニティの回避策です。

**エージェントの反復が失われる可能性**（GitHubイシュー #28843）: 複数日のワークフローでは、エージェントの反復とその蓄積されたコンテキストが破壊される可能性があります。複数のセッションや日にわたるワークフローを実行している場合は、N回の反復ごとに明示的なステートファイルを保存してください。Claudeの会話メモリだけを唯一の情報源として頼らないでください。

**複数日ワークフローの脆弱性**: 長期実行の自動化にはチェックポイントの規律が必要です。定期的にディスク（JSONファイル、gitコミット、イシューコメント）に状態を保存してください。パターンはシンプルですが忘れやすいです: ディスク上のファイルだけからエージェントの進捗を再構築できない場合、ワークフローはセッション境界で壊れます。
