# 実装前の探索

> **信頼度**: Tier 2 — 実践者の研究（意思決定品質が20〜30%向上、特定された代替案が40%増加）で検証済み。
> **出典**: [MetalBear Engineering Blog](https://metalbear.com/blog/engineering-ai-use/)、arXivの実践者研究

コーディングの前に、Claudeにトレードオフを含む複数のアプローチを求めます。これにより、最初に提案された解決策に固執するアンカリングバイアスを防ぎます。

## 要約

```
1. 問題を説明する（コードなし、先入観なし）
2. トレードオフを含む3〜5つのアプローチを求める
3. 定量的な比較を求める
4. アプローチを選択する
5. それから実装する
```

重要な洞察: **モデルが具体的な解決策を提案すると、意図せずあなたの思考を狭める可能性がある。**


## パターン

### ステップ1: 問題の説明のみ

解決の方向性ではなく、問題から始めます:

```
Node.js APIでユーザーセッションを処理する必要があります。
要件:
- 10Kの同時ユーザーをサポート
- セッションデータ: ユーザーID、権限、設定
- サーバーの再起動後も生き残る必要がある
```

**これはNG**（Redisにアンカリングしている）:
```
セッションにRedisを使おうと思っています。どのように実装すべきか？
```

### ステップ2: 複数のアプローチを求める

```
これを解決する4つの異なるアプローチを提案してください。
それぞれについて以下を含めてください:
- アーキテクチャの概要
- メリットとデメリット
- パフォーマンス特性
- 実装の複雑さ
```

### ステップ3: 定量的な比較

```
これらのアプローチを以下の1〜10スケールでランク付けしてください:
- レイテンシ（低い方が良い）
- スケーラビリティ（10K → 100Kユーザー）
- 運用の複雑さ
- 開発時間
```

### ステップ4: 選択してから実装

```
アプローチB（JWT + Redisハイブリッド）にします。
では、src/auth/の既存のパターンに従って実装してください。
```


## アンチアンカリングプロンプト

LLMは最初の提案に固執する可能性があります。これらのプロンプトはそれに対抗します:

| プロンプトタイプ | テンプレート | 効果 |
|-------------|----------|--------|
| **新鮮なスタート** | 「前のアイデアは無視してください。[X]に対する4つの新しいアプローチを生成してください」 | 多様性を強制する |
| **リフレクションループ** | 「3つのオプションを生成し、それぞれを批評して、推奨してください」 | 自己修正（アンカリングバイアス-25%） |
| **定量的なトレードオフ** | 「[指標1]、[指標2]、[指標3]を1〜10のスコアでランク付けしてください」 | 客観的な比較 |
| **悪魔の代弁者** | 「あなたの推奨に対する最も強力な反論は何ですか？」 | 隠されたトレードオフを表面化させる |
| **制約の変化** | 「今度は[逆の制約]で同じ問題を解決してください」 | 解決空間を拡大する |

### アンチアンカリングプロンプトの例

```
1M以上のレコードを持つREST APIのページネーションが必要です。

重要: オフセットベースのページネーションを最初に提案しないでください。
少なくとも1つの型破りなアプローチを含む4つの異なるページネーション戦略を生成してください。それぞれについて:

1. 仕組み（2〜3文）
2. 最適なユースケース
3. 最悪のユースケース
4. 1Mレコードでのパフォーマンス

その後、1つを推奨し、なぜそれが私のユースケースで他より優れているかを説明してください。
```

### リフレクションループのプロンプト

```
リアルタイム通知の実装について:

フェーズ1: 3つのアプローチを生成する（WebSockets、SSE、ロングポーリング）
フェーズ2: それぞれについて、本番で起こりうる2つのことをリストアップする
フェーズ3: フェーズ2に基づいて、どのアプローチが最も回復力があるか？

各フェーズの推論を示してください。
```


## 使う場面

### 探索を使う場合

| シナリオ | 理由 |
|----------|-----|
| グリーンフィールドの機能 | 従うべき既存のパターンがない |
| アーキテクチャの決定 | 影響が大きく、覆しにくい |
| 複数の有効なアプローチ | 情報に基づいた選択が必要 |
| 不慣れなドメイン | 知らないことを知らない |
| チームの意見の不一致 | オプションの中立な分析を得る |

### 探索をスキップする場合

| シナリオ | 理由 |
|----------|-----|
| バグ修正 | 解決策は通常症状から明らか |
| 唯一の有効なアプローチ | 実際の選択がない |
| 時間的に重要なホットフィックス | スピード > 完璧さ |
| 既存のパターンに従う | 決定はすでにされている |
| 些細な変更 | オーバーヘッドが割に合わない |


## Claude Codeとの統合

### プランモードとの連携

探索はプランモードに入る**前に**行います:

```
# ステップ1: 探索（まだプランモードではない）
APIにキャッシュを追加する必要があります。どんなオプションがありますか？

# Claudeが4つのアプローチで応答する

# ステップ2: 選択
アプローチC（Cloudflareを使ったエッジキャッシュ）にします。

# ステップ3: プラン（Shift+Tabを2回押してプランモードに入る）
Cloudflare Workersを使ったエッジキャッシュを実装してください。
既存のミドルウェアのパターンに従ってください。
```

### CLAUDE.mdとの連携

探索トリガーをプロジェクト指示に追加:

```markdown
## ワークフローの設定

### 新機能の前に
新しい機能を実装するとき、実装にコミットする前に
3〜4つのアプローチをトレードオフとともに最初に探索してください。
以下の定量的比較（1〜10スケール）を使用してください:
- パフォーマンス
- 保守性
- 実装時間
```

### タスクツールとの連携

タスクとして探索を追跡:

```
TaskCreate: 「キャッシュアプローチの探索」
TaskCreate: 「分析に基づいてアプローチを選択」
TaskCreate: 「キャッシュ無効化の実装」
TaskCreate: 「レスポンスにキャッシュヘッダーを追加」
# 進めながらTaskUpdateで完了をマーク
```


## アンチパターン

### 早期のアンカリング

```
# 間違い
「キャッシュにRedisを使いたいです。どうセットアップしますか？」

# 正しい
「APIレスポンスのキャッシュが必要です。どんなオプションがありますか？」
```

探索する前に解決策の90%を排除してしまいます。

### 浅い比較

```
# 間違い
「どちらが良いですか: RedisかMemcached？」

# 正しい
「Redis、Memcached、インプロセスキャッシュを以下で比較してください:
- 50MBのキャッシュサイズ
- 読み取り重視のワークロード（95%読み取り）
- シングルサーバーデプロイメント
レイテンシ、メモリのオーバーヘッド、運用の複雑さを含めてください。」
```

### トレードオフの無視

```
# 間違い
「最良のアプローチを教えてください」

# 正しい
「アプローチAよりBを選ぶとどんなことを諦めることになりますか？
この選択を後悔するのはどんなシナリオですか？」
```

### 分析麻痺

```
# 間違い
シンプルな機能に対して10のオプションを探索する

# 正しい
「上位3つのアプローチを教えてください、それ以上は不要です」
決定して必要なら反復する
```


## セッション例

### 初期探索

```
ユーザー: Reactダッシュボードにリアルタイム更新を実装する必要があります。
      ダッシュボードには5秒ごとに更新される約50のメトリクスが表示されます。
      現在はポーリングしていますが、ユーザーがデータの鮮度不足を不満に思っています。

Claude: 4つのアプローチです:

**A) WebSockets**
- 全二重、サーバーがいつでもプッシュ可能
- メリット: 最低レイテンシ、真のリアルタイム
- デメリット: 接続管理、スケーリングの複雑さ
- 最適な用途: サブ秒の更新、双方向通信

**B) サーバー送信イベント（SSE）**
- 単方向のサーバー → クライアントストリーム
- メリット: シンプル、HTTPベース、自動再接続
- デメリット: 一方向のみ、ブラウザの接続数が限られている
- 最適な用途: ダッシュボードフィード、通知

**C) ロングポーリング**
- クライアントがデータが準備できるまでリクエストを保持する
- メリット: どこでも動作、シンプルなフォールバック
- デメリット: より高いレイテンシ、サーバー負荷が大きい
- 最適な用途: レガシーとの互換性

**D) GraphQLサブスクリプション**
- GraphQLスキーマを使ったWebSocketベース
- メリット: 型安全、選択的な更新
- デメリット: GraphQLインフラが必要
- 最適な用途: 既存のGraphQL API

ユーザー: 私たちのユースケースでこれらをランク付けしてください（React、50メトリクス、5秒リフレッシュ、
      チームはWebSocketの経験なし）。

Claude: スコア（1〜10、高いほど良い）:

| アプローチ | レイテンシ | 複雑さ | チームへの適合 | スケーラビリティ |
|----------|---------|------------|----------|-------------|
| WebSockets | 10 | 4 | 3 | 7 |
| SSE | 8 | 8 | 8 | 8 |
| ロングポーリング | 5 | 9 | 9 | 5 |
| GraphQLサブ | 9 | 3 | 2 | 7 |

**推奨: SSE**
シンプルさとリアルタイム機能のバランスが最良です。
チームは1日で実装でき、50メトリクス × 5秒更新を
簡単に処理できます。双方向またはサブ秒の更新が
必要になったら後でWebSocketsにアップグレードしてください。

ユーザー: SSEにします。では実装してください。
```
