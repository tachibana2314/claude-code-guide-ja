## TL;DR — 5つの要点

1. **シンプルなループ**: Claude Codeは `while(tool_call)` ループを実行する — DAGも、分類器も、RAGもない。モデルがすべてを決定する。

2. **8つのコアツール**: Bash（ユニバーサルアダプター）、Read、Edit、Write、Grep、Glob、Task（サブエージェント）、TodoWrite。これが全ての武器庫だ。

   **検索戦略の進化**: 初期のClaude Codeバージョンは、セマンティックコード検索のためにVoyage embeddingsを使ったRAGを実験した。Anthropicは内部ベンチマークで、外部のembeddingプロバイダーからのセキュリティ上の問題なく、インデックス同期が不要なgrep ベース（ripgrep）のエージェント検索が優れたパフォーマンスを示したことから、このアプローチに切り替えた。この「検索して、インデックス化しない」哲学は、シンプルさ/セキュリティのためにレイテンシ/トークンをトレードオフとする。特殊なニーズ向けにはコミュニティプラグイン（ASTパターン用ast-grep）とMCPサーバー（シンボル用Serena、RAG用grepai）が利用可能。

   *ソース*: [Latent Spaceポッドキャスト](https://www.latent.space/p/claude-code)（2025年5月）、ast-grepドキュメント

3. **200Kトークンバジェット**: コンテキストウィンドウはシステムプロンプト、履歴、ツール結果、レスポンスバッファで共有される。約75〜92%の容量で自動コンパクト。

4. **サブエージェント = 分離**: `Task` ツールがサブエージェントを独自のコンテキストで生成する。サブエージェントはこれ以上サブエージェントを生成できない（depth=1）。要約テキストのみが返される。

5. **哲学**: 「足場を減らして、モデルをもっと活用する」— 周囲に複雑なオーケストレーションシステムを構築するよりもClaudeの推論を信頼する。

### これが意味すること

アーキテクチャ全体はシンプルな `while` ループです:

```
while (claude_response.has_tool_call):
    result = execute_tool(tool_call)
    claude_response = send_to_claude(result)
return claude_response.text
```

**以下のものは存在しません:**
- 意図分類器
- タスクルーター
- RAG/embeddingパイプライン
- DAGオーケストレーター
- プランナー/エグゼキューターの分割

モデル自身がいつツールを呼び出すか、どのツールを呼び出すか、いつ完了したかを決定します。これはAnthropicのエンジニアリングブログで説明されている「エージェントループ」パターンです。

### なぜこの設計？

1. **シンプルさ**: コンポーネントが少ない = 障害モードが少ない
2. **モデル駆動**: Claudeの推論はハードコードされたヒューリスティックより優れている
3. **柔軟性**: Claudeができることを制約する硬直したパイプラインがない
4. **デバッグ可能性**: 何が起こったのかとその理由を理解しやすい

## 2. ツール武器庫

**確信度**: 100%（Tier 1 - 公式）
**ソース**: [code.claude.com/docs](https://code.claude.com/docs/en/setup)

Claude Codeには正確に8つのコアツールがあります:

| ツール | 目的 | 重要な動作 | トークンコスト |
|--------|------|-----------|-------------|
| `Bash` | シェルコマンドの実行 | ユニバーサルアダプター、最も強力 | 低（コマンド）+ 変動（出力） |
| `Read` | ファイル内容の読み取り | 最大2000行、切り捨て処理 | 大きなファイルでは高い |
| `Edit` | 既存ファイルの変更 | diffベース、完全一致が必要 | 中 |
| `Write` | ファイルの作成/上書き | ファイルが存在する場合は最初に読む必要がある | 中 |
| `Grep` | ファイル内容の検索 | Ripgrepベース（正規表現）、RAG/embeddingアプローチを置き換えた。構造的なコード検索（ASTベース）については ast-grep プラグインを参照。トレードオフ: Grep（高速、シンプル）vs ast-grep（精密、セットアップ必要）vs Serena MCP（セマンティック、シンボル対応） | 低 |
| `Glob` | パターンによるファイル検索 | パスマッチング、mtime順でソート | 低 |
| `Task` | サブエージェントの生成 | 分離されたコンテキスト、depth=1の制限 | 高（新しいコンテキスト） |
| `TodoWrite` | 進捗の追跡 | 構造化されたタスク管理 | 低 |

### Bashユニバーサルアダプター

**重要なインサイト**: BashはClaudeのスイスアーミーナイフです。以下ができます:

- あらゆるCLIツールを実行（git、npm、docker、curlなど）
- スクリプトを実行
- パイプでコマンドをチェーン
- システム状態にアクセス

モデルは大量のシェルデータでトレーニングされており、特化したツールで不十分な場合にBashをユニバーサルアダプターとして使用することに非常に効果的です。

### ツール選択ロジック

Claudeはタスクに基づいてどのツールを使うかを決定します。ハードコードされたルーティングはありません:

```
┌─────────────────────────────────────────────────────┐
│           ツール選択（モデル駆動）                    │
├─────────────────────────────────────────────────────┤
│                                                     │
│  「auth.tsを読む」          → Readツール              │
│  「すべてのテストファイルを探す」→ Globツール          │
│  「TODOを検索」             → Grepツール              │
│  「npm testを実行」         → Bashツール              │
│  「コードベースを探索」      → Taskツール（サブエージェント）│
│  「進捗を追跡」             → TodoWriteツール         │
│                                                     │
│  モデルはトレーニング中にこれらのパターンを学習する    │
│  （明示的なルールからではない）                      │
│                                                     │
└─────────────────────────────────────────────────────┘
```

### 拡張ツールエコシステム

8つのコアツールを超えて、Claude Codeは以下を活用できます:

**MCPサーバー**（Model Context Protocol）:
- **Serena**: シンボル対応のコードナビゲーション + セッションメモリ
- **grepai**: セマンティック検索 + コールグラフ分析（Ollamaベース）
- **Context7**: 公式ライブラリドキュメントのルックアップ
- **Sequential**: 構造化された複数ステップの推論
- **Playwright**: ブラウザオートメーションとE2Eテスト
- **claude-code-ultimate-guide**: 12のツール — ガイド検索、リリース追跡、`compare_versions`、セキュリティ脅威のルックアップ（28のCVE + 655の悪意あるスキルを持つ `get_threat`、`list_threats`）、テンプレート検索（`search_examples`）— `npx -y claude-code-ultimate-guide-mcp`

**コミュニティプラグイン**:
- **ast-grep**: ASTベースの構造的なコード検索（明示的な呼び出し）

### 検索ツール選択マトリックス

Claude Codeはコードを検索するための複数の方法を提供し、それぞれ特定の強みを持っています:

| 検索ニーズ | ネイティブツール | MCP/プラグインの代替 | エスカレートするタイミング |
|-----------|-------------|-------------------|------------------------|
| 完全一致テキスト | `Grep`（ripgrep） | - | なし（最速） |
| 関数名 | `Grep` | Serena `find_symbol` | マルチファイルのリファクタリング |
| 意味による検索 | - | grepai `search` | 正確なテキストを知らない場合 |
| コールグラフ | - | grepai `trace_callers` | 依存関係分析 |
| 構造パターン | - | ast-grep | 大規模マイグレーション（>50kライン） |
| ファイル構造 | - | Serena `get_symbols_overview` | シンボルコンテキストが必要 |

**パフォーマンス比較**:

| ツール | 速度 | セットアップ | ユースケース |
|--------|------|------------|------------|
| Grep（ripgrep） | ⚡ 約20ms | ✅ なし | 検索の90% |
| Serena | ⚡ 約100ms | ⚠️ MCP | リファクタリング、シンボル |
| grepai | 🐢 約500ms | ⚠️ Ollama + MCP | セマンティック、コールグラフ |
| ast-grep | 🕐 約200ms | ⚠️ プラグイン | ASTパターン、マイグレーション |

**判断原則**: Grepから始めて（最速）、必要な場合のみ特化ツールにエスカレートする。

> **📖 深掘り**: すべての検索ツールを組み合わせた包括的なワークフローについては [Search Tools Mastery](../workflows/search-tools-mastery.md) を参照してください。

### システムプロンプトの内容

**確信度**: 100%（Tier 1 - Anthropic公式ドキュメント）
**ソース**:
- [Anthropicシステムプロンプトリリースノート](https://platform.claude.com/docs/en/release-notes/system-prompts)
- [Anthropicエンジニアリング: Claude Codeベストプラクティス](https://www.anthropic.com/engineering/claude-code-best-practices)

Claudeのシステムプロンプト（約5〜15Kトークン）は、透明性のコミットメントの一環としてAnthropicによって**公開されています**。これらのプロンプトは以下を定義します:

### 自動コンパクション

**確信度**: 75%（Tier 2 - コミュニティ検証済み、研究裏付けあり）

コンテキスト使用量がしきい値を超えると、Claude Codeは古い会話のターンを自動的に要約します:

| ソース | 報告されたしきい値 | 注記 |
|--------|----------------|------|
| VS Code拡張機能 | 約75%使用（25%残） | [GitHub #11819](https://github.com/anthropics/claude-code/issues/11819)（2025年11月） |
| CLIバージョン | 残り1〜5% | VS Codeより保守的 |
| PromptLayer分析 | 92% | 過去の観察 |
| Steve Kinney | 95% | [セッション管理ガイド](https://stevekinney.com/courses/ai-development/claude-code-session-management)（2025年7月） |
| ユーザーが実行する `/compact` | いつでも | 手動制御 |

**コンパクション中に何が起こるか:**

1. 古い会話のターンが要約される
2. ツール結果が圧縮される
3. 最近のコンテキストは完全に保持される
4. モデルが「コンテキストがコンパクトされた」というシグナルを受け取る

**パフォーマンスへの影響**（研究裏付けあり）:

最近の研究と実務家の観察によって**自動コンパクションによる品質低下**が確認されています:

- **複雑なタスクでのLLMパフォーマンスが1Kから32Kトークンに増加するにつれて50〜70%低下**（[コンテキスト劣化研究](https://research.trychroma.com/context-rot)、2025年7月）
- **12モデル中11モデルが32Kトークンで短いコンテキストパフォーマンスの50%を下回る**（NoLiMaベンチマーク）
- **自動コンパクションは繰り返し圧縮サイクルによってニュアンスを失い参照を破壊する**（[Claude Saves Tokens, Forgets Everything](https://golev.com/post/claude-saves-tokens-forgets-everything/)、2026年1月）
- **アテンションメカニズムが高コンテキストシナリオでの取得負荷に苦労する**

**コミュニティのコンセンサス**: 論理的なブレークポイントでの手動 `/compact` > 自動コンパクションがトリガーされるのを待つ。

**推奨戦略**（[Lorenz、2026](https://www.linkedin.com/posts/robin-lorenz-54055412a_claudecode-contextengineering-aiengineering-activity-7425136701515251713)）:

| コンテキスト % | アクション | 理由 |
|-------------|----------|------|
| **70%** | 警告 - クリーンアップを計画 | 早期の認識 |
| **85%** | 手動ハンドオフ推奨 | 自動コンパクションの劣化を防ぐ |
| **95%** | 強制ハンドオフ | 深刻な品質低下 |

**ユーザー制御**: 論理的なブレークポイントで要約をトリガーするために手動で `/compact` を使用するか、**セッションハンドオフ**（[セッションハンドオフ](#セッションの永続化)を参照）を使用して圧縮された履歴の上に意図を保持する。

### コンテキスト保持戦略

| 戦略 | 使用タイミング | 方法 |
|------|------------|------|
| サブエージェント | 探索的タスク | 分離された検索のための `Task` ツール |
| 手動コンパクト | プロアクティブなクリーンアップ | `/compact` コマンド |
| セッションのクリア | 新鮮なスタートが必要 | `/clear` コマンド |
| 特定の読み込み | 必要なものを知っている | ディレクトリではなく特定ファイルを読む |
| CLAUDE.md | 永続的なコンテキスト | メモリファイルに規約を保存 |

### セッション劣化の限界

**確信度**: 70%（Tier 2 - 実務家研究、arXiv研究）

Claude Codeの有効性は特定の条件下で予測可能に劣化します:

| 条件 | 観察されたしきい値 | 症状 |
|------|----------------|------|
| 会話のターン数 | **15〜25ターン** | 以前の制約を忘れる |
| トークンの蓄積 | **80〜100Kトークン** | セッション序盤に述べた要件を無視する |
| 問題のスコープ | **>5ファイル同時** | 一貫性のない変更、ファイルの見落とし |

**スコープ別の成功率**（実務家研究より）:

| スコープ | 成功率 | 例 |
|---------|------|-----|
| 1〜3ファイル | 約85% | 単一モジュールのバグ修正 |
| 4〜7ファイル | 約60% | コンポーネント間のフィーチャーリファクタリング |
| 8+ファイル | 約40% | コードベース全体の変更 |

**軽減戦略**:

1. **チェックポイントプロンプト**: 「続ける前に、現在の要件と制約を要約してください。」
2. **セッションのリセット**: 新しいタスクには新鮮に始める（`/clear`）
3. **スコープを絞る**: 大きなタスクを集中したサブタスクに分割
4. **サブエージェントを使用する**: メインコンテキストを保持するために `Task` ツールに探索を委任

### 失敗によるコンテキストドリフト

コンテキストサイズに依存しない別の劣化モード: ツールの繰り返し失敗。ツール呼び出しが失敗してClaudeが再試行すると、エラー出力がコンテキストウィンドウに蓄積します。スタックトレース、再試行ノイズ、エラーメッセージが元の意図を希薄化させます — 後続の試みはタスクの目標ではなく、エラーのナラティブに従います。コンテキストウィンドウは満杯ではありませんが、信号対雑音比が低下しています。

これはコンパクションドリフトとは異なります。コンパクションはコンテキストの*サイズ*に対処します; 失敗の再注入は限られたウィンドウ内のコンテキストの*品質*に対処します。

**パターン**: `/compact` の後だけでなく、すべてのコマンド失敗時にコアタスク指示を再注入する。`PostToolUse` フックが再試行されたプロンプトの先頭に元のタスクと制約の圧縮バージョンを付加できます:

```bash
# PostToolUseフック: 失敗後に意図を再注入
if [[ "$CLAUDE_TOOL_EXIT_CODE" != "0" ]]; then
  echo "リマインダー: 現在のタスクは: $ORIGINAL_TASK_SUMMARY。 上記のエラーが非ブロッキングなら無視してそのゴールに向かって続けてください。"
fi
```

ソース: [Nick Tune — Workflow DSL: Domain-Driven Claude Code Workflows](https://nick-tune.me/blog/2026-03-01-workflow-dsl-domain-driven-claude-code-workflows/)（2026-03-01）

## 4. サブエージェントアーキテクチャ

**確信度**: 100%（Tier 1 - ドキュメント化された動作）
**ソース**: [code.claude.com/docs](https://code.claude.com/docs/en/setup) + システムプロンプト（ツール定義で表示）

`Task` ツールは並行または分離された作業のためにサブエージェントを生成します。

### 分離モデル

```
┌─────────────────────────────────────────────────────────────┐
│                        メインエージェント                     │
│                                                             │
│  ┌───────────────────────────────────────────────────────┐  │
│  │ コンテキスト: 完全な会話 + すべてのファイル読み込み       │  │
│  │                                                       │  │
│  │         Task("認証パターンを探索")                     │  │
│  │                        │                              │  │
│  │                        ▼                              │  │
│  │  ┌─────────────────────────────────────────────────┐  │  │
│  │  │             サブエージェント（生成済み）           │  │  │
│  │  │                                                 │  │  │
│  │  │  • 独自の新鮮なコンテキストウィンドウ             │  │  │
│  │  │  • 受け取るもの: タスクの説明のみ                 │  │  │
│  │  │  • アクセスできるもの: 同じツール（Taskを除く）   │  │  │
│  │  │  • サブ-サブエージェントを生成できない（depth=1） │  │  │
│  │  │  • 返すもの: 要約テキストのみ                    │  │  │
│  │  │                                                 │  │  │
│  │  └─────────────────────────────────────────────────┘  │  │
│  │                        │                              │  │
│  │                        ▼                              │  │
│  │         結果: 「3つの認証パターンを発見: JWT...」        │  │
│  │         （このテキストのみがメインコンテキストに入る）    │  │
│  │                                                       │  │
│  └───────────────────────────────────────────────────────┘  │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### なぜdepth=1？

サブエージェントを1レベルに制限することで以下を防ぎます:

1. **再帰的な爆発**: エージェントのネストが無限のリソースを消費する
2. **コンテキストの汚染**: 各レベルがコンテキストを蓄積する
3. **デバッグの悪夢**: マルチレベルのエージェントチェーンを追跡するのが困難
4. **予測不可能なコスト**: ネストされたエージェント = 予測不可能なトークン使用量

### サブエージェントの種類

Claude Codeは `subagent_type` パラメーターを介して特化したサブエージェントタイプを提供します:

| タイプ | 目的 | 利用可能なツール |
|--------|------|---------------|
| `Explore` | コードベース探索 | すべての読み取り専用ツール |
| `Plan` | アーキテクチャ計画 | Edit/Writeを除くすべて |
| `Bash` | コマンド実行 | Bashのみ |
| `general-purpose` | 複雑なマルチステップ | すべてのツール |

### サブエージェントを使うタイミング

| ユースケース | サブエージェントが役立つ理由 |
|-----------|------------------------|
| 大規模コードベースの検索 | メインコンテキストをクリーンに保つ |
| 並行探索 | 複数の検索を同時に行う |
| リスクのある探索 | エラーがメインコンテキストを汚染しない |
| 特化した分析 | 異なるタスクに対して異なる「思考方法」 |

### 危険なパターンの検出

**確信度**: 80%（Tier 2 - 観察済みだが網羅的ではない）

Claude Codeは特定のパターンを特別な精査のためにフラグを立てるようです:

| パターン | リスク | 動作 |
|---------|------|------|
| `rm -rf` | 破壊的な削除 | 常にプロンプトを出す |
| `sudo` | 権限昇格 | 常にプロンプトを出す |
| `curl \| sh` | リモートコード実行 | 常にプロンプトを出す |
| `chmod 777` | 安全でないパーミッション | 常にプロンプトを出す |
| `git push --force` | 履歴の破壊 | 常にプロンプトを出す |
| `DROP TABLE` | データの破壊 | 常にプロンプトを出す |

これは完全なブロックリストではありません — パターンは明示的なルールではなくモデルのトレーニングを通じて検出される可能性が高いです。

### ネイティブサンドボックス（v2.1.0以降）

**確信度**: 100%（Tier 1 - 公式）
**ソース**: [code.claude.com/docs/en/sandboxing](https://code.claude.com/docs/en/sandboxing)

Claude Codeにはプロセスレベルの分離のためにOS レベルのプリミティブを使用したビルトインの**ネイティブサンドボックス化**が含まれています:

```
┌──────────────────────────────────────────────────────┐
│               ネイティブサンドボックスアーキテクチャ     │
├──────────────────────────────────────────────────────┤
│                                                      │
│  Bashコマンドのリクエスト                              │
│       │                                              │
│       ▼                                              │
│  サンドボックスラッパー（Seatbelt/bubblewrap）          │
│       │                                              │
│       ├─ ファイルシステム: 全読み取り、CWDのみ書き込み    │
│       ├─ ネットワーク: SOCKS5プロキシ + ドメインフィルタ │
│       ├─ プロセス: 分離された環境                      │
│       │                                              │
│       ▼                                              │
│  OSカーネルの強制                                     │
│       │                                              │
│       ├─ 許可: 境界内の操作                           │
│       ├─ ブロック: システムコールレベルでの違反           │
│       └─ 通知: 違反時にユーザーがアラートを受け取る       │
│                                                      │
└──────────────────────────────────────────────────────┘
```

**OSプリミティブ**:

| プラットフォーム | メカニズム | 注記 |
|--------------|---------|------|
| **macOS** | Seatbelt（TrustedBSD MAC） | ビルトイン、カーネルレベルのシステムコールフィルタリング |
| **Linux/WSL2** | bubblewrap（namespaces + seccomp） | 必要: `sudo apt-get install bubblewrap socat` |
| **WSL1** | ❌ サポートなし | bubblewrapには利用できないカーネル機能が必要 |
| **Windows** | ⏳ 計画中 | まだ利用不可 |

**分離モデル**:

1. **ファイルシステム**:
   - **読み取り**: コンピューター全体（拒否パスを除く）
   - **書き込み**: 現在の作業ディレクトリのみ（設定可能）
   - **ブロック**: CWD外への変更、クレデンシャルディレクトリ（`~/.ssh`、`~/.aws`）

2. **ネットワーク**:
   - **プロキシ**: すべての接続をSOCKS5プロキシ経由でルーティング
   - **ドメインフィルタリング**: 許可リスト/拒否リストモード
   - **デフォルトでブロック**: プライベートCIDR、localhostの範囲

3. **プロセス**:
   - **共有カーネル**: カーネルエクスプロイトに対して脆弱（Docker microVMとは異なる）
   - **子プロセス**: 同じサンドボックス制限を継承
   - **エスケープハッチ**: 互換性のないツール向けの `dangerouslyDisableSandbox` パラメーター

**サンドボックスモード**:

- **自動許可モード**: サンドボックス化された場合、Bashコマンドを自動承認（日常開発に推奨）
- **通常のパーミッションモード**: すべてのコマンドで明示的な承認が必要（高セキュリティ）

**セキュリティのトレードオフ**:

| 側面 | ネイティブサンドボックス | Dockerサンドボックス（microVM） |
|------|-------------------|--------------------------|
| **カーネル分離** | ❌ 共有カーネル | ✅ VM ごとに別々のカーネル |
| **セットアップ** | 0依存（macOS）、2パッケージ（Linux） | Docker Desktop 4.58以降 |
| **オーバーヘッド** | 最小限（約1〜3% CPU） | 中程度（約5〜10% CPU） |
| **ユースケース** | 日常開発、信頼できるコード | 信頼できないコード、最大セキュリティ |

**セキュリティの制限**:

⚠️ **ドメインフロンティング**: CDN（Cloudflare、Akamai）がドメインフィルタリングをバイパスできる
⚠️ **Unixソケット**: 設定ミスの `allowUnixSockets` が権限昇格を許可する
⚠️ **ファイルシステム**: 過度に広い書き込みパーミッションが `$PATH` ディレクトリへの攻撃を可能にする

**使用タイミング**:

- ✅ **ネイティブサンドボックス**: 日常開発、信頼できるチーム、軽量なセットアップ
- ✅ **Dockerサンドボックス**: 信頼できないコード、カーネルエクスプロイト保護、Docker-in-Dockerが必要

**詳細**: 完全な技術リファレンス、設定例、トラブルシューティングについては [ネイティブサンドボックスガイド](../security/sandbox-native.md) を参照してください。

### フックシステム

フックはClaudeのアクションをプログラム的に制御できます:

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [{
          "type": "command",
          "command": "/path/to/validate-command.sh"
        }]
      }
    ],
    "PostToolUse": [
      {
        "matcher": "*",
        "hooks": [{
          "type": "command",
          "command": "/path/to/audit-log.sh"
        }]
      }
    ]
  }
}
```

**フックの機能:**

| 機能 | サポート | 方法 |
|-----|---------|------|
| 実行のブロック | はい | 終了コード2 |
| パラメーターの変更 | はい | 変更されたJSONを返す |
| アクションのログ | はい | フックでファイルに書き込む |
| 非同期処理 | はい | フック設定で `async: true` を設定（v2.1.0以降） |

**フックのJSONペイロード**（stdinで渡される）:

```json
{
  "session_id": "abc123",
  "transcript_path": "/home/user/.claude/projects/.../transcript.jsonl",
  "cwd": "/path/to/project",
  "permission_mode": "default",
  "hook_event_name": "PreToolUse",
  "tool_name": "Bash",
  "tool_input": {
    "command": "npm install lodash"
  }
}
```

すべてのイベントに送られる共通フィールド: `session_id`、`transcript_path`、`cwd`、`permission_mode`、`hook_event_name`。イベント固有のフィールド（例: PreToolUseの `tool_name`/`tool_input`）がその上に追加されます。

→ **クロスリファレンス**: 完全な例については、メインガイドの [セクション7 - フック](./ultimate-guide.md#7-hooks) を参照してください。

## 6. MCP統合

**確信度**: 100%（Tier 1 - 公式）
**ソース**: [code.claude.com/docs/en/mcp](https://code.claude.com/docs/en/mcp)

MCP（Model Context Protocol）サーバーがClaude Codeを追加のツールで拡張します。

### MCPアーキテクチャの概要

> **💡 ビジュアルガイド**: 次のダイアグラムは、MCPがLLMと実際のシステムの間にどのように安全な制御層を作るかを示しています。LLM層は**直接データアクセスがありません** — MCPサーバーがツールがデータベース、API、またはファイルと対話する前にセキュリティポリシーを強制します。

![MCPアーキテクチャ — 7層セキュリティモデル](./images/mcp-architecture-diagram.svg)

*図1: thinking（LLM）、制御（MCPサーバー）、実行（ツール）の分離を示すMCPアーキテクチャ。[Dinesh KumarのLinkedinビジュアライゼーション](https://www.linkedin.com/posts/dinesh-kumar-6b0528b4_model-context-protocol-mcp-why-it-came-activity-7419969525795782656-VoFh)からデザインを参考に、Apache-2.0ライセンスで再作成。*

**重要なセキュリティ境界**:
- **黄色の層（LLM）**: 推論のみ — **データアクセスなし**
- **オレンジの層（MCPサーバー）**: セキュリティ制御ポイント（ポリシー、検証、ログ）
- **グレーの層（実際のシステム）**: 保護されたデータ — **AIから隠された**

### MCPの重要な事実

| 側面 | 動作 |
|------|------|
| プロトコル | stdioまたはHTTP上のJSON-RPC 2.0 |
| ツールの命名 | `mcp__<server>__<tool>` 規約 |
| コンテキスト共有 | ツールパラメーターと戻り値経由のみ |
| ライフサイクル | 最初の使用時にサーバーが起動、セッション中は起動状態を維持 |

| Claudeのシステムプロンプトの変更 | ツールのみ、プロンプトインジェクションなし |
| パーミッションのバイパス | ネイティブツールと同じセキュリティ層 |

### MCP拡張機能: Apps（SEP-1865）

**ステータス**: 安定版（2026年1月26日）
**仕様**: [SEP-1865 on GitHub](https://github.com/modelcontextprotocol/ext-apps)
**共同著者**: OpenAI、Anthropic、MCP-UIの作成者

#### MCP Appsとは？

MCP Appsは、Model Context Protocolへの**最初の公式拡張機能**で、MCPサーバーが従来のツールレスポンスと共に**インタラクティブなユーザーインターフェース**を提供できるようにします。

**解決される問題**: テキストベースの従来のレスポンスは、探索を必要とするワークフローでフリクションを生み出します。各インタラクション（ソート、フィルター、ドリルダウン）は新しいプロンプトサイクルを必要とします。MCP Appsは会話内で直接インタラクティブなUIをレンダリングすることでこの「コンテキストギャップ」を解消します。

#### 技術アーキテクチャ

**2つのコアプリミティブ**:

1. **UIメタデータを持つツール**:
   ```json
   {
     "name": "query_database",
     "description": "顧客データベースをクエリ",
     "_meta": {
       "ui": {
         "resourceUri": "ui://dashboard/customers"
       }
     }
   }
   ```

2. **UIリソース**（`ui://` スキーム）:
   - サーバーサイドのHTML/JavaScriptバンドル
   - ホストによってサンドボックス化されたiframeでレンダリング
   - `postMessage` 経由の双方向JSON-RPC通信

**通信フロー**:

```
┌─────────────────────────────────────────────────────────┐
│                  MCP APPSアーキテクチャ                   │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  ┌──────────────┐         ┌──────────────┐             │
│  │  MCPクライアント│◄───────►│  MCPサーバー │             │
│  │（Claude/IDE） │ JSON-RPC│ （あなたのApp）│             │
│  └──────┬───────┘         └──────────────┘             │
│         │                                               │
│         │ ui://リソースをフェッチ                        │
│         ▼                                               │
│  ┌─────────────────────────────────────────┐            │
│  │     サンドボックス化されたIframe（UIレンダー）│         │
│  │  ┌───────────────────────────────────┐  │            │
│  │  │  サーバーからのHTML/JSバンドル     │  │            │
│  │  │  - インタラクティブダッシュボード   │  │            │
│  │  │  - バリデーション付きフォーム       │  │            │
│  │  │  - リアルタイムデータの可視化      │  │            │
│  │  └───────────────────────────────────┘  │            │
│  │                                          │            │
│  │  postMessage ◄─────► JSON-RPC           │            │
│  └─────────────────────────────────────────┘            │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

#### セキュリティモデル

**多層保護**:

| 層 | 保護 |
|----|------|
| **Iframeサンドボックス** | 制限されたパーミッション（直接システムアクセスなし） |
| **事前宣言されたテンプレート** | ホストがレンダリング前にHTML/JSをレビュー |
| **監査可能なメッセージング** | すべてのUIからホストへの通信がJSON-RPCログ経由 |
| **ユーザーの同意** | UIが開始するツール呼び出しのオプション要件 |
| **コンテンツブロッキング** | ホストがレンダリング前に不審なリソースを拒否できる |

→ **クロスリファレンス**: より広範なMCPセキュリティの考慮事項については [セクション8.6 - MCPセキュリティ](./ultimate-guide.md#86-mcp-security) を参照してください。

#### SDK: @modelcontextprotocol/ext-apps

**インストール**:
```bash

```

**コアAPI**（フレームワーク非依存）:

```typescript

const app = new App();

// 1. ホストとの通信を確立

// 2. ホストからのツール結果を受け取る

```

### MCPツール検索（レイジーローディング）

**確信度**: 100%（Tier 1 - 公式）
**ソース**: [anthropic.com/engineering/advanced-tool-use](https://www.anthropic.com/engineering/advanced-tool-use)

v2.1.7（2026年1月）以降、Claude Codeはすべてのツールをコンテキストに事前読み込みする代わりに、MCPツール定義に**レイジーローディング**を使用しています。これはAnthropicの[Advanced Tool Use](https://www.anthropic.com/engineering/advanced-tool-use) API機能によって実現されています。

**解決される問題:**
- MCPツール定義は大量のコンテキストを消費する（例: GitHub MCPだけで93ツールに約46Kトークン）
- 開発者Scott Spenceが1つのプロンプトを入力する前に66,000以上のトークンが消費されていることをドキュメント化
- この「コンテキスト汚染」が実際のMCPの採用を制限していた

**ツール検索の動作:**

```
┌─────────────────────────────────────────────────────────────┐
│                   MCPツール検索フロー                         │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  ツール検索なし（積極的なローディング）:                       │
│  ┌──────────────────────────────────────────────────────┐   │
│  │全100+ツール定義が事前読み込み（約55Kトークン）          │   │
│  └──────────────────────────────────────────────────────┘   │
│                                                             │
│  ツール検索あり（レイジーローディング）:                       │
│  ┌──────────────────────────────────────────────────────┐   │
│  │ ステップ1: 検索ツールのみ読み込み（約500トークン）      │   │
│  │ ステップ2: Claudeが必要な機能を決定                    │   │
│  │ ステップ3: ツール検索が一致するツールを見つける（regex/BM25）│ │
│  │ ステップ4: 一致したツールのみ読み込み（約600トークン/各）│   │
│  │ ステップ5: ツールが通常通り呼び出される                 │   │
│  └──────────────────────────────────────────────────────┘   │
│                                                             │
│  結果: 55Kトークン → 約8.7Kトークン（85%削減）               │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**測定された改善**（Anthropicベンチマーク）:

| メトリック | 前 | 後 | 改善 |
|---------|-----|-----|------|
| トークンオーバーヘッド（5サーバーセットアップ） | 約55K | 約8.7K | **85%削減** |
| Opus 4ツール選択精度 | 49% | 74% | +25ポイント |
| Opus 4.5ツール選択精度 | 79.5% | 88.1% | +8.6ポイント |
| Opus 4.6適応型thinking | N/A | 自動調整 | 動的な深さ |

**設定**（v2.1.9以降）:

```bash
# 環境変数
ENABLE_TOOL_SEARCH=auto      # デフォルト（10%コンテキスト閾値）
ENABLE_TOOL_SEARCH=auto:5    # 積極的（5%閾値）
ENABLE_TOOL_SEARCH=auto:20   # 控えめ（20%閾値）
ENABLE_TOOL_SEARCH=true      # 常に有効
ENABLE_TOOL_SEARCH=false     # 無効（積極的なローディング）
```

| 閾値 | 推奨用途 |
|-----|---------|
| `auto:20` | 軽量なセットアップ（5〜10ツール） |
| `auto:10` | バランスのとれたデフォルト（20〜50ツール） |
| `auto:5` | パワーユーザー（100以上のツール） |

→ Simon Willisonが述べているように: 「コンテキスト汚染がMCPをめったに使わなかった理由です。それが解決された今、Claude Codeに数十または数百のMCPをフックアップしない理由はありません。」 — [X/Twitter、2026年1月14日](https://twitter.com/simonw)

### ファジーマッチングの詳細

完全一致が失敗した場合、Editツールは以下を試みます:

1. **空白の正規化**: 末尾のスペースを無視し、インデントを正規化
2. **改行コードの正規化**: CRLFとLFの違いを処理
3. **コンテキストの拡張**: 周囲の行を使用して正しい場所を特定

ファジーマッチングも失敗した場合、ツールはClaudeにold_stringを確認するよう求めるエラーを返します。

### 編集の検証

変更を適用する前に、Editツールは以下を確認します:

| チェック | 目的 |
|---------|------|
| ファイルが存在する | Editを通じてファイルを作成することを防ぐ |
| old_stringが見つかった | 正しい場所を編集していることを確認 |
| 単一一致 | old_stringが一意でなければならない（または `replace_all` を使用） |
| 新しいコンテンツが異なる | 無操作編集を防ぐ |

### Editが失敗する場合

| エラー | 原因 | Claudeの対応 |
|-------|------|------------|
| 「old_stringが見つからない」 | 最後の読み込み以来コンテンツが変更された | ファイルを再読み込みして再試行 |
| 「複数一致」 | old_stringが一意でない | より多くのコンテキスト行を使用 |
| 「ファイルが見つからない」 | 間違ったパス | 正しいパスを検索 |

## 8. セッションの永続化

**確信度**: 100%（Tier 1 - 公式）
**ソース**: [code.claude.com/docs](https://code.claude.com/docs/en/setup)

セッションはターミナルセッションを超えて再開できます。

### 再開メカニズム

| コマンド | 動作 |
|---------|------|
| `claude --continue` / `claude -c` | 最新のセッションを再開 |
| `claude --resume <id>` / `claude -r <id>` | IDで特定のセッションを再開 |

### 永続化されるもの

| 永続化されるもの | 永続化されないもの |
|--------------|----------------|
| 会話履歴 | ライブなツール状態 |
| ツール呼び出し結果 | 保留中の操作 |
| セッションID | ファイルロック |
| 作業ディレクトリのコンテキスト | 環境変数 |

### ストレージ形式

**確信度**: 50%（Tier 3 - 推測）

セッションは `~/.claude/` にJSON/JSONLファイルとして保存されているようですが:

- 形式は公開ドキュメント化されていない
- 安定したAPIとして意図されていない
- バージョン間で変更される可能性がある

外部ツール向けに**セッションファイル形式に依存しないでください**。

## 9. 哲学: 足場を減らして、モデルをもっと活用する

**確信度**: 100%（Tier 1 - 公式）
**ソース**: Daniela Amodei（Anthropicの共同創業者兼プレジデント）— 公開の発言

Claude Codeの背後にある哲学:

> 「少ないリソースでより多くを達成する。スマートなアーキテクチャの選択、より良いトレーニング効率、そして集中した問題解決が、生の規模と競争できる。」

### これが実際に意味すること

| 従来のアプローチ | Claude Codeのアプローチ |
|---------------|----------------------|
| 意図分類器 → ルーター → スペシャリスト | 単一のモデルがすべてを決定 |
| embeddingsを使ったRAG | Grep + Glob（正規表現検索） |
| DAGタスクオーケストレーション | シンプルなwhileループ |
| ツール固有のプランナー | モデル駆動のツール選択 |
| 複雑な状態マシン | 状態としての会話 |
| プロンプトエンジニアリングフレームワーク | モデルを信頼する |

### なぜ機能するのか

1. **モデルの能力**: Claude 4以降は分類ルーティングの決定を処理できる
2. **レイテンシの削減**: コンポーネントが少ない = より速いレスポンス
3. **シンプルなデバッグ**: 何かが失敗した場合、探す場所は1つ
4. **より良い汎化**: エッジケースで壊れるハードコードされたルールがない

### トレードオフ

| 利点 | 欠点 |
|-----|------|
| シンプルさ | きめ細かな制御が少ない |
| 柔軟性 | 厳格なふるまいの強制が難しい |
| バグが少ない | モデルのエラーがすべてに影響する |
| 高速なイテレーション | 良いモデルの品質が必要 |

### コミュニティの検証

「ネイティブ機能ファースト」アプローチは、外部の実務家によってますます検証されています。組み込みエンジニアリングチーム（以前のCursorのパワーユーザーを含む）は、外部のオーケストレーションフレームワークよりもAgent Skills標準に収束し、追加の足場層を構築するよりもClaudeのネイティブ推論を信頼することの実行可能性を示しています。

**例**: [Gur Sannikov](https://www.linkedin.com/posts/gursannikov_claudecode-embeddedengineering-aiagents-activity-7423851983331328001-DrFb)（組み込みエンジニアリング）は、外部フレームワークなしでネイティブのClaude Code機能（フック、スキル、Taskツール）のみを使用したADR駆動のワークフローを採用しました — このガイドでドキュメント化されたアーキテクチャ哲学を検証しています。

この収束は、「足場を減らして、モデルをもっと活用する」アプローチが、組み込みシステム開発などの複雑なエンジニアリングドメインでさえも、当初の予想を超えてスケールすることを示しています。
