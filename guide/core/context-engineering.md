## 1. コンテキストエンジニアリングとは

### 定義

Andrej Karpathy はこの言葉を作った: **「コンテキストエンジニアリングとは、コンテキストウィンドウに適切な情報を適切なタイミングで詰め込む技術だ。」**

この一文には、一見わかりにくい3つの要件が含まれている:

- **詰め込む**: コンテキストウィンドウは意図的に埋めるべきであり、偶然に任せてはならない。ほとんど空のままにすればモデルの能力を無駄にし、混沌と詰め込めばトークンを無駄にして出力品質を落とす。
- **適切な情報**: すべての情報が等価ではない。アーキテクチャの決定はlintの設定より価値がある。ネガティブな制約（「生のSQLエラーをクライアントに返さない」）は、前向きな目標（「きれいなコードを書く」）より実行しやすい。
- **適切なタイミング**: バックエンドコード向けのpath-scopedルールは、フロントエンドコンポーネントを編集しているときには意味がない。何でも常にロードする怠惰なアプローチは、遵守率を下げる。

### プロンプトエンジニアリングとコンテキストエンジニアリング

この2つはよく混同される。違いは重要だ:

| 軸 | プロンプトエンジニアリング | コンテキストエンジニアリング |
|-----------|-------------------|---------------------|
| スコープ | 1件のリクエスト | セッション全体またはシステム全体 |
| 継続性 | 単一インタラクション | インタラクションをまたいで持続 |
| 労力 | リクエストごとに作成 | 最初にシステム設計 |
| スケール | 個人 | チーム全体または組織全体 |
| 成果物 | プロンプト文字列 | 設定システム |

**プロンプトエンジニアリング**とは、1つのタスクに対して適切な質問を作ることだ。**コンテキストエンジニアリング**とは、クロードがどのタスクを始める前にも適切な背景知識を持てるよう保証するシステムだ。優れたプロンプトと粗末なコンテキストエンジニアリングを組み合わせても、依然として凡庸な結果しか得られない——なぜならモデルは、プロジェクト・規約・制約に関する構造的な理解を欠いているからだ。

実用的な類比: プロンプトエンジニアリングは請負業者へのわかりやすいメールを書くことだ。コンテキストエンジニアリングは、その請負業者がメールを1通も読む前にプロジェクトを理解できるよう保証するオンボーディングプロセス、コードスタイルガイド、アーキテクチャドキュメント、チームのノルムだ。

### なぜ重要か

LLMはコンテキストウィンドウコンピュータだ。出力の品質は入力の品質によって上限が決まる。これは曖昧な主張ではなく、技術的な根拠がある:

1. モデルはセッション間に持続的なメモリを持たない（明示的なツールがなければ）。コンテキストが意図的に提供されない限り、すべてのセッションはゼロから始まる。
2. モデルは明示されていない規約を推論できない。TypeScriptのインターフェースを `type` エイリアスの代わりに使いたいなら、それを明示しなければならない。エラーはthrowする前にログに記録したいなら、それを明示しなければならない。
3. モデルは命令の配置とフレーミングに敏感だ。500行のCLAUDE.mdの400行目に埋め込まれた命令は、最初の50行にある命令ほど守られない。

コンテキストエンジニアリングに投資しているチームは、一貫してリビジョンサイクルの減少、規約への遵守率向上、より予測可能な出力を報告している。投資は最初に集中する（システムの構築）が、リターンはすべてのインタラクションにわたって複利で増える。

役立つ診断フレームの転換: **AIの出力失敗のほとんどはコンテキストの失敗であり、モデルの失敗ではない。** クロードが一般的な返答をしたり、規約を無視したり、スタックに合わないコードを生成したとき、モデルがほぼ壊れているということはない——受け取ったコンテキストが不完全だったか、矛盾していたか、適切な情報が適切なタイミングで欠けていたのだ。このフレームの転換により、トラブルシューティングは「AIがこれが苦手」から「コンテキストに何が欠けているか」へとシフトする。

### 3つのレイヤー

Claude Codeにおけるコンテキストエンジニアリングは、3つの異なるレイヤーをまたいで機能する:

| レイヤー | メカニズム | スコープ | ロードタイミング |
|-------|-----------|-------|-------------|
| **グローバル設定** | `~/.claude/CLAUDE.md` | すべてのプロジェクト | 常時 |
| **プロジェクト設定** | `./CLAUDE.md` + path-scopedモジュール | 現在のプロジェクト | セッションごと |
| **セッション** | インライン命令、`/add`、フラグ | 現在のセッションのみ | 実行時 |

各レイヤーにはトレードオフがある。グローバル設定は常時オンだが、プロジェクト固有の詳細を参照できない。セッション命令は柔軟だが一時的だ。プロジェクト設定がもっとも重要な部分: 構造化されていて、バージョン管理され、レビュー可能だ。

優れたコンテキストエンジニアリングとは、各情報を適切なレイヤーに配置することだ——すべてを1つのファイルに詰め込んだり、重要な知識をセッションレイヤーに残してすべての会話後に消えてしまわせたりしない。

### 静的コンテキストと動的コンテキスト

上記の3レイヤーシステムは*静的コンテキスト*だ——セッション開始前にアセンブルされ、セッション中は安定した設定ファイルだ。Claude Codeは主に静的コンテキストシステムであり、だからこそCLAUDE.mdの構造とpath-scopingがこれほど重要なのだ。

エージェントワークフローに移行するにつれて、2番目のカテゴリが現れる: *動的コンテキスト*——エージェントの動作中に推論時にアセンブルされるものだ。

| 種別 | アセンブルの方法 | Claude Codeでの例 |
|------|--------------|-------------------------|
| **静的** | セッション前、ファイルから | CLAUDE.md、path-scopedモジュール、スキル |
| **動的** | 実行時、ツールから | ツール出力、ファイルの読み込み、Webフェッチ、MCPデータ |

実際には、すべてのClaude Codeセッションが両方を使う。静的コンテキスト（設定）が動作の包絡線を設定し、動的コンテキスト（クロードが読むファイル、処理するツール結果）が各タスクの具体的な情報を提供する。コンテキストエンジニアリングは両方をカバーするが、失敗のモードは異なる: 静的コンテキストの問題は一貫した規約違反として現れ、動的コンテキストの問題はタスク途中でクロードが古い情報や不完全な情報に基づいて行動するとして現れる。

自動化パイプラインとエージェントを構築しているチームには、Anthropicの2025年9月のエンジニアリングポスト ["Effective context engineering for AI agents"](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) が動的側面を詳しく解説している。


## 2. コンテキストバジェット

### トークン計算

中規模プロジェクトの具体的なベースライン:

| ソース | 典型的なトークン範囲 |
|--------|---------------------|
| グローバルCLAUDE.md | 1,000 – 3,000トークン |
| プロジェクトCLAUDE.md（ルート） | 2,000 – 8,000トークン |
| path-scopedモジュール（全アクティブ） | 1,000 – 5,000トークン |
| インポートされたスキル/コマンド | 500 – 3,000トークン |
| **常時オンコンテキスト合計** | **~5,000 – 20,000トークン** |

Claude Sonnet 4.6は200Kトークンのコンテキストウィンドウを持つ。つまり、大きな常時オン設定バジェット（20Kトークン）でさえウィンドウの約10%を占めるに過ぎない——実際の作業のために180Kトークンが残る: コードファイル、会話履歴、ツール出力。

実用的なルール: **常時オンコンテキストはコンテキストウィンドウの5%以下に収める。** それを超えると、実際のタスクコンテンツを圧迫することになる。1トークンあたりの価値では、タスクコンテンツの方が常駐命令より重要だ。

### 150ルール上限

大きなCLAUDE.mdファイルを運用するチームからの経験的な観察: 約150個の個別ルールを超えると、モデルはその一部を選択的に無視し始める。これは厳密なカットオフではなく——ルールの複雑さ、重複、配置に依存する——が、ルールが多ければ遵守率が上がるわけではないことを示す信頼性の高いシグナルだ。

メカニズムはアテンションの拡散: プロンプトに何百もの潜在的に関連する制約が含まれると、モデルのアテンションはそれらに分散される。高顕著性のルール（最近のもの、強い言い回し、早い配置）が低顕著性のルールを押しのける。

HumanLayerのプロダクションデータによると、構造化されたコンテキスト——少なく、より具体的なルール、階層的に整理——を持つチームは、未整理の長いルールリストを持つチームより15〜25%高い遵守率を示す。

含意: **ルールの品質はルールの数に勝る。** 20個の具体的で実行可能なルールは、200個の一般的な抱負ルールに勝る。

### ファイルサイズによる遵守率劣化

```
CLAUDE.mdの行数    遵守率（推定）
─────────────────  ─────────────────────
1 – 100            ~95%
100 – 200          ~88%
200 – 400          ~75%
400 – 600          ~60%
600+               ~45%以下、低下中
```

これらは推定ベースラインであり、保証ではない。path-scopingとモジュラーアーキテクチャは、任意の時点でコンテキストに関連するルールのみを保証することで、より大きな総ルール数でも高い遵守率を維持できる。

### コンテキスト過負荷のサイン

常時オンコンテキストが大きすぎるか雑音が多すぎると、予測可能な失敗モードが現れる:

- **ルールのサイレント化**: クロードは規約の80%を一貫して守るが、適用されるべき特定のルールを無視する。
- **矛盾した動作**: クロードはあるファイルではルールを適用するが他のファイルでは適用しない、あるいはフレーミングによって矛盾するルールを適用する。
- **最初の応答が遅い**: モデルが出力を生成する前に大きなコンテキストの処理に多くの時間を費やす（シンプルなタスクでの長いレイテンシとして観察可能）。
- **一般的な出力**: プロジェクト固有のパターンを適用する代わりに、クロードが一般的なベストプラクティスに後退する——プロジェクトコンテキストが維持されていないサイン。

これらのパターンが見られたとき、診断は: コンテキスト監査を実行する（セクション7参照）であり、さらに命令を追加することではない。

### path-scopingとバジェット効率

path-scopingは常時オンコンテキストを削減するための最も効果的な単一テクニックだ。コードベースのすべての部分のすべてのルールをロードする代わりに、現在のコンテキストに含まれるファイルに関連するルールのみをロードする。

path-scopingなしの典型的なプロジェクト:

```
常時オン: バックエンド + フロントエンド + データベース + APIルールを含むルートCLAUDE.md = 8,000トークン
```

path-scopingありの同じプロジェクト:

```
常時オン: 共有ルールのみのルートCLAUDE.md = 2,000トークン
src/api/内での作業時にアクティブ: apiモジュール = +1,500トークン
src/components/内での作業時にアクティブ: frontendモジュール = +1,200トークン
prisma/内での作業時にアクティブ: databaseモジュール = +800トークン
```

結果: カバレッジを失わずに常時オンコンテキストが40〜50%削減。各サブシステムはそのサブシステムで作業しているときのみ、フルルールセットを得る。


## 3. 設定の階層構造

### 3レイヤースタック

```
┌──────────────────────────────────────────────┐
│  グローバル (~/.claude/CLAUDE.md)             │
│  アイデンティティ、トーン、ユニバーサルツール、 │
│  クロスプロジェクト規約                        │
├──────────────────────────────────────────────┤
│  プロジェクト (./CLAUDE.md + pathモジュール)   │
│  アーキテクチャ決定、スタック規約、            │
│  チームルール、デプロイ手順                    │
├──────────────────────────────────────────────┤
│  セッション (インライン命令、フラグ)            │
│  アドホックなオーバーライド、実験制約、         │
│  ワンオフのタスクパラメータ                    │
└──────────────────────────────────────────────┘
```

後のレイヤーは前のものをオーバーライドする。セッション命令はプロジェクトルールをオーバーライドでき、プロジェクトルールはグローバルデフォルトをオーバーライドできる。これにより、共有設定に永続的な変更を要求することなく、エスケープハッチが得られる。

### グローバル設定

**場所**: `~/.claude/CLAUDE.md`

**ここに属するもの**:
- アイデンティティとコミュニケーションスタイルの設定
- ユニバーサルなツール設定（RTK、優先するCLIツール）
- クロスプロジェクトコーディング規約（コミットメッセージ形式、PRスタイル）
- どこにでも適用されるセキュリティ制約
- トーンと出力フォーマットのデフォルト

**ここに属さないもの**:
- プロジェクト固有のアーキテクチャ決定
- スタック固有のルール（Reactフック、Prismaパターン）
- デプロイや環境の詳細
- プロジェクトごとに変わるもの

**サイズ目標**: グローバル設定は200行以下に収める。これはすべてのプロジェクトのすべてのセッションでの常時オンオーバーヘッドだ。肥大化するとすべてのプロジェクトに等しく悪影響を与える。

```markdown
# 例: 最小限の効果的なグローバルCLAUDE.md

## コミュニケーション
- ユーザーが書いた言語と同じ言語で返答する
- 前置きより直接的な回答を優先する
- 書き言葉でemダッシュを使用しない

## Git
- コミットメッセージ: 命令形、件名行は72文字以内
- 頼まれない限りコミットしない

## コードスタイル
- サイレントな失敗より明示的なエラー処理を優先する
- TODOコメントは追跡されたissueを参照する場合のみ追加する
```

### プロジェクト設定

**場所**: `./CLAUDE.md`（プロジェクトルート）

**ここに属するもの**:
- 使用するテクノロジースタックとバージョン
- アーキテクチャ決定とその根拠
- このコードベース固有のチーム規約
- ファイル整理パターン
- テスト要件とカバレッジ目標
- このプロジェクト固有のセキュリティ制約
- サブシステムモジュールのpath-scopeインポート

**構造パターン**:

```markdown
# プロジェクト: [名前]

## スタック
- 言語: TypeScript 5.3
- フレームワーク: Next.js 14（App Router）
- データベース: Prisma経由PostgreSQL 16
- テスト: Vitest + React Testing Library

## アーキテクチャ
- デフォルトでServer Components; インタラクティビティが必要な場合のみ `"use client"` を使用
- APIルートは /app/api; ルートハンドラにビジネスロジックを入れない
- ビジネスロジックは /lib/services; 各サービスはプレーン関数モジュール

## 規約
- ファイル命名: ファイルにkebab-case、Reactコンポーネントにみ PascalCase
- エラー処理: サービス呼び出しをResult<T, E>パターンでラップ（lib/result.ts参照）
- APIレスポンスで生のデータベースIDを公開しない; UUIDを使用する

## path-scopedモジュール
@src/api/CLAUDE-api.md
@src/components/CLAUDE-components.md
@prisma/CLAUDE-db.md
```

### セッション設定

**メカニズム**: 現在のセッションのためのインライン命令、`/add-dir`、またはシステムプロンプトフラグ。

**ここに属するもの**:
- ワンオフのタスク制約（「このリファクタリングでは、パブリックAPIサーフェスを変更しない」）
- 実験パラメータ（「このファイルでテスト中の新しいエラーフォーマットを使用する」）
- デバッグ制約（「このセッションではすべてのツール呼び出しをログに記録する」）
- プロジェクト規約の一時的なオーバーライド

セッション命令は永続しない。セッションが終わると消える。セッションをまたいで繰り返し入力していることに気づいた命令は、セッションレイヤーではなくプロジェクト設定に属する。

### 判断ツリー: このルールはどこに置くか?

```
このルールは自分が作業するすべてのプロジェクトに関係するか?
├── はい → グローバルCLAUDE.md
└── いいえ ↓

このルールは特定のファイルやサブシステムに関係するか?
├── はい → path-scopedモジュール（例: src/api/CLAUDE-api.md）
└── いいえ ↓

このルールはプロジェクト全体に関係するか?
├── はい → プロジェクトCLAUDE.md（ルート）
└── いいえ ↓

このルールは現在のタスクまたはセッションのみに適用されるか?
├── はい → インラインセッション命令
└── いいえ → 再考: これは本当にルールなのか、それとも単なるワンタイムの設定か?
```

### インポートチェーンとオーバーライドセマンティクス

インポートチェーンは `グローバル → プロジェクトルート → path-scopedモジュール → セッション` の順に流れる。

競合が存在する場合:
- より具体的なものがより一般的なものをオーバーライドする（path-scopedはルートに勝り、ルートはグローバルに勝る）
- 同じレベルでは後に宣言されたものが先に宣言されたものに勝る
- セッション命令はすべての永続設定をオーバーライドする

**実用的な例**: グローバル設定が「2スペースインデントを使用する」と言っている。プロジェクト設定が「Pythonには4スペースインデントを使用する」と言っている。セッションが「既存のファイルスタイルに合わせる」と言っている。セッション命令がこのセッションで勝ち、Pythonファイルには4スペースのデフォルトが適用され、他のすべては2スペースになる。

オーバーライドは明示的にドキュメント化すること。親ルールと矛盾する無記録のオーバーライドは、監査時に混乱を生む。


## 4. モジュラーアーキテクチャ

### モノリシック設定の問題

構造のない600行のCLAUDE.mdは、プロダクション環境でもっともよく見られる失敗モードだ。症状:

1. 異なるドメインのルールが混在する——Reactコンポーネントのルールがデータベースマイグレーションルールの隣にある
2. クロードは600行すべてを読むが、アテンションバジェットの制約から5ページ目のルールは1ページ目のルールより少ない重みしか得られない
3. 新チームメンバーが関連するルールを素早く見つけられない
4. 更新のために、編集前に関連ルールを見つけるためにファイル全体をスキャンする必要がある
5. ファイルが成長するにつれて遵守率が漸進的に劣化する

修正はアーキテクチャ的だ: モノリスを焦点を絞ったモジュールに分解し、次にpath-scopingを使って各モジュールが関連するときだけロードする。

### path-scopingパターン

**メカニズム**: Claude CodeはCLAUDE.mdで `@path/to/file.md` インポートをサポートする。path-scopedインポートがアクティブなとき、そのモジュールからのルールは、指定されたパスの下のファイルがスコープ内にあるときのみコンテキストに追加される。

**ファイル構造**:

```
project/
├── CLAUDE.md                       # ルート設定、共有ルール + @インポート
├── src/
│   ├── api/
│   │   └── CLAUDE-api.md           # API固有のルール
│   ├── components/
│   │   └── CLAUDE-components.md    # React/UI固有のルール
│   └── lib/
│       └── CLAUDE-lib.md           # ユーティリティ/共有ライブラリのルール
├── prisma/
│   └── CLAUDE-db.md                # データベースとマイグレーションのルール
└── tests/
    └── CLAUDE-tests.md             # テスト規約
```

**インポートありのルートCLAUDE.md**:

```markdown
# プロジェクト設定

## 共有ルール
[...ここに共有ルール...]

## サブシステムモジュール
@src/api/CLAUDE-api.md
@src/components/CLAUDE-components.md
@src/lib/CLAUDE-lib.md
@prisma/CLAUDE-db.md
@tests/CLAUDE-tests.md
```

**path-scopedモジュールの例** (`src/api/CLAUDE-api.md`):

```markdown
# APIルール

- ルートハンドラは /app/api のみ; インラインにビジネスロジックを入れない
- すべてのエンドポイントは処理前にZodで入力バリデーションを行う
- エラーレスポンスは標準フォーマットを使用: { error: string, code: string }
- PIIを含む可能性のあるリクエストボディはログに記録しない; IDのみをログに記録する
- レートリミットヘッダーはすべてのパブリックエンドポイントに必要
- 認証: 個別ハンドラではなくミドルウェアでJWTを検証する
```

このモジュールの6ルールは `src/api/` で作業しているときのみコンテキストに含まれる。`src/components/` で作業しているときはコンテキストバジェットを消費しない。

### スキルとルール

この区別は活用されておらず、重要だ:

| 軸 | ルール | スキル |
|-----------|-------|--------|
| 性質 | 制約、標準、規約 | 能力、手順、ワークフロー |
| アクティブなとき | 常に適用 | 要求時に呼び出し |
| 例 | 「TypeScriptで `any` を使わない」 | 「新しいAPIエンドポイントの追加方法」 |
| 場所 | CLAUDE.md | `.claude/skills/` |
| トークンコスト | 常時オン | 呼び出し時のみロード |

**ルール**はクロードがデフォルトで何をすべきか、すべきでないかを定義する。許容できる出力の境界を設定する。

**スキル**は、プロジェクト固有のパターンの知識を必要とする複雑な多段階タスクの実行方法を定義する。特定のタイプのタスクを実行する必要があるときにロードされ、常にではない。

**実用的な例**: ルールは「APIエンドポイントにはZodバリデーションが必要」と言う。スキルは「このプロジェクトで新しいAPIエンドポイントを作成するためのステップバイステップのパターン、Zodスキーマパターン、エラー処理ラッパー、auth middlewareのフック、テストファイル構造を含む」と言う。

エンドポイント作成手順をルールに入れると、エンドポイントを作成していないときでも、すべてのセッションで40行の手続き的命令をロードすることになる。スキルに入れると、エンドポイントを作成するときのみその40行をロードできる。

**ルール**: `データベースのIDをAPIレスポンスで公開しない。`
**スキル**: `エンティティのUUIDベースのパブリック識別子を生成・使用する方法。`

### プログレッシブディスクロージャー

原則: すべてを事前にロードしない。現在のタスクに必要なものをロードする。

**コアコンフィグ（常時オン）**:
- アーキテクチャ決定とその根拠
- コーディング標準と命名規約
- セキュリティ制約
- ツール設定

**コンテキストモジュール（タスクごとにロード）**:
- デプロイ手順（デプロイ時にロード）
- APIパターン（APIレイヤーで作業時にロード）
- テストテンプレート（テスト作成時にロード）
- データベースマイグレーション手順（スキーマに触れるときにロード）

**スキルを使った実装パターン**:

```
.claude/
├── skills/
│   ├── deploy-production.md      # ロードタイミング: 「これをデプロイする」
│   ├── add-api-endpoint.md       # ロードタイミング: 「Xのエンドポイントを追加する」
│   ├── write-migration.md        # ロードタイミング: 「DBカラムを追加する」
│   └── create-component.md      # ロードタイミング: 「Xのコンポーネントを作る」
```

各スキルファイルにはプロジェクト固有のパターンを含むステップバイステップの手順が含まれる。クロードはタスクタイプが検出されたときにロードし、事前にはロードしない。

### アンチパターン: モノリシックCLAUDE.md

**どのように見えるか**:

```markdown
# CLAUDE.md（600行）

## ルール
1. TypeScriptを使う
2. anyタイプを使わない
3. コミット前にテストを実行する
4. APIエンドポイントには認証が必要
5. DBクエリにPrismaを使う
6. ReactコンポーネントはPascalCase
7. ./scripts/deploy.sh でデプロイする
8. リリース前にOWASP Top 10を確認する
[...あと492のルール...]
```

**なぜ失敗するか**:

- ルール1〜20が約95%のアテンション重みを得る; ルール500以上が約30%
- フロントエンド開発者が不要なバックエンドDBルールを読み、その逆も同様
- 論理的なグループ化がないため、関連するルールを見つけるにはすべてを読む必要がある
- 新しいルールを追加するには競合がないかファイル全体をチェックする必要がある
- ファイルが成長するにつれて遵守率が継続的に劣化する

**修正**:

1. ルールをドメインごとにpath-scopedモジュールに抽出する
2. ルートCLAUDE.mdを共有ルール + インポート宣言のみに保つ
3. 手続き的知識をスキルに移動する
4. 抽出後、ルートCLAUDE.mdを150行以下に目標設定する


## 5. チームアセンブリ

### N × M × P の問題

チームスケールでは、コンテキストエンジニアリングは組み合わせ論的な課題に直面する:

- **N人の開発者**: 異なる役割、ツール、コミュニケーション設定
- **Mのプロジェクト**: 異なるスタック、規約、デプロイターゲット
- **P の設定**: 各開発者 × 各プロジェクトに設定が必要

N × M個の個別CLAUDE.mdファイルを手動で管理するのは持続可能ではない。共有規約が変わると、N × Mファイルを更新する。新しいプロジェクトが作成されると、ゼロから構築する。開発者が役割を変えると、設定を再構築する。

解決策は**プロファイルベースのアセンブリ**: モジュールの共有ベースが一つ存在し、個別プロファイルがどのモジュールを含めるか、個人の設定をオーバーレイするかを宣言的に指定する。

N × M × P が N プロファイル × 1共有モジュールベースになる——管理可能だ。

### アセンブリスクリプト

アセンブリスクリプトはプロファイルを読み込み、指定されたモジュールをCLAUDE.mdに連結する:

```bash
#!/usr/bin/env bash
# scripts/assemble-context.sh

set -euo pipefail

PROFILE="${1:-}"
CHECK_MODE="${2:-}"

if [[ -z "$PROFILE" ]]; then
  echo "Usage: ./assemble-context.sh <profile-name> [--check]"
  exit 1
fi

PROFILE_FILE=".claude/profiles/${PROFILE}.yaml"
OUTPUT_FILE="CLAUDE.md"
MODULES_DIR=".claude/modules"

if [[ ! -f "$PROFILE_FILE" ]]; then
  echo "Profile not found: $PROFILE_FILE"
  exit 1
fi

# yq または python でプロファイルをパース
MODULES=$(python3 -c "
import yaml
with open('$PROFILE_FILE') as f:
    profile = yaml.safe_load(f)
for m in profile['modules']['include']:
    print(m)
")

# 出力をアセンブル
ASSEMBLED=$(mktemp)

echo "# Claude Code Configuration" > "$ASSEMBLED"
echo "# Generated from profile: $PROFILE" >> "$ASSEMBLED"
echo "# Generated at: $(date -u +%Y-%m-%dT%H:%M:%SZ)" >> "$ASSEMBLED"
echo "" >> "$ASSEMBLED"

while IFS= read -r module; do
  MODULE_PATH="${MODULES_DIR}/${module}"
  if [[ -f "$MODULE_PATH" ]]; then
    echo "## From: ${module}" >> "$ASSEMBLED"
    cat "$MODULE_PATH" >> "$ASSEMBLED"
    echo "" >> "$ASSEMBLED"
  else
    echo "WARNING: module not found: $MODULE_PATH" >&2
  fi
done <<< "$MODULES"

# 個人オーバーライドを追加
python3 -c "
import yaml
with open('$PROFILE_FILE') as f:
    profile = yaml.safe_load(f)
overrides = profile.get('overrides', [])
if overrides:
    print('## Personal Overrides')
    for o in overrides:
        print(f'- {o}')
" >> "$ASSEMBLED"

if [[ "$CHECK_MODE" == "--check" ]]; then
  if diff -q "$OUTPUT_FILE" "$ASSEMBLED" > /dev/null 2>&1; then
    echo "OK: CLAUDE.md matches profile $PROFILE"
    rm "$ASSEMBLED"
    exit 0
  else
    echo "DRIFT: CLAUDE.md does not match profile $PROFILE"
    diff "$OUTPUT_FILE" "$ASSEMBLED"
    rm "$ASSEMBLED"
    exit 1
  fi
fi

mv "$ASSEMBLED" "$OUTPUT_FILE"
echo "Assembled CLAUDE.md from profile: $PROFILE"
```

**使用法**:

```bash
# プロファイルからCLAUDE.mdを生成
./scripts/assemble-context.sh alice

# ドリフトを確認（CIで使用）
./scripts/assemble-context.sh alice --check
```

### CIドリフト検出

チームメンバーはプロファイルからCLAUDE.mdを再生成するが、ベースモジュールは時間とともに進化する。ドリフト検出なしでは、開発者が古い設定——セキュリティルールの追加や規約の更新より前のもの——を使っている可能性がある。

GitHub Actionsジョブがこれを検出する:

```yaml
# .github/workflows/context-drift.yml

name: Context Drift Detection

on:
  schedule:
    - cron: '0 9 * * 1'   # 毎週月曜日 9:00 UTC
  push:
    paths:
      - '.claude/modules/**'

jobs:
  check-drift:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: 依存関係のインストール
        run: pip install pyyaml

      - name: すべてのプロファイルのドリフト確認
        run: |
          DRIFT=0
          for profile_file in .claude/profiles/*.yaml; do
            profile=$(basename "$profile_file" .yaml)
            echo "Checking profile: $profile"
            if ! ./scripts/assemble-context.sh "$profile" --check; then
              echo "DRIFT detected in profile: $profile"
              DRIFT=1
            fi
          done
          exit $DRIFT

      - name: ドリフト時に通知
        if: failure()
        uses: actions/github-script@v7
        with:
          script: |
            github.rest.issues.create({
              owner: context.repo.owner,
              repo: context.repo.repo,
              title: 'Context drift detected — CLAUDE.md needs regeneration',
              body: 'One or more team profiles are out of sync with the current module library. Run `./scripts/assemble-context.sh <profile>` to regenerate.',
              labels: ['context-engineering']
            })
```

### プロファイルを使ったオンボーディング

新しいチームメンバーへのオンボーディング手順はこのようになる:

```bash
# 1. 役割に適したスタータープロファイルをコピー
cp .claude/profiles/template-frontend.yaml .claude/profiles/yourname.yaml

# 2. 自分の好みに合わせてプロファイルを編集
```

## 6. コンテキストのライフサイクル

### 命令負債

ルールは蓄積される。ほとんど削除されない。これが命令負債だ: 古くなった、冗長な、または矛盾したルールの漸進的な蓄積——それぞれがまだコンテキストバジェットを消費している。

命令負債のサイン:

- ルールが6ヶ月前に使用をやめたライブラリに言及している
- 2つのルールが同じパターンについて反対のことを言っている
- ルールが特定のマイグレーション中のみに適用されたエッジケースをカバーしている
- 同じ制約が異なるセクションで3回述べられている
- 開発者が現在の実践と競合するため特定のルールをコメントアウトしたり無視したりする

命令負債は複利でコストがかかる: 各競合または無関係なルールが有用なルールを押しのけ、ルールが競合するとモデルの動作が予測不可能になる。

**四半期監査のリズム**: 四半期ごと（または主要なプロジェクトマイルストーン後）にコンテキスト監査をスケジュールする。監査プロンプト:

```
CLAUDE.mdのすべてのルールを以下の観点でレビューする:
1. 関連性: これは現在のスタックとパターンにまだ適用されるか?
2. 具体性: これは実行可能か、それとも実施するには曖昧すぎるか?
3. 競合: これは別のルールと矛盾するか?
4. カバレッジ: これはより一般的なルールによってすでにカバーされているか?

各ルールについて、KEEP | UPDATE | ARCHIVE | DELETE として分類する
```

現在のCLAUDE.mdを与えて構造化された監査を依頼する実際のClaudeセッションとしてこれを実行する。

### 更新ループ

悪いClaudeの出力後のもっとも一般的な間違いは、出力を手動で修正して先に進むことだ。これは無駄にされた学習機会だ。

**悪いループ**:
```
クロードが間違ったパターンを生成
→ 開発者が手動で修正
→ 次のセッション: クロードが再び間違ったパターンを生成
→ 開発者が再び手動で修正
→ 無限に繰り返す
```

**良いループ**:
```
クロードが間違ったパターンを生成
→ 開発者が根本原因を特定（ルールが欠けている? 曖昧なルール? 競合するルール?）
→ 開発者がCLAUDE.mdを修正または新しいルールで更新
→ 次のセッション: クロードが正しいパターンを生成
→ ルールは設定に永続的に残る
```

更新ループは設定システムが経験から学ぶ方法だ。悪い出力はそれぞれ、コンテキストエンジニアリングに何かが欠けているか壊れているかのシグナルだ。CLAUDE.mdに対するバグレポートとして扱い、単なる一度きりの失敗として扱わない。

**ルール更新の実用的なフォーマット**:

失敗からルールを追加するとき、根拠をインラインで含める:

```markdown
- サービス関数には try/catch ではなく `Result<T, E>` 型を使用する
  （根拠: サービスレベルの try/catch は呼び出し元からエラー型を隠す;
   Resultは呼び出しサイトでの明示的なエラー処理を強制する）
```

根拠は2つの目的を果たす: 将来の監査担当者がルールが存在する理由を理解するのに役立ち、クロードがルールを正しく適用するためのより良いコンテキストを与える。

### スプリント後の知識フィード

各スプリントまたはリリースサイクルの終わりに、簡単な知識フィードセッションを実行する:

1. **新しいパターン**: 「このスプリントでYタイプの問題にXアプローチを標準化した。これをCLAUDE.mdに追加する。」
2. **発見されたアンチパターン**: 「Xを試したがYが原因となった。それを避けるルールを追加する。」
3. **アーキテクチャ決定**: 「ZのためにYよりXを使うことにした。クロードがYを提案しないようにドキュメント化する。」
4. **非推奨パターン**: 「Xから離れていく。代わりにYを使うルールを追加し、既存のX使用をフラグを立てる。」

これにより、大規模な定期的な見直しを必要とせず、コンテキストシステムを最新に保てる。

### ACEパイプライン

自動化または半自動化されたワークフローでClaude Codeを実行するチームのために、ACEパイプラインは構造化された実行モデルを提供する:

```
Assemble → Check → Execute
```

**Assemble**: チームプロファイル + プロジェクトモジュールからコンテキストを構築する。開発者とタスクコンテキスト固有のCLAUDE.mdを生成する。

**Check**: カナリア検証を実行する——実際のタスク前に主要な動作を検証する3〜5個のテストプロンプトのセット。カナリアチェックが失敗したら、先に進む前にコンテキストの問題を修正する。

**Execute**: 検証済みのコンテキストで実際のタスクに対してクロードを実行する。

```bash
#!/usr/bin/env bash
# ace.sh — Assemble, Check, Execute

PROFILE="${1:-}"
TASK="${2:-}"

if [[ -z "$PROFILE" || -z "$TASK" ]]; then
  echo "Usage: ./ace.sh <profile> <task-description>"
  exit 1
fi

echo "=== ASSEMBLE ==="
./scripts/assemble-context.sh "$PROFILE"

echo "=== CHECK ==="
./scripts/run-canaries.sh
CANARY_EXIT=$?

if [[ $CANARY_EXIT -ne 0 ]]; then
  echo "Canary checks failed. Fix context issues before executing."
  exit 1
fi

echo "=== EXECUTE ==="
claude "$TASK"
```

### セッション振り返り

各Claude Codeセッションの終わり、クローズする前に問う:

```
このセッションで構築または変更したものを踏まえて:
1. CLAUDE.mdにないどのパターンを使ったか?
2. ルールになり得る何を修正しなければならなかったか?
3. ドキュメント化すべきどんな決定をしたか?

このセッションに基づいてCLAUDE.mdの候補ルールを3〜5個生成する。
```

これは2〜3分かかり、具体的な改善候補を生成する。それを確認してどれを追加するかを決める。時間をかけて、これは設定システムが単なる一般的なルールではなく、真のプロジェクト知識を蓄積する方法だ。


## 7. 品質計測

### 自己評価の質問

CLAUDE.mdに対して定期的に（最低でも四半期ごとに）これらの質問を実行する:

**関連性**:
- このルールは現在のスタック、ライブラリ、チームの実践にまだ適用されるか?
- このルールはもはや存在しない問題のために書かれたか?
- 新チームメンバーはなぜこのルールが存在するかを理解するか?

**具体性**:
- このルールはいつ適用されるかをクロードが知るほど具体的か?
- このルールには少なくとも1つの具体的な例や反例があるか?
- 2人の開発者がこのルールを異なる解釈をするか?

**競合**:
- このルールは同じファイル内の別のルールと矛盾するか?
- このルールはpath-scopedモジュールのルールと矛盾するか?
- このルールはグローバルルールと、明示的にオーバーライドせずに矛盾するか?

**カバレッジ**:
- このルールはすでに存在するより一般的なルールの特定のケースか?
- このルールは他の場所に書かれているアーキテクチャ決定によってすでに示唆されているか?

これらのチェックのうち2つ以上に失敗するルールは、更新または削除の候補だ。

### カナリアチェック

カナリアチェックとは、クロードが主要な規約に従うことを確認するシンプルなテストプロンプトだ。CLAUDE.mdへの主要な変更の前後に実行して、リグレッションをキャッチする。

**構造**: 素早く回答できるほどシンプルで、遵守失敗を明らかにするほど具体的な3〜5個のプロンプト。

**React/TypeScriptプロジェクトのカナリアセット例**:

```bash
# scripts/run-canaries.sh

PASS=0
FAIL=0

check() {
  local name="$1"
  local prompt="$2"
  local expected_pattern="$3"

  result=$(claude "$prompt" --output-format text 2>/dev/null)

  if echo "$result" | grep -qE "$expected_pattern"; then
    echo "PASS: $name"
    PASS=$((PASS + 1))
  else
    echo "FAIL: $name"
    echo "  Expected pattern: $expected_pattern"
    echo "  Got: $(echo "$result" | head -5)"
    FAIL=$((FAIL + 1))
  fi
}

check "TypeScript interfaces" \
  "Generate a React component that accepts a name and age prop" \
  "interface.*Props"

check "Named exports" \
  "Create a utility function that formats a date" \
  "^export (function|const)"

check "No any type" \
  "Write a function that processes user data" \
  "^((?!: any).)*$"

check "Error result type" \
  "Write a service function that fetches user data from an API" \
  "Result<"

echo ""
echo "Canaries: $PASS passed, $FAIL failed"
[[ $FAIL -eq 0 ]]
```

**カナリアを実行するタイミング**:
- CLAUDE.mdへの変更をマージする前
- 新しいpath-scopedモジュールを追加した後
- チームメンバーが予期しないクロードの動作を報告したとき
- CIドリフト検出ジョブの一部として

### 遵守率の追跡

非公式だが効果的: CLAUDE.mdの各主要ルールについて、ルールが適用されるべき10回の連続したインタラクションにわたって、クロードがそれを違反する頻度を追跡する。

| ルール | 違反数 / 10回 | ステータス |
|------|----------------|--------|
| propsにTypeScriptインターフェースを使用 | 1/10 | 健全 |
| サービス関数にResultタイプを使用 | 0/10 | 健全 |
| APIレスポンスに生のデータベースIDを含めない | 3/10 | ルールを見直す |
| リクエストコンテキストIDの構造化ログ | 5/10 | ルールが曖昧すぎる |
| リリース前にOWASP Top 10を確認 | 8/10 | 現状では実行不可能 |

20%超の違反率を持つルールは3つの方法のいずれかで壊れている:
1. 一貫して適用するには曖昧すぎる
2. 別のルールと競合している
3. ファイルの後半すぎてアテンションが足りない

**「曖昧すぎる」の修正**: 遵守の具体的な例と違反の反例を追加する。

**「競合している」の修正**: 競合を見つけ、どのルールが優先されるかを決定し、負けたルールを更新または削除し、明示的なメモを追加する。

**「後半すぎる」の修正**: ルールをファイルの最初の3分の1に移動するか、そのセクション内のより目立つ位置に移動する。

### コンテキスト負債スコア

コンテキストエンジニアリングシステムの健全性を示す単一メトリクス:

```
コンテキスト負債スコア = (total_rules / 150) × (conflicts_found / total_rules) × 100
```

ここで:
- `total_rules` = ロードされたすべての設定ファイル全体での個別ルールの数
- `150` = アテンションの概算上限
- `conflicts_found` = 別のルールと矛盾するルール

| スコア範囲 | ステータス | アクション |
|-------------|--------|--------|
| < 30 | 健全 | 標準的な四半期監査 |
| 30 – 60 | 劣化 | 剪定と重複排除; 競合を修正 |
| 60 – 80 | 劣悪 | 大幅な再構成が必要 |
| > 80 | 深刻 | トップ30ルールでゼロから開始 |

**スコア計算の実行**:

```bash
# ルールのカウント（近似: - で始まる行）
TOTAL_RULES=$(grep -c "^- " CLAUDE.md 2>/dev/null || echo 0)

# 競合のカウントには手動レビューまたはLLM監査パスが必要
# 使用: claude "Scan CLAUDE.md and count rules that contradict each other. Return the count."

echo "Total rules: $TOTAL_RULES"
echo "Run conflict audit manually or with Claude"
```

### 経時的に追跡する有用なメトリクス

| メトリクス | 計測方法 | 目標 |
|--------|---------------|--------|
| 常時オンコンテキストサイズ | `wc -w CLAUDE.md ~/.claude/CLAUDE.md` | 5,000ワード以下 |
| ルール数 | `grep -c "^- " CLAUDE.md` | 150以下 |
| ファイルの年齢 | `git log --follow -p CLAUDE.md | head -20` | 6ヶ月ごとに主要なレビュー |
| 主要ルールごとの違反率 | 手動スポットチェック | 20%以下の違反 |
| カナリアの合格率 | `./scripts/run-canaries.sh` | 100%（すべて合格） |


## 8. コンテキスト削減テクニック

### path-scoping: 最高レバレッジのテクニック

path-scopingはカバレッジを失わずに常時オンコンテキストを40〜50%削減する。設定が約200行を超えるプロジェクトに対して、最も影響の大きい単一の構造的変更だ。

実装ステップ:

1. コードベースの自然なドメイン境界を特定する（API、フロントエンド、データベース、テスト、インフラ）
2. 各ドメインのために、ドメインディレクトリに `CLAUDE-{domain}.md` ファイルを作成する
3. ルートCLAUDE.mdからドメイン固有のルールを適切なモジュールに移動する
4. ルートCLAUDE.mdで移動したコンテンツを `@path/to/CLAUDE-domain.md` インポートに置き換える
5. カナリアチェックで遵守率を確認する

リファクタリング後の目標: ルートCLAUDE.mdを150行以下（共有ルール + インポート宣言のみ）に。

### ネガティブ制約

経験的に、ネガティブな制約（「Xをしない」）はポジティブな命令（「Xをする」）より悪いパターンを防ぐのに15〜25%優れている。これは反直感的だ——「Xをする」の方が明確に思えるかもしれない。しかし実際には、モデルは間違ったことをする誘惑に積極的に抵抗する必要があり、間違ったことを明示的に名指しして「絶対にするな」と言うことがより顕著だ。

| パターン | 表現 | 遵守率 |
|---------|-------------|-----------|
| ポジティブ（弱い） | 「すべてのバックエンドサービスに構造化ログを使用する」 | ~75% |
| ネガティブ（強い） | 「バックエンドサービスでは console.log を絶対に使わない; 構造化ロガー（pino）を使用する」 | ~90% |

**テクニック**: 間違ったパターンが一般的なデフォルトであるルール（生のtry/catch、console.log、デフォルトエクスポート、anyタイプ）では、避けるべき具体的なパターンを名指しするネガティブ制約としてルールをフレーミングする。

### ルール圧縮

長い説明的なルールはトークンを消費してアテンションを希薄にする。説明をその本質に圧縮する:

**圧縮前**（冗長、38ワード）:
```markdown
- Reactコンポーネントを作成するとき、propsには常にTypeScriptインターフェースを
  使用するようにし、読みやすさを向上させて再利用を可能にするために、
  インラインではなくコンポーネント宣言の前で定義する。
```

**圧縮後**（簡潔、9ワード相当）:
```markdown
- Reactのprops: TypeScriptインターフェース、コンポーネントの前に宣言、インラインは不可。
```

圧縮されたバージョンの方が遵守率が高い——短いルールはルールあたりのアテンション重みをより多く処理される。本当に理解に必要な場合の説明は、根拠フォーマット用に取っておく。

**圧縮のヒューリスティック**: ルールが1行を超える場合、余分なコンテンツが制約か説明かを問う。説明をコメント（`#` または `>` ブロッククォートで始まる）または根拠アノテーションに移動する。強制する制約は1行に収める。

### 重複排除

同じ制約が複数回述べられている（異なる言葉で）場合、それは強化されない——総アテンションバジェットを希薄にする。意味的な重複を見つけて削除する。

**重複の一般的な原因**:
- 一般的なセクションに1つのルール、path-scopedモジュールにより具体的なバージョン
- 問題を修正するために追加されたルール、それが上書きするより曖昧な元のルールを削除せずに
- マージ中に異なるチームメンバーの設定からコピーされたルール

**重複排除ワークフロー**:

```
CLAUDE.mdの意味的な重複をスキャンする。2つのルールが異なる言葉で
表現されていても同じ動作を制約する場合、それらは重複だ。すべての重複
ペアをリストし、具体性と明確さに基づいてどちらのバージョンを保持するかを
推奨する。
```

これをCLAUDE.mdに対するClaudeプロンプトとして実行する。提案を見直してマージする。

### アーカイブパターン

ルールを削除すると、なぜそれが存在したかの知識が失われる。その組織的な記憶は価値があり得る——6ヶ月後に、誰かがルールが防いでいたのと同じパターンを再導入しようとするかもしれない。

廃止されたルールを削除する代わりに、アーカイブする:

```
.claude/
├── CLAUDE.md              # アクティブなルール
└── CLAUDE-archive.md      # 廃止メモ付きの過去のルール
```

**アーカイブエントリのフォーマット**:

```markdown
## アーカイブされたルール

### [2026-01廃止] セッションストレージにMongoDBを使用する
置き換え: セッションストレージにはsessionsテーブルを使ったPostgreSQLを使用する。
理由: 単一データベースに標準化; MongoDBはセッションのみに使用されており、運用の複雑さを追加していた。
```

アーカイブはクロードによってロードされない——人間向けの参照ドキュメントだ。同じ議論と間違いが再発するのを防ぐ。

### ルールの80/20ルール

ほとんどのプロダクション設定では、ルールの20%がクロードの重要な決定の80%を占める。残りの80%のルールはエッジケース、スタイルの好み、めったに起きない状況をカバーする。

上位20%を特定する:

1. CLAUDE.mdのすべてのルールをリストアップする
2. 各ルールについて推定する: 「このルールはセッションでクロードの出力を意味のある形で変更する頻度はどのくらいか?」
3. 毎日適用されるルール: 保持し、優先し、早い位置に配置する
4. 毎週適用されるルール: 保持し、中間に配置する
5. 毎月適用されるルール: アーカイブするか、オンデマンドロードスキルに移動することを検討する
6. めったに適用されないルール: アーカイブする

目標はカバレッジを排除することではない——最も重要なルールが最も重要でないルールに希薄化されないことを保証することだ。

**配置が重要**: 上位20%のルールをCLAUDE.mdの最初の3分の1に配置する。アテンション重みは長いドキュメント全体で均一ではない——早いコンテンツがより高い顕著性を持つ。

### まとめ: 影響による削減テクニック

| テクニック | コンテキスト削減 | 努力 | 遵守率への影響 |
|-----------|------------------|--------|-----------------|
| path-scoping | 40-50% | 中程度 | +15-25% |
| ネガティブ制約 | 0%（再フォーミュレーション） | 低い | ルールごとに +15-25% |
| ルール圧縮 | 20-30% | 低い | +5-10% |
| 重複排除 | 10-20% | 低い | +5-15% |
| アーカイブパターン | 10-30% | 低い | +5-10% |
| 80/20優先順位付け | 0%（並べ替え） | 低い | +10-20% |

コンテキスト負債を抱えるプロジェクトの最高レバレッジの手順:

1. path-scope（最大の構造的勝利）
2. 重複排除（ノイズを削除）
3. 圧縮（残りのルールを鋭くする）
4. アーカイブ（廃止されたルールを安全にクリア）
5. 並べ替え（最も重要なルールを優先する）


## 9. 成熟度アセスメント

コンテキストエンジニアリングの能力はステージを経て発展する。ほとんどのチームはレベル2に達してとまる——より高いレベルが複雑だからではなく、レベル2での失敗が見えないからだ。出力品質は許容可能で、さらに進む圧力は現れない。このアセスメントはそのギャップを可視化する。

### 6つのレベル

| レベル | 名前 | 存在するもの | 失敗モード |
|-------|------|-------------|--------------|
| **0** | 設定なし | CLAUDE.mdのないLLM | 一般的な出力、プロジェクト認識ゼロ |
| **1** | フラット設定 | 単一のCLAUDE.md、構造なし | ルールが蓄積し、~100行後に遵守率が劣化 |
| **2** | 構造化設定 | セクション、明確な整理、グローバル/プロジェクトの分離 | 個人では機能するが、チームスケールで壊れる |
| **3** | モジュラー設定 | path-scopedモジュール、意図的なレイヤリング | ルールは維持されるが検証なし |
| **4** | 計測された設定 | カナリアテスト、遵守率追跡、ライフサイクル管理 | システムは機能するが時間とともに静かにドリフトする |
| **5** | エンジニアリングされたシステム | プロファイル、CIドリフト検出、ACEパイプライン、四半期監査リズム | — |

### 自己アセスメント

各質問に答える。最初の「いいえ」でとめる——それがあなたの現在のレベルだ。

**レベル0 → 1**: プロジェクトにCLAUDE.mdファイルがあるか?

**レベル1 → 2**: 設定はグローバル規約（`~/.claude/CLAUDE.md`）とプロジェクト固有のルール（`./CLAUDE.md`）を区別しているか? セクションは明確に分離されているか?

**レベル2 → 3**: サブシステム固有のルールはルートCLAUDE.mdではなくpath-scopedモジュールにあるか? ルートCLAUDE.mdは150行以下か?

**レベル3 → 4**: 主要な規約を検証するカナリアチェックがあるか? もっとも重要なルールの違反率を追跡しているか? 主要なマイルストーン後にコンテキスト監査を実行しているか?

**レベル4 → 5**: チームメンバーは直接編集するのではなくプロファイルからCLAUDE.mdをアセンブルするか? 設定がソースモジュールから乖離したときにアラートを出すCIドリフト検出はあるか? 新しいパターンを設定にフィードバックするセッション振り返りを実行しているか?

### 各レベルで何をすべきか

| 現在のレベル | 次のアクション |
|------------|-------------|
| 0 | 5〜10ルールの最小限のCLAUDE.mdを作成する。何が属するかは§3を参照。 |
| 1 | グローバルとプロジェクト設定を分割する。クロスプロジェクトの設定を `~/.claude/CLAUDE.md` に移動する。 |
| 2 | 最も高トラフィックな2〜3のサブシステムを特定する。それらのpath-scopedモジュールを作成する。 |
| 3 | もっとも違反されているルールのために3〜5個のカナリアプロンプトを書く。自動化する。 |
| 4 | チームメンバーにプロファイルを導入する。CIドリフト検出を追加する。セッション振り返りを始める。 |
| 5 | 四半期監査を維持する。システムは構築済み——作業は継続的なキャリブレーションだ。 |

ほとんどのチームは1つの午後でレベル0からレベル2に移行する。レベル3からレベル4に移行するには、より多くの設定ではなく計測の習慣が必要だ。より高いレベルでのボトルネックは知識ではない——設定を一回限りのセットアップではなく生きたシステムとして扱う規律だ。
