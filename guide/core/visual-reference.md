## 1. コンテキスト管理ゾーン

コンテキストウィンドウの使用率に基づいてどう対応するか（`/status` で確認）:

```
コンテキスト使用率
0%          50%         70%         90%       100%
├───────────┼───────────┼───────────┼──────────┤
│   GREEN   │  YELLOW   │  ORANGE   │   RED    │
│  自由に   │  慎重に   │ /compact  │  /clear  │
│  作業する │  選択的に │  今すぐ   │  必須    │
└───────────┴───────────┴───────────┴──────────┘
              ▲                       ▲
              │                       │
         読み込みと              リスク: 指示を
         ツール使用を            忘れる、
         選択的に               ハルシネーション
```

**ゾーン別アクション:**
- **グリーン（0〜50%）** — フルスピード。ファイルを読み、自由に探索する。
- **イエロー（50〜70%）** — 選択的に。不要なファイル読み込みを避ける。
- **オレンジ（70〜90%）** — すぐに `/compact` を実行。コンテキストが低下している。
- **レッド（90%以上）** — `/clear` を実行して再起動。レスポンスは信頼できない。

→ ソース: [ultimate-guide.md:1335](./ultimate-guide.md)


## 2. パーミッションモードのサイクル

`Shift+Tab` でモードを切り替える:

```
                 Shift+Tab              Shift+Tab
  ┌──────────┐ ────────────→ ┌───────────────┐ ────────────→ ┌───────────┐
  │ DEFAULT  │               │  AUTO-ACCEPT   │               │ PLAN MODE │
  │          │               │                │               │           │
  │ edit=ask │               │ edit=auto      │               │ edit=no   │
  │ exec=ask │               │ exec=ask       │               │ exec=no   │
  └──────────┘ ←──────────── └───────────────┘ ←──────────── └───────────┘
                 Shift+Tab              Shift+Tab
```

**各モードの使用タイミング:**

| モード | 使用タイミング | リスクレベル |
|-------|-------------|------------|
| **デフォルト** | 通常の開発 — 各変更をレビュー | 低 |
| **Auto-accept** | 信頼できるタスク（フォーマット、リファクタリング） | 中 |
| **Planモード** | 複雑/リスクのある操作 — 最初に安全に探索 | なし |

**ショートカット:**
- `Shift+Tab` — 次のモードへサイクル
- `Shift+Tab × 2` — デフォルトからplanモードへジャンプ
- `/plan` — planモードに直接入る
- `/execute` — planモードを終了する

→ ソース: [ultimate-guide.md:760](./ultimate-guide.md)


## 3. ワークフローパイプライン（9ステップ）

すべてのタスクの推奨ワークフロー:

```
  ┌─────────┐    ┌──────────┐    ┌────────────┐    ┌─────────────┐
  │1. START │───→│2./status │───→│ 3. 計画?   │───→│ 4. 説明     │
  │  claude │    │ ctx確認  │    │Shift+Tab×2 │    │ WHAT/WHERE  │
  └─────────┘    └──────────┘    │（リスクなら）│    │ HOW/VERIFY  │
                                 └────────────┘    └──────┬──────┘
                                                          │
      ┌───────────────────────────────────────────────────┘
      │
      ▼
  ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
  │ 5. diff  │───→│ 6. y/n   │───→│ 7. テスト│───→│8. コミット│───→│9./compact│
  │  レビュー│    │ 承認?    │    │   実行   │    │完了したら │    │ >70%なら │
  └──────────┘    └──────────┘    └──────────┘    └──────────┘    └──────────┘
```

**重要な原則:**
- **ステップ2**: 開始前に必ずコンテキストを確認。>70%なら最初に `/compact`。
- **ステップ3**: リスクのあること、複雑なこと、複数ファイルにはplanモードを使用。
- **ステップ4**: 具体的に — 曖昧なプロンプトは曖昧な結果を生む。
- **ステップ5**: すべてのdiffを読む。盲目的に承認しない。
- **ステップ9**: 各タスク後にコンパクト化してグリーンゾーンを保つ。

## 10. 検索ツール選択

適切な検索ツールを選ぶための3レベル意思決定ツリー:

**レベル1: 何を知っているか？**

```
正確なテキスト/パターンを知っているか？
│
├─ はい → rg (ripgrep) を使う
│  ├─ 既知の関数名: rg "createSession"
│  ├─ 既知のimport: rg "import.*React"
│  └─ 既知のパターン: rg "async function"
│
└─ いいえ → レベル2へ
```

**レベル2: 何を探しているか？**

```
検索の意図は何か？
│
├─ 「意味/概念で探したい」
│  → grepai を使う
│  └─ 例: grepai search "payment validation logic"
│
├─ 「関数/クラスの定義を探したい」
│  → Serena を使う
│  └─ 例: serena find_symbol --name "UserController"
│
├─ 「コード構造で探したい」
│  → ast-grep を使う
│  └─ 例: エラー処理のない async
│
└─ 「依存関係を理解したい」
   → grepai trace を使う
   └─ 例: grepai trace callers "validatePayment"
```

**レベル3: 最適化**

```
結果が多すぎる？
│
├─ rg → --type フィルターを追加またはパスを絞る
├─ grepai → --path フィルターを追加またはtraceを使う
├─ Serena → シンボルタイプでフィルター（function/class）
└─ ast-grep → パターンに制約を追加する
```

→ ソース: [search-tools-mastery.md:75](./workflows/search-tools-mastery.md)

## 17. TDD Red-Green-Refactorサイクル

テスト駆動開発の核心にある反復ループ:

```
                    ┌──────────────────────────┐
                    │                          │
                    ▼                          │
            ┌──────────────┐                   │
            │   🔴 RED      │                   │
            │              │                   │
            │  失敗する     │                   │
            │  テストを     │                   │
            │  書く         │                   │
            └──────┬───────┘                   │
                   │                           │
                   │ テストが失敗する            │
                   │ （期待通り）               │
                   ▼                           │
            ┌──────────────┐                   │
            │   🟢 GREEN   │                   │
            │              │                   │
            │  パスするた  │                   │
            │  めの最小限  │                   │
            │  のコードを  │                   │
            │  書く        │                   │
            └──────┬───────┘                   │
                   │                           │
                   │ テストがパスする            │
                   │ （最小限）                 │
                   ▼                           │
            ┌──────────────┐                   │
            │   🔵 REFACTOR│                   │
            │              │                   │
            │  テストを     │                   │
            │  グリーンに   │                   │
            │  保ちながら   │                   │
            │  クリーンアップ│                  │
            └──────┬───────┘                   │
                   │                           │
                   │ 次のフィーチャーへ          │
                   └───────────────────────────┘

重要なルール:
  RED    → 実装を書く前にテストが失敗しなければならない
  GREEN  → パスするための最低限のコードだけを書く（それ以上ではない）
  REFACTOR → 構造を改善、テストはグリーンのままでなければならない
  REPEAT → 一度に一つのフィーチャー、常にこの順序で
```
