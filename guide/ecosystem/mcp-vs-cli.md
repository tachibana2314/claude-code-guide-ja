# MCP vs CLI — 意思決定ガイド

**最終更新**: 2026年3月

> インタラクティブ版（ガイダンス表と実践者の声を含む）: [cc.bruniaux.com/ecosystem/mcp-vs-cli/](https://cc.bruniaux.com/ecosystem/mcp-vs-cli/)

このページでは、Claude Code が外部ツールやサービスにアクセスするための2つの統合パターン、MCP サーバーと CLI ツールを比較します。どちらが一律に優れているわけではありません。正しい選択はコンテキストによって異なり、実際の本番ワークフローのほとんどは両方を使っています。

---

## 各アプローチの概要

**MCP サーバー**は、セッション開始時にツールスキーマを Claude のコンテキストに注入します。Claude はパラメータ、型、説明を備えた利用可能ツールの構造化リストを参照し、それらのツールをネイティブに呼び出して構造化レスポンスを受け取ります。

**CLI ツール**は、Claude が Bash 経由で呼び出すシェルコマンドです。Claude は開発者と同じ方法でドライブします。コマンド文字列を組み立て、テキスト出力をパースする形です。起動時のスキーマ注入はなく、シェルがインターフェースになります。

## トレードオフ

### MCP の強み

| 利点 | 詳細 |
|-----------|--------|
| **構造化インターフェース** | ツールスキーマが Claude を正確に誘導 — フラグや引数のハルシネーションが減る |
| **複雑な認証** | OAuth、トークンリフレッシュ、シークレットのローテーションはサーバー側で処理 — プロンプト不要 |
| **構造化出力** | JSON レスポンスは Claude と下流エージェントが直接パースできる |
| **可観測性** | リモート MCP サーバーはすべての呼び出しをログ記録できる — エンタープライズの利用追跡と ROI 帰属に不可欠 |
| **大規模配布** | サーバーを一度更新すれば、接続しているすべてのクライアントに変更が反映。マシンごとのパッケージ管理が不要。 |
| **非技術ユーザー** | ターミナルを触らないユーザーも MCP コネクター経由でツールを透過的に利用できる |
| **能力の低いモデル** | 構造化スキーマが、CLI ヘルプテキストのパースが苦手なモデルを補完する |

### CLI の強み

| 利点 | 詳細 |
|-----------|--------|
| **コンテキストオーバーヘッドゼロ** | 起動時にスキーマが注入されない — コンテキスト予算が逼迫しているときに有効 |
| **決定論的なアクション** | 予測可能な出力を持つ明示的なコマンドは監査とテストが容易 |
| **人間と AI の共用** | 同一の CLI ラッパーが、手動で実行する開発者にも Claude にも機能する |
| **フロンティアモデル** | Claude Opus/Sonnet 4.6 は複雑な CLI（aws-cli、glab、gh）を構造化スキーマなしで直接ドライブできる |
| **速度** | 接続セットアップも MCP ハンドシェイクも不要 — 直接サブプロセス実行 |
| **シンプルさ** | リモートサーバー呼び出しチェーンよりもデバッグ・ログ・理解が容易 |
| **スキルのカプセル化** | スキルにラップされた CLI はユーザーから透明に見え、ツールロジックのバージョン管理が維持される |

### MCP の弱み

| 弱み | 詳細 |
|----------|--------|
| **スキーマのトークンコスト** | すべての MCP サーバーは、そのセッションでツールが使われるかどうかに関わらず、セッション開始時にフルのツールリストをコンテキストウィンドウに注入する |
| **接続オーバーヘッド** | 多くの MCP サーバーを接続しているとセッション起動が遅くなる |
| **デバッグの困難さ** | MCP サーバー内部の障害は、失敗したシェルコマンドよりも追跡が難しい |
| **メンテナンスの複雑さ** | リモート MCP サーバーの実行・更新・セキュリティ確保にインフラが必要 |
| **単純な API には過剰** | glab の機能の 20% しか提供しない GitLab MCP は、glab 本体よりも劣る |

### CLI の弱み

| 弱み | 詳細 |
|----------|--------|
| **可観測性なし** | ローカルマシン上のシェルコマンドは、運用・管理ツールから見えない |
| **配布問題** | チーム全体で CLI を最新状態に保つにはパッケージ管理の規律が必要（brew、scoop など） |
| **能力の低いモデルは苦手** | 能力の低いモデルはフラグをハルシネートしたり、ヘルプテキストの読み誤りが起きる — スキーマが助けになる |
| **マルチエージェント構造なし** | CLI 出力はパースが必要。構造化された MCP レスポンスはエージェント間ハンドオフでより信頼性が高い |
| **非技術ユーザーの障壁** | 設定済み CLI 環境を持つことを非技術ユーザーに期待できない |

## 4つの判断軸

「MCP か CLI か？」を問う前に、この4つの質問に答えてください。制約の強さが高い順に並んでいます。

### 1. エンドユーザーは誰か？

これが最も支配的な変数です。他のすべては二次的です。

- **非技術ユーザー**（チャットインターフェース使用、ターミナルなし）→ **MCP またはスキルでカプセル化された CLI**。生の CLI を非開発者ユーザーに提供することはできません。コネクターは MCP ベース、またはスキル内部で CLI を処理して見えなくする必要があります。
- **技術ユーザー / 開発者** → 質問2に進む。

### 2. ツールを動かすモデルはどれか？

- **フロンティアモデル**（Claude Opus/Sonnet 4.6）→ 複雑な CLI を直接ドライブできる十分な能力がある。構造化 MCP スキーマはそれに見合ったメリットなしにオーバーヘッドを加えるだけ。
- **小規模またはローカルモデル**（Qwen、Mistral、軽量デプロイ）→ 構造化 MCP スキーマが CLI パース能力の弱さを補完する。MCP の方が信頼性が高い。

### 3. 組織に可観測性が必要か？

- **必要**（エンタープライズ、経営層レポート、コンプライアンス、AI 投資の ROI 帰属）→ **MCP リモートサーバー**。ローカルの CLI 呼び出しは見えません。リモート MCP サーバーはすべてのツール呼び出しをログし、ユーザーに紐付け、ダッシュボードに流せます。ローカルマシン上の CLI でこれを再現することはできません。
- **不要**（個人開発者、ローカルワークフロー）→ 可観測性は制約ではない。CLI で問題なし。

### 4. ツールスキーマはどのくらい変わるか？

- **安定した API**（成熟したツール、バージョン管理されたインターフェース）→ MCP への投資は時間をかけて報われる。
- **急速に変化**または**薄いラッパー** → CLI の方がメンテナンスコストが低い。実際に使う5つのコマンドだけを公開する手製の glab ラッパーは、完全な API サーフェスを複製する GitLab MCP よりも耐久性がある。

## 状況別ガイダンス

クイックリファレンス — ルールではなく方向性のデフォルトです。

| 状況 | 傾向 | 理由 |
|-----------|-------------|-----------|
| 非技術ユーザー、チャットインターフェース | **MCP / スキル** | CLI はアクセス不能。コネクターは透明である必要がある |
| フロンティアモデル（Claude 4.x）、開発者ワークフロー | **CLI** | モデルがネイティブに処理。スキーマはオーバーヘッド |
| 小規模/ローカルモデル | **MCP** | スキーマがモデルを確実に誘導 |
| エンタープライズ、可観測性が必要 | **MCP リモート** | 使用状況のログ記録・帰属・レポートの唯一の手段 |
| チーム配布（10名以上の開発者） | **MCP** | 中央集中型更新 vs マシンごとの CLI メンテナンス |
| 個人開発者、ローカルマシン | **CLI またはスキル** | シンプル、高速、インフラ不要 |
| 決定論的なアクション（git、CI、デプロイ） | **CLI** | 明示的なコマンド、予測可能な出力、監査可能 |
| 複雑な認証（OAuth、トークンリフレッシュ） | **MCP** | サーバーが認証を処理。CLI では認証情報の配管が必要 |
| コンテキスト予算が逼迫 / 多数のツールをロード | **CLI** | 起動時のスキーマ注入なし |
| エージェント間の構造化出力 | **MCP** | JSON レスポンスはパースされた CLI テキストより信頼性が高い |
| 新しい統合のデバッグ/プロトタイピング | **CLI** | 検査が容易で、イテレーションが速い |
| ブラウザ自動化（非フロンティアモデル） | **MCP** | Playwright MCP が相互作用を確実に構造化 |
| ブラウザ自動化（フロンティアモデル、Claude Code） | **CLI + スキル** | playwright-cli + スキルの方が速く効率的と実践者から報告 |
| GitLab / GitHub アクセス | **CLI**（glab、gh） | 公式 CLI はほとんどの MCP ラッパーより機能が豊富 |
| ドキュメント検索（Context7） | **MCP** | CLI 相当なし。構造化ドキュメント取得のシェル代替手段なし |

## ハイブリッドがデフォルト

ほとんどの本番ワークフローはどちらか一方を選びません。両方を使い、それぞれが最も得意なレイヤーをカバーします。

**実践的な例**（実践者より）:

- **内側レイヤー**（ローカル開発イテレーション、git、ファイル操作、シェルスクリプト）→ CLI、高速、決定論的、オーバーヘッドなし
- **外側レイヤー**（CI/CD、共有インフラ、クロスチームサービス）→ MCP リモート、可観測、集中管理、スケーラブル
- **スキルレイヤー**（ユーザー向けアクション、非技術ユーザー向けにカプセル化された CLI ツール）→ スキルにラップされた CLI、エンドユーザーから透明

1つの答えを両方のレイヤーに適用することが間違いです。自分のために Claude Code ワークフローを構築するソロ開発者は、ほとんど CLI を使うべきです。非技術の同僚に AI アシスタントをデプロイするチームは、ほとんど MCP を使うべきです。

## MCP スキーマのトークンコスト — 数字で見ると

MCP サーバーは、セッション開始時にフルのツールリストをコンテキストに注入します。これはタダではありません。

10〜15 のツールを持つ典型的な MCP サーバーは、タスクが始まる前にセッションあたり 500〜2,000 トークンを注入します。5つの MCP サーバーを接続すると、そのツールが使われるかどうかに関わらず、毎セッション 2,500〜10,000 トークンのオーバーヘッドが発生します。

実際の影響: 10 の MCP サーバーをロードして特定のセッションで2つしか使わない場合、毎回8つ分のサーバースキーマのコストを払っていることになります。これはセッションが長くなり、高頻度のワークフローになるほど蓄積します。

**軽減策:**

- MCP サーバーをプロジェクトごとに選択的にロードする（プロジェクトレベル設定 vs グローバル設定）
- スキーマオーバーヘッドが蓄積する高頻度操作には CLI ツールを使用
- セッションごとのトークン使用量を監視して、ロードされているが未使用の MCP スキーマを特定
- タイトなループで頻繁に使うツールには CLI ラッパーを検討（コンパイル → テスト → 修正サイクル）

## この分野のツール

| ツール | 機能 | ステータス |
|------|-------------|--------|
| **RTK**（Rust Token Killer） | CLI 出力が Claude のコンテキストに届く前にフィルタリング — レスポンスの冗長性を削減、スキーマオーバーヘッドではない | 本番対応、積極的メンテナンス中 |
| **MCPorter**（steipete） | MCP サーバーをスクリプトから呼び出し、CLI ラッパーを生成し、型付き TS クライアントを出力する TypeScript ランタイム。MCP サーバーのテストや MCP アクセスが必要なフックの記述に有用。 | 3K スター、MIT、2週以上、使用可能 |
| **mcp2cli**（knowsuchagency） | MCP/OpenAPI/GraphQL をランタイム CLI に変換し、スキーマ注入を排除。96〜99% のトークン節約を主張。 | 1.2K スター、8日前 — ウォッチリスト、まだ本番対応ではない |

mcp2cli についての注記: コアの主張（MCP を CLI に変換してスキーマ注入を排除）は、アーキテクチャ的に有効です。しかし Claude Code は MCP 接続を内部で管理するため、トークン節約は標準的な Claude Code ワークフローには直接適用されません。Claude Code スキル統合（`npx skills add knowsuchagency/mcp2cli --skill mcp2cli`）が実際の入り口です。

## 実践者の声

経験豊富な Claude Code ユーザーからの代表的な意見をいくつか紹介します。

> 「私は決定論的なアクションには CLI を好みます。GitLab のやり取りには glab を使います（GitLab MCP は機能が限られすぎている）。カスタム CLI にラップして、人間にも AI にも使えるようにしています。」— 実践者

> 「フロンティアモデルを使った Claude Code では、MCP は少ない方がいい。playwright-mcp を playwright-cli + スキルに置き換えました。速くて効果的です。CLI 相当が見つからないので context7-mcp だけ今でも使っています。」— 実践者

> 「CLI vs MCP の議論は、開発者として開発をしているユーザーの間でしか起きていません。でも根本的な制約が1つあります。単純にツールを使いたい非技術ユーザーに CLI ソリューションを提案することはできません。」— 実践者

> 「エンタープライズの産業化には、可観測性は絶対条件です。ローカルマシン上の CLI はブラックボックスです。MCP リモートは、経営層が投資を帰属させるために必要なロギングを提供します。」— 実践者

> 「フロンティアモデルは CLI を直接ドライブできる十分な能力があります。能力の低いローカルモデルは苦戦します。そこで MCP スキーマがオーバーヘッドに見合う価値を発揮します。」— 実践者
